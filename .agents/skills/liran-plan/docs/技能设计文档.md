## 一、核心目标

`liran-plan` 用来把用户的口语化项目想法，整理成 AI 能稳定执行、可检查、可接力、可真机验收的文档体系。

## 1.1 PRD 事实源边界

具体修改任务从首轮需求整理开始使用 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`。先创建聊天式需求整理文档，后续每轮更新同一文件；用户确认“需求整理好了”后，根据整理结果重新生成独立正式 PRD。正式 PRD 只记录产品/功能需求、稳定 REQ/AC、边界和关联文档索引，不复制 Goal 合同、微观任务、开发流水、测试执行、真机执行、UI 接收或归档日志。Goal、模块/微观任务、04、08、09、10 和 archive 各自保存执行事实。

唯一闭环顺序固定为：需求整理文档 → 正常聊天整理 → 用户确认整理完成 → 正式 PRD → PRD 确认 → 可选 UI 壳 → 内部开发 → 真机实测 → 问题回写 → 修复复测 → 安全归档。每一步以前一步的真实产物为门禁。

需求收口先询问“需求整理好了吗？整理好了的话，请回复‘需求整理好了’”，再转换并输出正式 PRD；用户必须通过“PRD 没问题”确认后才能进入后续目标。凡需选择的节点都必须提供纯文本选项，原生选择器不可用时使用“选项一：……”回退，缺选项不得继续。

核心三句话：

```text
需求没整理清楚前，不开干。
目标模式没收口前，不吐下一条命令。
已确认的 Codex 真机测试或用户验收没通过前，不标完成。
```

补充原则：

```text
提示词要信息完整但不重复。普通目标提示词采用文件指针型短格式，正文写清任务 ID、档位、目标 N/M、阶段、读取文件、执行边界、验证、状态回写、完成条件和下一阶段解锁条件；不复制 PRD 或执行文档正文。Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整模板和长度规则。
详细 = 边界清楚、完成条件清楚、文件路径清楚、禁止事项清楚。
```

## 二、四档路由架构

用户有最高覆盖权，未指定时由 Codex 自动路由；用户指定低档位时仍不能绕过安全门禁。

```text
具体任务
→ 最小必要只读调查
→ 修改前评分
→ 显式宣布当前流程、开始方式和选择原因
→ 按档位整理需求
→ 一个 Codex 单选框集中确认
→ 生成当前阶段的 /goal
→ 通过产物门禁后按 N/M 接力
→ 修改后评分
→ 必要时自动升级
→ 按验收责任收口
```

| 分数 | 流程 | 需求确认 | 执行单位 |
|---:|---|---|---|
| `0–35` | 轻量流程 | 一次简短整理、一次确认 | 一条轻量 `/goal` |
| `36–69` | 标准流程 | 一次模块级整理、一次确认 | 一条标准 `/goal` |
| `70–89` | 深度流程 | 必要多轮整理、一次详细集中确认 | 非 UI 2 次，UI 3 次 `/goal` |
| `90–100` | 完整流程候选 | 完整规划和总结确认 | 非 UI 3 次，UI 4 次 `/goal` |

简单多模块改造仍属于标准流程；只有复杂多模块、跨层、共享核心逻辑或高风险影响才进入深度流程。模块数量本身不能单独触发深度。90–100 只是完整流程候选，没有项目级条件时按深度流程执行；新项目或项目级改造可以在低于 90 分时进入完整流程。

五项评分各 `0–20` 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 项目现状 | 入口、测试、文档和状态清楚 | 部分信息缺失或有相关未提交修改 | 状态混乱、冲突或根因入口不清 |
| 修改规模 | 一个明确行为和所有权边界 | 同一模块多个文件、单页面或一条业务流程 | 跨模块、跨层、公共组件、全局配置或核心逻辑 |
| 依赖与修改后影响 | 私有实现或一个明确调用方 | 有限调用链且可以列完 | 多个消费者、共享状态、公共协议或影响未知 |
| 风险与回滚 | 易撤销，不涉及持久化、安全或生产 | 状态、兼容、缓存、异步、配置或第三方影响 | 数据迁移/删除、认证权限、密钥支付、生产或不可逆 |
| 验证复杂度 | 一个定向测试或局部操作 | 模块联调、正常/失败/回归或一个真实流程 | 跨模块、跨服务、真机、多端或完整业务链 |

每项取命中的最高分。已确认没有影响才可以打 `0`；尚未查清至少打 `1`；关键影响未知打 `2`。关键影响未知时不能只按低总分进入轻量流程；先显示暂未确定并继续调查，执行前仍无法查清时最低按深度流程处理。每项必须附代码、调用方、测试、文档或 Git 证据，不能先选档位再编理由。

未命中安全门禁时采用用户指定档位；安全门禁只规定最低档位。数据删除/迁移、认证权限密钥支付、生产操作、公共 API、共享数据结构、核心共享逻辑、跨多个独立模块、Stitch、高保真和新 UI 壳最低深度；新项目、同时新增三个或以上独立功能模块、整体架构重构、大规模数据或技术栈迁移、多个大型模块同时改造、项目事实严重混乱或用户明确要求完整流程时进入完整流程。

四档路由同时决定通用过程技能的使用深度。轻量和标准不机械执行完整 brainstorming、writing-plans、完整文档树和完整分支收尾；适用的系统化调试、测试和完成前验证仍然保留。

小任务档位上限：老项目单文件局部修改最高轻量；老项目单模块小功能最高标准；单模块完整改造默认标准、必要时深度；跨模块功能、新 UI 壳和高保真还原进入深度；只有新项目或项目级改造进入完整。安全门禁负责最低深度，不负责把局部高风险任务直接升级为完整。

### 确认与提示词交付合同

```text
需要集中确认
→ request_user_input 可用：实际调用 Codex 原生选择框，问题/选项/描述均为纯文本
→ 工具不可用：退回“选项一：……”纯文本普通段落
→ 用户点击或发送选项
→ 同一轮自动生成对应档位 /goal
→ 完整提示词只放一个 Markdown 代码块
```

用户选择已经是正式授权，不需要再补“请给我提示词”。流程状态继续在正文正常加粗显示；可复制提示词整体进入单一代码块，内部不嵌套三反引号。

目标矩阵是：轻量/标准均为 single 1/1；深度非 UI 为 documentation 1/2 → development-and-acceptance 2/2，UI 为 documentation 1/3 → ui 2/3 → development-and-acceptance 3/3；完整非 UI 为 documentation 1/3 → development 2/3 → acceptance 3/3，UI 为 documentation 1/4 → ui 2/4 → development 3/4 → acceptance 4/4。

UI 只能插入一次。外部 AI/Stitch 未回传时暂停同一 UI 目标，恢复时 N/M 不变。非 UI 部署、迁移和发布不自动新增目标；超出原确认范围的独立授权、风险或验收要求使当前目标受阻，回到 `$liran-plan` 确认后再作为新任务/新目标重新路由，不悄悄改当前 N/M。

4.5 在原有编码解锁状态机上新增基础目标数、当前第 N/M 次、目标阶段、UI 目标决策、UI 路线和外部等待状态。每条完整提示词都必须携带 `## 流程合同` 和 `## 档位执行门禁`；执行者必须检查文件存在、正文非占位和真实 diff。文档阶段未通过时禁止编辑实现源码；中间阶段禁止归档和整体完成话术。

### 4.4 任务文档与归档生命周期

### 4.5 普通目标回收与独立 archive

普通目标完成和项目归档是两套状态。最后 M/M 普通目标在真实验收、问题回写、复测和修改后评分完成后进入 goal_status=reclaim_pending，回收成功后进入 goal_status=reclaimed；项目状态进入待用户检查，资料归档状态保持待归档确认。用户回复“归档”后才创建独立 archive 目标，archive 不计入普通 N/M。归档失败保留 reclaimed 和活动资料，不能重新打开普通目标。

具体修改任务在需求整理首轮创建或复用 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`。用户确认整理完成后，再生成同任务的独立正式 PRD。纯解释、状态查询、只读审查、知识问答和用户明确禁止写文件时不创建。

任务文档保存稳定任务 ID、元数据、首次原话、项目事实、现状与期望、确认需求、影响与禁改范围、验收、待确认项、决策和下一步。同一 ID 贯穿任务拆分、微观任务、`04/08/09/10` 和归档；后续讨论默认只输出文件更新后的增量回执。

活动文档与历史职责分离：`04` 只留活动状态/顺序/阻塞，`08` 只留活动用例和精简稳定回归，`09` 只留待实测/失败/待复测，`03` 只留当前入口和归档索引，`10` 只留当前接线。长期项目与模块文档只维护当前事实；一次性功能树、模块/微观任务和 UI 过程归档。

归档严格先更新长期事实，再创建并验证归档、更新索引，最后按任务 ID 清理活动区并验证其他任务未受影响。最后普通目标完成后先进入 `待用户检查 → 待归档确认`，用户明确回复“归档”后才进入 `归档中 → 已归档 → 已完成`；归档失败保留原文并进入 `归档受阻`。普通目标与 archive 目标分离，archive 不计入普通目标数量。

## 四、入口路由与六类场景

用户只引用技能且没有具体任务时，先问六选一，不直接写代码、拆任务或开 `/goal`：

```text
1. 新项目
2. 老项目新增功能
3. 老项目续作
4. 老项目修复
5. 老项目删除
6. 其他
```

新项目默认完整流程；其他场景先调查评分。已有具体任务时跳过六选一，直接执行修改前评分并分档。

顶层规则不能绕过这里的分档：四档具体任务都先更新需求整理文档并回复增量回执；收到“需求整理好了”后重新归纳并输出正式 PRD，用户回复“PRD 没问题”后才进入集中选择。

完整流程多轮整理时的固定收尾：

```text
整理好了吗，还需要补充吗？
```

保留这句口令：`[$liran-plan](../SKILL.md) 整理好了或者需求整理好了或者总结好了`。用户说出这句或等价表达时，都视为进入总结确认阶段。

如果你回复“需求整理好了”或“总结好了”，我会先读取需求整理文档并重新归纳为正式 PRD，建立索引并输出给你确认；你回复“PRD 没问题”后，才在同一个确认问题的纯文本选择框里集中确认验收责任和页面检查。

选项一：$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

确认后同一轮立即交付 documentation 阶段目标，同时更新文档体系并拆完全部已确认需求的微观任务。

## 五、显式流程声明

修改前评分完成后，回复最前面必须直接使用正常 Markdown 加粗文本：

**当前流程：标准流程（40/100）**

**开始方式：按照标准流程，先整理当前模块和影响范围，确认后生成一条标准 /goal 提示词。**

**选择原因：修改集中在一个模块，但涉及多个关联文件；影响范围可以确认，不涉及公共协议和高风险数据。**

关键状态禁止放进代码块或复制框。用户指定流程时显示“用户指定”和 Codex 复核评分；信息不足时显示当前暂未确定并继续调查。

修改完成后重新评分。升级时正常显示：

**流程已升级：标准流程 → 深度流程（40/100 → 70/100）**

**升级原因：修改过程中发现该逻辑被多个模块共同调用，并且需要跨模块回归和真机测试。**

升级仍在确认范围内时直接继续，不要求用户复制第二条提示词。

轻量、标准升级到深度且仍在确认范围内时可以在原目标继续；升级到完整流程时必须先安全收口当前范围，再切回完整流程需求确认，不得在原目标里静默扩张。

## 八、四档闭环流程

```text
轻量：任务文档 → 调查 → 评分 → 简短整理 → 一次确认 → 一条短 /goal → 测试 → 验收 → 用户检查交接 → 用户确认后独立归档
标准：任务文档 → 模块调查 → 评分 → 模块级整理 → 一次确认 → 一条标准 /goal → 回归 → 验收 → 用户检查交接 → 用户确认后独立归档
深度非 UI：任务文档 → 调查/整理/集中确认 → documentation 1/2 → development-and-acceptance 2/2 → 用户检查交接 → 用户确认后独立归档
深度 UI：任务文档 → 调查/整理/集中确认 → documentation 1/3 → ui 2/3 → development-and-acceptance 3/3 → 用户检查交接 → 用户确认后独立归档
完整非 UI：任务文档 → 多轮整理 → documentation 1/3 → development 2/3 → acceptance 3/3 → 用户检查交接 → 用户确认后独立归档
完整 UI：任务文档 → 多轮整理 → documentation 1/4 → ui 2/4 → development 3/4 → acceptance 4/4 → 用户检查交接 → 用户确认后独立归档
```

页面任务按档位处理：轻量局部 UI patch 不建完整壳；标准整页或整组件调整不走完整五路线，状态验证必做，页面样式检查按用户选择执行；深度新页面、复杂状态、跨页面交互或 UI 与业务联动创建受影响 UI 壳清单，Design QA 按用户选择执行；完整流程走五路线。Stitch 不调用 Product Design Design QA，但必须经过初次接收检查和强制实例级细节复修；其他明确高保真 Product Design 路线仍按规则执行 Design QA。

深度页面确认框保留三个分支：Codex 真机并检查页面、Codex 真机但不检查页面、完成后我自己测试。重新判断流程使用自由输入。用户完成选择后已经授权对应验收方式，执行 `/goal` 时不再重复确认。

## 九、状态机

Codex 真机分支：

`待开发 → 进行中 → 内部测试通过 → 待实测 → 真机测试通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

用户自己测试分支：

`待开发 → 进行中 → 内部测试通过 → 待用户验收 → 用户验收通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

补充状态为 `受阻`。用户选择自己测试后不能直接标记完成。

如果当前判断不需要 UI，先明确原因，再跳过 UI 目标。有 UI 时，文本视觉方案、视觉图、真实前端 UI 壳、五条 UI 路线、Stitch 实例级保真、接收检查和适用的 Design QA 都在独立 UI 目标完成。造壳前必须由 Codex 生成 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md`，创建合法占位文件并明确白名单。Stitch 以下载 HTML 为第一事实来源，必须先做控件规格盘点、初次接收检查和强制复修。UI 目标不接真实 API、权限、状态和表单；这些全部留给后续开发目标。

Stitch 固定复修的“项目级微调”只能填充或替换项目事实、增加项目专属文件/限制/验证，以及将不存在的元素标记为 `不适用：当前 Stitch 原始产物中不存在该元素。`。任何微调都不得删除固定正文的词语、句子、列表项或章节；实例级复修提示词也必须保持 3000–10000 个字符，不走普通流程合同，并同等覆盖页面结构与布局、尺寸与间距、字体与文本排版、颜色和视觉样式、控件规格、图片和视觉资源、层级与组合关系、状态表现、响应式与不同视口。

第五路线补充：`@product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI` 由 Codex 通过 OpenCodex 本地路由在当前会话内选择实际可用模型生成真实前端 UI 壳；不要求外部复制提示词，不维护固定模型白名单，不新增强制模型选择框，仍执行 UI 壳接入清单、合法占位文件、文件白名单、样式隔离、UI 壳接收检查和非 Stitch Design QA。

## 十、`/goal` 合同

轻量和标准在 single 目标中完成各自所有阶段并进入用户检查交接。深度的 documentation 目标只做受影响文档、任务拆分、追踪和验收准备；development-and-acceptance 目标做开发、内测、已确认的真实验收、修复复测和用户检查交接。完整流程将 documentation、development 和 acceptance 分成三次，仅 acceptance 是最终普通目标；正式归档由用户确认后独立 archive 目标执行。

若有 UI，在 documentation 和开发之间插入一次 ui 目标。深度流程在用户明确不需要 UI 时跳过；完整流程默认保留，客观不涉及 UI 或用户明确跳过时取消。

每一目标都带基础目标数、N/M、stage、UI 决策、UI 路线、等待状态、进入证据、职责、禁止后续阶段和解锁条件。中间目标统一使用 `non-final`，最后普通目标使用 `handoff` 并按验收责任执行 Codex 真机或用户验收、回写和复测；用户明确回复“归档”后再启动独立 `archive`。

## 十一、事实证据与完成门禁

- 不得伪造读取过的文件、调用方、命令、测试结果、截图、真机操作、用户反馈和完成状态。
- 没有证据时标记 `未验证`、`待确认` 或 `受阻`。
- 结构校验通过不等于真实操作发生；用户未反馈通过不等于用户验收通过。
- 修改后评分必须依据真实 diff、重新搜索到的调用方、公共行为变化和实际测试输出。

## 十二、真机硬性阻塞

只有下面情况允许停下来找用户：

1. 缺少必须由用户提供的账号、权限、密钥、私有文件或外部系统访问权限。
2. 当前环境完全无法运行必要工具，且没有任何替代验证方式。
3. 任务涉及安全、法律、隐私或平台规则限制，导致无法继续。
4. 用户要求互相冲突，且无法通过合理默认策略自行选择。
