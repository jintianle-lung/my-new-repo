# 通用避坑

## 1. 3.1 起仓库根目录才是唯一技能主体

**现象**

如果仍把 `~/.codex/skills/liran-plan`、`~/.codex/skills/plan-docs` 或 `~/.codex/prompts/liran-plan.md` 指向旧子目录，或者文档里还残留旧目录路径，后续安装、校验、教程和发布口径会全部错位。

**根因**

3.1 这轮已经把仓库彻底收口为单一 Codex 版本。过去的旧环境兼容目录和旧主体子目录都已退出，根目录现在直接承载 `SKILL.md`、`references/`、`templates/`、`scripts/` 和发布说明。

**正确做法**

- 全局 skill 软链直接指向仓库根目录。
- slash prompt 也要同步到 3.1 口径。
- 以后新增或修改文档、教程、模板、校验脚本时，只允许引用根目录路径，不允许写回旧子目录。

**验证方式**

- `readlink ~/.codex/skills/liran-plan`
- `readlink ~/.codex/skills/plan-docs`
- `python3 scripts/check_codex_ui_flow_docs.py`

**禁止事项**

- 不要把仓库根目录再写成“索引页”。
- 不要恢复旧环境兼容说明。
- 不要把旧路径硬编码回教程、提示词或脚本。

**相关文件或命令**

- `README.md`
- `SKILL.md`
- `AGENTS.md`
- `~/.codex/prompts/liran-plan.md`
- `scripts/check_codex_ui_flow_docs.py`

**适用范围**

适用于安装、升级、发布、排障、教程维护和全局入口同步。

## 2. 真机清单结构校验脚本不能被当作真实验收

**现象**

`scripts/check_real_test_checklist.py` 跑过了，但功能其实没有在真实环境里操作验证，结果被误报为“已经真机通过”。

**根因**

这个脚本只检查 `09-真机实测.md` 的 Markdown 结构和门禁项，不会替用户完成真实点击、真实登录态、真实接口联调或真实设备操作。

**正确做法**

- 把它当成真机阶段的结构兜底。
- 真正的“通过”仍然必须来自真实环境操作、问题回写、修复和复测证据。

**验证方式**

- `python3 scripts/check_real_test_checklist.py <目标项目>/liran_docs/09-真机实测.md`
- 同时保留真实操作记录、回写记录和复测结果。

**禁止事项**

- 不要因为脚本返回 0 就声明真机通过。
- 不要用结构校验替代真实环境验证。

**相关文件或命令**

- `scripts/check_real_test_checklist.py`
- `references/功能6-真机实测与回写.md`

**适用范围**

适用于最后的 acceptance 或 development-and-acceptance `/goal`、真机验收、问题回写和发布前确认。

## 3. UI 流程不能退回旧原型 HTML / 旧 Gemini 分流

**现象**

**根因**

当前有效流程早已不是独立原型 HTML，也不是旧 Gemini 分流。现在统一是**真实前端 UI 壳五路线**，并且所有路线都先确认文本视觉方案，再决定是否需要视觉图 / 原型图。

**正确做法**

- 只保留当前五条路线：
  - `Codex 直接生成前端 UI 壳`
  - `@product-design`

- 先确认文本视觉方案，必要时再确认视觉图 / 原型图。
- 已有项目中途插入视觉确认时，按当前规则处理，不要机械退回旧流程。

## 4. 2.8 以后 UI 壳不能绕过接入清单、合法占位文件和文件白名单

**现象**

如果只告诉外部 AI “去做页面”，它会自己猜文件结构、自己加文件、自己加依赖、自己动全局样式，回到 Codex 时很难稳定接真实业务，也容易污染老页面。

**根因**

真实前端 UI 壳流程的关键，不是换个模型写前端，而是 Codex 先把施工条件布置好：接入清单、占位文件、入口、mock/type、局部样式和注释锚点都要先安排。

**正确做法**

- 造壳前先生成或更新 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md`
- 由 Codex 先创建合法占位文件
- 明确允许编辑文件清单和禁止编辑范围
- 准备 `TODO(ui-shell)`、`TODO(codex-connect)`、`TODO(codex-state)`、`TODO(codex-permission)`、`TODO(codex-validate)`、`TODO(codex-route)` 锚点

**验证方式**

- `python3 scripts/check_codex_ui_flow_docs.py`
- `rtk git diff --stat`
- `rtk rg -n "合法占位文件|允许编辑文件清单|TODO\\(ui-shell\\)|TODO\\(codex-connect\\)" SKILL.md references templates`

**禁止事项**

- 不要让外部 AI 自行新增、删除、移动、重命名文件
- 不要让外部 AI 新增依赖、重写全局样式、替换 UI 库、接真实接口或补业务逻辑
- 不要跳过 UI 壳接收检查直接进入后续开发目标

**相关文件或命令**

## 5. Stitch 路线不能退回模仿式重画

**现象**

执行者下载完 Stitch 原件后，表面上“差不多还原了”，实际上是凭感觉重写了一遍，只保留了大致风格，最终和 Stitch 原始 HTML、静态数据、屏幕映射都对不上。

**根因**

Stitch 路线不是“参考图路线”，而是“原始产物承接路线”。如果不把 HTML、代码 / 样式 / MD、截图的优先级写死，执行者就会把 Stitch 当灵感板。

**正确做法**

- HTML 是第一事实来源
- 代码 / 样式 / MD 规范是第二事实来源
- 截图只能作为第三层校对
- 必须先做 `控件规格盘点`
- 必须按实例级视觉规格保真去落真实前端
- Stitch HTML 里的静态数据，UI 壳阶段就直接沿用

**验证方式**

- `python3 scripts/check_codex_ui_flow_docs.py`
- `rtk rg -n "实例级尺寸保真规则|控件规格盘点|第一事实来源：Stitch 下载下来的 HTML|静态数据来源" SKILL.md references templates README.md`

**禁止事项**

- 不要自由发挥
- 不要只模仿大概风格
- 不要重新设计
- 不要要求 Stitch 预留接口
- 不要把 Stitch 静态数据随手改成另一套假数据

**相关文件或命令**

- `SKILL.md`
- `references/功能3-高保真原型.md`
- `templates/10-UI壳接入清单.md`
- `templates/UI壳单项接入清单.md`

**适用范围**

适用于 `@product-design + $Stitch / Stitch MCP` 路线、多屏映射、静态壳落地和 UI 壳接收检查。

## 6. Stitch 路线最容易丢的不是大布局，而是实例级控件规格

**现象**

大框架看起来对了，但图标、按钮、输入框、表格工具栏、表头、单元格 padding、操作列按钮、文字换行和控件占位关系一旦被统一成默认组件规格，整块排版流就会开始变形。

**根因**

常见问题不是“忘了抄布局”，而是承接时过早抽象、过早组件化、过早统一规格，或者被老项目默认 Button / Input / Icon / Table 组件和全局样式偷偷带偏。

**正确做法**

- 视觉未对齐前，禁止为了工程整洁去统一按钮、图标、输入框、表格规格
- 高风险控件优先使用局部作用域和实例级覆盖
- 如果沿用现有组件，必须验证最终视觉结果与 Stitch 一致
- 技术栈有差异时，只允许实现路径例外，不允许视觉结果例外

**验证方式**

- `python3 scripts/check_codex_ui_flow_docs.py`
- `rtk rg -n "Button / Input / Icon / Table|尺寸保真检查|实例级控件规格检查|表格 / 表头 / 单元格 / 筛选栏 / 操作列按钮" SKILL.md references templates README.md`

**禁止事项**

- 不要把不同按钮合成一套统一尺寸
- 不要把不同图标场景抹平成一个规格
- 不要把不同输入控件统一成一个高度
- 不要默认沿用老项目现成的 Button / Input / Icon / Table 规格

**相关文件或命令**

- `SKILL.md`
- `references/功能3-高保真原型.md`
- `references/提示词向导.md`
- `templates/UI壳单项接入清单.md`

**适用范围**

适用于 Stitch 承接、强制实例级细节复修、UI 壳接收检查和后续开发目标之前的静态壳验收。

## 7. Stitch 复修不能被缩成控件大小检查

**现象**

固定复修提示词虽然能抓住图标、按钮、输入框和表格的尺寸问题，执行者却可能因为这些例子太突出，忽略页面结构、布局、字体、颜色、资源、层级、状态和响应式。

**根因**

检查合同只强调了容易出错的控件规格，没有将完整视觉维度和固定正文不可删写成可校验的硬规则，也没有区分普通长提示词的长度门禁与实例级复修的3000–10000 个字符例外。

**正确做法**

- 固定复修同等覆盖结构布局、尺寸间距、字体排版、颜色样式、控件、资源、层级、状态和响应式。
- 保留旧固定正文的哈希证据，新规则只增量追加。
- 项目微调只允许补充或替换项目事实，不适用项仍保留规则并明确标记。
- 普通长提示词的长度范围为 3000–10000 个字符；Stitch 实例级复修提示词是固定模板直出例外，不走普通流程合同，也必须保持 3000–10000 个字符。

## 8. 需求整理完成不能直接生成提示词

**现象**

用户说“需求整理好了”后，助手跳过详细总结和集中确认，直接输出 `/goal`；或者把验收责任拆成第二个问题，导致用户没有在同一确认事件中授权验收方式。

## 8. Design QA 不能放水，也不能一轮只修一个点

**现象**

执行者可能把“90% 高还原”误解成可以放松 Product Design QA，也可能每轮只盯一个小问题，来回截图、来回返修，浪费很多轮。

**根因**

当前规则是双重门禁：90% 只是最低视觉相似度线；真正的 Product Design QA 仍要求没有 actionable P0/P1/P2 才能 passed。

**正确做法**

- 先做批量差异盘点，再批量修 P0 + P1，并尽量合并处理 P2
- 必须做同图对比、必要时局部放大对比、更新 `design-qa.md`
- 布局必须对齐，字体字号、间距和视觉细节最多只允许肉眼可接受的细微差距
- QA 范围要覆盖所有可见前端元素、状态变化、响应式断点和内容增减后的稳定性
- Chrome 扩展场景要先去 `chrome://extensions` 刷新扩展，再刷新目标页面

**验证方式**

- `python3 scripts/check_codex_ui_flow_docs.py`
- `rtk rg -n "90%|QA 不能挤牙膏|批量差异盘点|没有 actionable P0/P1/P2|chrome://extensions|刷新扩展" SKILL.md references README.md`

**禁止事项**

- 不要把 90% 当成放行理由
- 不要跳过 `design-qa.md`
- 不要每轮只修一个小 CSS 再重跑整轮 QA
- 不要在 Chrome 扩展没刷新扩展本体时截图验收

**相关文件或命令**

- `SKILL.md`
- `references/功能3-高保真原型.md`
- `references/提示词向导.md`

**适用范围**

适用于非 Stitch Product Design 路线、外部 AI 路线、Chrome 扩展 UI 和所有已触发 Product Design QA 的前端收口；Stitch 使用独立复修门禁。

## 9. 修改行数小不代表影响小

**现象**

执行者看到“只改一行”或“只是一个小逻辑”，就直接判定为轻量流程，遗漏多个调用方、共享状态或公共协议影响。

**根因**

修改规模和依赖影响是两个独立维度。代码改得少，不代表修改后的消费者少，也不代表回归范围小。

**正确做法**

- 修改前搜索定义、引用、调用方、事件订阅、配置读取和数据消费者。
- 修改后再次搜索调用方，并根据真实 diff 重新评分。
- 公共逻辑、多个消费者或影响未知时，依赖影响按最高命中值计分并触发必要升级。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 检查评分证据是否包含调用方和修改后影响，而不是只有文件数量。

**禁止事项**

- 不要用“只改一行”作为轻量流程的充分理由。
- 不要把修改规模分数代替依赖影响分数。

## 10. 未知不能打零分

**现象**

执行者没有查清入口、调用方或验证链路，却把对应评分项写成 `0`，制造虚假的低风险结论。

**根因**

`0` 表示已经有证据确认没有额外影响，不表示“暂时没看到”。

**正确做法**

- 尚未查清至少打 `1`。
- 关键影响无法确认时打 `2`。
- 信息不足时只补完成评分所需的最少调查或问题。

**验证方式**

- 检查每个评分项是否附代码、调用方、测试、文档或 Git 证据。
- 用压力场景 `S05-未知依赖不能打零分` 回归。

**禁止事项**

- 不要把缺少证据写成没有风险。
- 不要先选低档位再反推低分。

## 11. 手动验收不能标完成

**现象**

用户选择“我自己测试”后，Codex 完成内部测试就把任务标为 `已完成`，实际用户还没有验收。

**根因**

Codex 真机分支和用户验收分支混成了同一条状态链。

**正确做法**

- 用户自己测试时进入 `待用户验收`。
- 用户明确反馈通过后进入 `用户验收通过`。
- 完成必要问题回写、长期事实更新和单任务归档后，才能进入 `已归档 → 已完成`。

**验证方式**

- 检查 `04-开发追踪.md` 是否使用 `待用户验收 → 用户验收通过 → 归档中 → 已归档 → 已完成`。
- 用压力场景 `S08-用户自测进入待用户验收` 回归。

**禁止事项**

- 不要把内部测试通过当成用户验收通过。
- 不要代替用户编造手动测试结果。

## 12. 加粗状态不能放代码块

**现象**

执行者为了展示格式，把“当前流程”“开始方式”“选择原因”或升级信息放进三反引号代码块，用户看到的是 Markdown 源码或复制框，不是正常加粗结果。

**根因**

示例展示方式和真实用户输出要求没有分开。

**正确做法**

- 关键流程状态直接使用正常 Markdown 加粗文本。
- 当前流程、开始方式、选择原因、修改后评分、流程已升级和升级原因都在正文渲染。
- 校验脚本扫描 fenced block 内的关键状态标记。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 用压力场景 `S14-关键状态使用正常加粗文本` 回归。

**禁止事项**

- 不要把关键状态放进 `text`、`markdown` 或其它代码块。
- 不要显示供用户二次理解的 Markdown 源码。

## 13. 用户选择不能被后续无条件门禁覆盖

**现象**

用户在确认框中选择“不检查页面样式”，前面的分流规则允许跳过 Design QA，但 UI SOP 后半段又写成“所有 UI 壳必须 Design QA”，最终执行者仍会强制进入视觉对比。

**根因**

完整流程时期的强制 QA 口径被原样保留在四档共用 SOP 中，没有区分用户选择、完整流程、Stitch 和明确高保真分支。

**正确做法**

- 只有用户选择检查页面样式、完整流程或明确要求非 Stitch Product Design 高保真时执行 Design QA；Stitch 使用独立强制复修。
- 用户选择不检查页面样式时，仍验证功能、状态、错误和交互，但不做视觉方案对比，也不声明视觉还原通过。
- Stitch 不能用任何页面样式选项绕过初次接收检查和强制实例级细节复修；其他明确高保真 Product Design 和完整流程不能绕过已触发的 Design QA。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 检查 `references/功能3-高保真原型.md` 是否同时写清 QA 触发条件和跳过分支边界。

**禁止事项**

- 不要在共用 UI SOP 中使用没有分支限定的“所有 UI 都必须 QA”。
- 不要把“跳过视觉对比”误写成“跳过功能和状态验证”。

## 14. 共用模板不能残留完整流程阶段名

**现象**

深度流程复用 UI 壳接入模板时，模板里的锚点、临时入口和下一步仍写“第一次 `/goal`”，让执行者误以为还要切到完整流程的第二次交棒。

**根因**

模板从“只服务完整流程”升级为“四档共用”后，只修改了标题和总说明，没有逐项清理旧阶段名；Markdown 表格同步扩列时也容易漏掉分隔列。

**正确做法**

- 共用模板统一按职责写“后续 development 或 development-and-acceptance 目标”，不再使用“当前档位 `/goal`”这种模糊说法。
- 完整流程按 N/M 和阶段名称描述，不再使用“第一次 `/goal`”这种 UI/非 UI 不通用的旧阶段名。
- 修改 Markdown 表格列数后同步核对表头、分隔行和示例行。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 检查 `templates/10-UI壳接入清单.md` 和 `templates/UI壳单项接入清单.md` 中的阶段名与表格列数。

**禁止事项**

- 不要在四档共用模板里无条件写“第一次 `/goal`”或“第二次 `/goal`”。
- 不要只改表头而不改分隔行和示例行。

## 15. 只检查正向关键词会产生假绿

**现象**

文档里已经出现“四档流程”“按用户选择 QA”等正确关键词，校验脚本返回通过，但另一个执行入口仍保留错误选项、无条件 QA 或旧的两次 `/goal` 口径。

**根因**

校验只确认“正确句子至少出现一次”，没有验证所有执行入口、精确选项、边界分数和冲突旧句。

**正确做法**

- 同时做正向必需项和负向冲突模式检查。
- 对“一次确认”这类跨句合同检查上下文组合，不能只要求某个固定口号在文件任意位置出现；正常换行必须允许，把口号放在别处不能掩盖实际旧句。
- 精确验证四组 Codex 选项在主 SOP 和提示词向导中都存在。
- 覆盖当前 `0–100` 评分区间的每个档位边界（`0/19/20/44/45/69/70/100`），而不是只抽查几个代表值；历史记录中的 `0–10` 不能作为当前契约。
- 把 `.gitignore`、共用模板、HTML 教程和最终报告合同纳入职责范围。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 故意恢复一个旧句，确认校验会失败；修复后再确认通过。

**禁止事项**

- 不要把“某处出现过正确词”当成全仓口径一致。
- 不要让固定短语检查替代上下文语义组合检查。
- 不要只检查主 SOP，忽略提示词向导、模板和教程。

## 16. 完整流程纪律没有按档位限定

**现象**

主入口已经声明轻量不建完整文档、标准只定向更新、深度只更新受影响文档，但后半段仍无条件要求原话文档、独立成文、索引优先、完整 UI 壳清单和两次 `/goal`，导致小 Bug 最终仍走完整流程。

**根因**

新增四档路由时只增加了新规则，没有给旧完整流程纪律补作用域。正确规则和旧规则可以同时存在，执行者通常会选择更严格的旧规则。

**正确做法**

- 完整文档树、叶子独立成文、完整索引和全部微任务只作用于完整流程；完整非 UI 固定 3 次、UI 固定 4 次 `/goal`。
- 深度只更新受影响文档和任务；非 UI 固定 2 次、UI 固定 3 次 `/goal`，不再用一条长目标包住所有阶段。
- 标准只定向更新已有文档；轻量不为小改新建整套文档。
- 校验器同时检查必需新句和禁止旧的无条件句。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py`
- 检查 `SKILL.md`、功能 1–6、提示词向导和教程中的档位作用域。

**禁止事项**

- 不要只在四档总表里写“轻量”，却让后续无条件纪律覆盖。
- 不要用“更严格更安全”为理由把所有任务扩大成完整流程。

## 17. 真机清单有步骤不等于结构有效

**现象**

空文件、只有步骤标题、步骤没有表格、状态单元格包含否定句中的 `✅`、全部未勾选等清单仍可能返回成功。

**根因**

旧脚本只搜索 `✅` 子串和少量占位符，没有验证步骤连续、表头、必填列、严格状态、代码块伪表格和最终完成门禁。

**正确做法**

- 步骤必须从 1 连续编号，每步至少有一张合法表格和一行数据。
- 必填列必须存在，`跑通` 只有严格等于 `✅` 才算通过。
- 已勾行的所有必填证据列必须非空，也不能残留占位符、TODO、TBD 或其它待处理文字。
- 准备标记完成时使用 `--require-complete`，要求全部数据行严格通过。
- 忽略代码块中的伪标题和伪表格。

**验证方式**

- 运行 `python3 -m unittest discover -s tests -p 'test_*.py'`
- 运行 `python3 scripts/check_real_test_checklist.py <清单> --require-complete`

**禁止事项**

- 不要把“脚本返回 0”解释成真实操作已经发生。
- 不要允许证据列为空的行只靠 `✅` 通过完成门禁。
- 不要用状态单元格里出现过 `✅` 字符代替严格通过状态。

## 18. 一次确认不能在执行阶段被重复询问

**现象**

用户已经在 Codex 单选框选择真机和页面检查方式，进入 `/goal` 后又被要求确认是否开始、是否继续、使用哪个工具。

**根因**

四档确认规则和通用浏览器/真机流程没有明确授权关系，执行者把同一决定当成两个阶段的确认。

**正确做法**

- 单选框选择同时确认需求、验收责任和页面样式检查方式。
- 把选择结果写入生成的 `/goal`，后续直接执行。
- 完整流程的详细总结、模式文档、教程和可复制提示词必须在同一个确认问题里同时确认验收责任，不能只改主技能正文。
- 只有新增高风险动作、超出范围、缺少账号权限或外部输入时重新确认。

**验证方式**

- 检查 `AGENTS.md`、`SKILL.md`、四档 SOP、提示词向导和功能六。
- 检查模式文档、Markdown 提示词清单和两份 HTML 教程是否仍有“只确认总结、稍后再问验收责任”的旧句。
- 压力场景验证执行者不会在真机阶段重复提问。

**禁止事项**

- 不要把工具选择当成第二个用户问题。
- 不要让可复制提示词省略验收责任，否则用户复制后仍会生成第二个确认问题。
- 不要把等待外部 Stitch 产物误写成第二次需求确认。

## 19. 模式文档不能绕过统一验收状态机

**现象**

主状态机已经支持 Codex 真机测试和用户自己测试两条分支，但新项目、老项目或其它模式文档仍可能残留“没有真机通过就不能完成”的单分支旧句，导致用户自测永远无法正常收口。

**根因**

验收状态机更新时只改了主入口、功能四和功能六，没有把所有模式文档纳入负向冲突校验。

**正确做法**

- 所有模式文档都按已确认的验收责任收口。
- Codex 真机分支必须达到 `真机测试通过`。
- 用户自己测试分支必须收到用户明确反馈并达到 `用户验收通过`。
- 完整流程只在最后的 acceptance `/goal` 按验收责任分支，不能把 Codex 真机写成唯一路径。
- 校验器禁止模式文档重新出现把真机测试写成唯一完成路径的旧句。

**验证方式**

- `python3 -m unittest tests.test_check_adaptive_flow_docs.AdaptiveFlowValidatorTests.test_new_project_mode_rejects_codex_only_completion_gate -v`
- `python3 scripts/check_adaptive_flow_docs.py`

**禁止事项**

- 不要在新项目或其它完整流程模式里把 Codex 真机测试写成唯一验收分支。
- 不要因为完整流程更严格就取消用户已经选择的自测责任。

## 20. 顶层原则和兜底入口也必须标明档位作用域

**现象**

四档总入口和详细 SOP 已经写清轻量、标准、深度、完整的整理深度，但 `SKILL.md` 顶层核心原则仍写“每轮都先输出当前完整整理后的需求”，或“其他”入口仍写“继续多轮需求整理”，导致低档位被更靠前或更直接的旧句重新拉回完整流程。

**根因**

作用域审计只检查了功能 SOP、模板和两次 `/goal`，没有覆盖顶层原则与六类入口中的兜底场景。正确分档规则存在，不代表无作用域旧句不会覆盖它。

**正确做法**

- 顶层“每轮完整整理”必须明确限定为完整流程的需求整理阶段。
- “其他”入口先判断任务类型和项目实际影响，再按四档评分结果选择整理深度。
- 轻量一次简短整理、标准一次模块级整理、深度必要多轮、完整默认多轮，不得由入口类型直接改写。
- 校验器使用 S27、S28 负向压力场景拦截这两类回退。

**验证方式**

- `python3 -m unittest tests.test_check_adaptive_flow_docs.AdaptiveFlowValidatorTests.test_unscoped_core_principle_cannot_force_full_requirement_summary -v`
- `python3 -m unittest tests.test_check_adaptive_flow_docs.AdaptiveFlowValidatorTests.test_other_entry_cannot_force_multiround_requirement_clarification -v`
- `python3 scripts/check_adaptive_flow_docs.py`

**禁止事项**

- 不要在顶层原则里写没有“完整流程”限定的“每轮完整整理”。
- 不要因为任务属于“其他”就跳过评分并直接进入多轮整理。

## 21. 确认框、自动交付和代码块必须是可执行合同

**现象**

文档写了“使用 Codex 单选框”，执行者却只输出普通编号；用户选择后还要再说“请给我提示词”；最终提示词散落在正文或多个代码块中。深度提示词也可能直接跳到实现，只在最后笼统写“更新文档”。

**根因**

旧规则只描述期望结果，没有规定必须调用哪个工具、选择后的触发时点、代码块边界和深度目标的阶段顺序。

**正确做法**

- `request_user_input` 可用时实际调用，工具不可用时才用文字编号。
- 用户点击或发送选项后，同一轮自动生成对应 `/goal`。
- 可复制提示词整体只放一个 Markdown 代码块，内部不嵌套三反引号。
- 深度目标先准备文档、任务、UI 判断和验收清单，再实现；内部验证和真实验收后分别回写。
- 使用 S29–S32 做负向回归。

**验证方式**

- `python3 -m unittest tests.test_check_adaptive_flow_docs -v`
- `python3 scripts/check_adaptive_flow_docs.py --check-global`

**禁止事项**

- 不要把普通编号冒充 Codex 原生选择框。
- 不要要求用户重复催促生成提示词。
- 不要把一条提示词拆成多个复制块。
- 不要让深度目标只在最后笼统回写文档。

## 22. 工具清单不等于自动降级合同

**现象**

规则同时列出 `@Chrome` 和 `@电脑`，但 `@Chrome` 无法完成某个操作时，执行者仍然停下来让用户手动操作。

**根因**

只说明了每个工具适合什么，没有规定失败后的自动切换顺序，也没有禁止把可执行步骤转交用户。

**正确做法**

- 真实 Chrome 状态先用 `@Chrome`。
- `@Chrome` 无法完成时自动切换 `@电脑`，从原步骤继续。
- 除真实安全或外部阻塞外，不得要求用户代为操作。
- 使用 `S33` 同时检查技能入口、`/goal` 规范和真机 SOP。

## 23. 无人值守不等于全权托管

**现象**

规则虽然说执行阶段无人值守，但用户已明确全权授权后，入口仍弹出“Codex 测试 / 我自己测试”选择，或遇到阻塞后让用户代操作。

**正确做法**

- 识别明确的全权授权语义，直接预选 Codex 验收和适用的页面检查。
- 跳过验收选择框和用户自测分支。
- 客观阻塞只记录为 `受阻`，不转交操作。
- 使用 `S34` 检查全权托管合同。

## 24. Stitch 初次承接通过不等于视觉基线合格

**现象**

Stitch HTML 已经落到真实前端、入口也能打开，执行者就直接生成第一次 `/goal`。后续才发现图标、按钮、输入框、表格和文本的实例级规格被通用组件或全局样式带偏。

**根因**

把“文件已落地”和“视觉已完整对齐”合并成了一个检查。Product Design Design QA 也不是这条路线的正确替代，因为 Stitch 已有 HTML 级硬依据，需要的是实例级规格复修，不是另一套 90% 和 P0/P1/P2/P3 分级。

**正确做法**

- Stitch 初次接收结果只能是 `可以进入实例级细节复修` 或 `初次承接受阻`。
- 得出前者后自动交付 `templates/Stitch-实例级细节复修提示词.md`，不等用户再催。
- 只允许项目名、路径、技术栈、入口、验证命令、白名单和“不适用”项微调，不得缩短固定正文。
- 复修通过后才解锁后续 development 或 development-and-acceptance 目标。
- 其他 Product Design 路线仍保留 Design QA，不得因 Stitch 解耦而误删。

**验证方式**

- `python3 scripts/check_codex_ui_flow_docs.py`
- `python3 scripts/check_adaptive_flow_docs.py`
- `rtk rg -n "可以进入实例级细节复修|初次承接受阻|复修通过后|Stitch-\u5b9e例级细节复修提示词" SKILL.md references templates scripts`

**禁止事项**

- 不要在 Stitch 初次接收后跳过强制复修、直接解锁后续开发目标。
- 不要用 Product Design Design QA 代替固定实例级细节复修。
- 不要把固定提示词缩成一句“按 Stitch 一比一还原”。

**相关文件或命令**

- `SKILL.md`
- `references/功能3-高保真原型.md`
- `references/提示词向导.md`
- `templates/Stitch-实例级细节复修提示词.md`

**适用范围**

适用于 `@product-design + $Stitch / Stitch MCP` 的初次承接、复修、业务接线和回退重做。

## 25. 短口令不等于完整执行提示词

**现象**

文档里已有一句“请直接开始执行”或一个字段骨架，执行者就把它原样交给用户。提示词缺少当前项目事实、文件范围、安全边界、UI 约束、验证证据和收口条件，导致 Codex 需要猜测或中途重新追问。

**根因**

没有区分“流程触发口令”与“具备独立执行意义的完整提示词”，或为了简短而用“详见文档”“其他要求不变”代替关键内容。反过来，也可能为了长度而重复句子、空话或大量“不适用”，表面很长但仍然不可执行。

**正确做法**

- 完整执行提示词统一保持 `3000–10000` 字符。
- 必须覆盖任务性质、当前场景、目标和完成结果、读取要求、修改范围、执行步骤、业务与安全边界、UI 专项要求、验证要求、完成后输出和收口条件。
- 只用一个 Markdown 代码块交付，代码块后不再补执行要求。
- 普通澄清、选择框、进度、状态、阻塞、单句启动语和单条命令保持简短，不机械扩写。
- Stitch 实例级复修继续使用原固定正文不可删门禁，不走普通流程合同，但提示词必须保持 3000–10000 个字符；普通长提示词同样统一为 3000–10000。

**验证方式**

- `python3 -m unittest tests.test_check_adaptive_flow_docs -v`
- `python3 scripts/check_adaptive_flow_docs.py --check-global`

**禁止事项**

- 不要把启动句或模板骨架当成最终成品。
- 不要为了达到字数重复句子或填充空话。
- 不要把 Stitch 实例级复修的 3000 字符下限降级为更短的通用下限。

## 26. 五个子代理是并发上限，不是累计上限

**现象**

把“最多五个子代理”写成整个任务只能总共开四个，导致前一批子代理已经完成后，后续阶段仍不能按需开启新子代理。

**根因**

只定义了数量上限，没有明确这是“任一时刻的同时运行上限”，也没有规定子代理完成后的回收和名额复用。

**正确做法**

- 只允许一个主智能体负责统筹、分工、整合和回收。
- 任一时刻最多同时运行五个子代理。

## 35. PRD 不能被过程资料污染（历史条目，4.9 已修正首轮文件口径）

**现象**

**根因**

- 【当前 4.9 规则】需求讨论每轮先更新需求整理文档；正式 PRD 只保存确认后的需求事实和关联文档索引。

## 36. 简单多模块改造不能仅因模块数量升级流程

**现象**

旧评分把多个模块、较多测试或多个关联文件直接解释为深度流程，导致普通联动优化和局部修复频繁进入深度或完整流程。

**根因**

评分区间过窄，且没有区分简单多模块协同与复杂跨层改造；完整候选阈值也过低，安全门禁和项目级完整条件混在一起。

**正确做法**

- 使用 `0–35` 轻量、`36–69` 标准、`70–89` 深度、`90–100` 完整流程候选。
- 2–3 个相关模块、接口基本不变、无公共数据结构变化且验证有限时，按简单多模块改造处理，默认标准流程。
- 复杂多模块、跨层、公共协议、共享核心逻辑或高风险影响才进入深度流程。
- 90 分以上没有项目级条件时仍按深度流程执行；新项目或项目级改造可以在低于 90 分时进入完整流程。

**验证方式**

- `python3 -m unittest discover -s tests -p 'test_*.py'`
- `python3 scripts/check_adaptive_flow_docs.py --check-global`
- 检查简单多模块、复杂多模块、模块数量不能单独触发深度和 90 分候选回落场景。

**禁止事项**

- 不要把“涉及多个模块”直接写成深度流程。
- 不要把文件数量、测试数量或普通文档更新直接当作升级证据。
- 不要把高风险局部任务自动扩大成完整项目流程。

**相关文件或命令**

- `scripts/check_adaptive_flow_docs.py`
- `tests/test_check_adaptive_flow_docs.py`
- `references/四档自适应流程.md`
- `SKILL.md`

**适用范围**

适用于老项目优化、修复、单模块改造、简单多模块联动、复杂多模块改造和四档流程重新评分。

## 37. 技能主体 frontmatter 不能混入无键名说明文字

**现象**

slash prompt 能以 `prompts:<name>` 出现，但技能选择列表不显示同名技能；`skills/list` 返回该 `SKILL.md` 的 YAML 解析错误。

**根因**

Codex 只把 `SKILL.md` 开头 `---` 到结束 `---` 之间当作 YAML frontmatter。普通说明文字如果没有键名就放在这段区域内，会让整个技能加载失败；单独的 `~/.codex/prompts/<name>.md` 仍可能正常显示，因此容易误判为安装路径问题。

**正确做法**

- frontmatter 只保留合法 YAML 字段（至少 `name` 和 `description`）；规则说明放在结束标记之后。
- 修复后用 app-server 的 `skills/list` 强制重扫，确认 `errors` 为空且目标技能名存在。
- slash prompt 与 `SKILL.md` 是两条独立入口，不能用 prompt 出现来证明技能加载成功。

**验证方式**

- `python3 scripts/check_adaptive_flow_docs.py --check-global`
- 通过 `codex app-server --stdio` 调用 `skills/list`，传入 `forceReload: true`，检查 `liran-plan` 出现在 `skills` 且 `errors` 为空。

**禁止事项**

- 不要把版本说明、中文摘要或 Markdown 段落插入 frontmatter 而不加 YAML 键名。
- 不要只检查 `~/.codex/prompts/` 或 slash 搜索结果就宣称技能已部署。

**相关文件或命令**

- `SKILL.md`
- `~/.codex/prompts/liran-plan.md`
- `scripts/check_adaptive_flow_docs.py --check-global`
- app-server 方法 `skills/list`

**适用范围**

适用于新增、升级、部署和排查所有 Codex `SKILL.md` 技能入口。
## 最后普通目标与正式归档不能耦合

- **现象**：M/M 普通目标一完成验收就自动创建归档、清理活动区并标记已完成，用户还没有机会检查软件或补充需求。
