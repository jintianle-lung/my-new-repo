# liran-plan：项目规划与文档化技能

## 这个技能是做什么的

`liran-plan` 是 `liran` 的个人项目规划与文档化技能。4.52 把 Stitch 页面生成提示词接到分端清单和 MCP 回传口径上，并继续要求最后目标交接、用户确认后独立归档和正式 PRD 完整转换审计。

核心原则：

```text
需求没整理清楚前，不开干。
具体任务首轮创建 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`；需求讨论每轮更新需求整理文档；用户确认“需求整理好了”后，才重新生成独立正式 PRD。
目标模式没收口前，不吐下一条命令。
已确认的 Codex 真机测试或用户验收没通过前，不标完成。
最后一次普通目标完成后先等待用户检查；没有用户明确回复“归档”，不创建归档、不更新归档索引、不清理活动区，也不标记已归档或已完成。
提示词要信息完整但不重复，开头要有明确执行语句，不能因为追求简短导致 Codex 跑偏。
```

底层原则：人和 AI 有“代沟”。本技能的工作是把口语化想法逐步收敛成 AI 能精确执行、可自检、可接力的结构化文档与详细提示词。

### 唯一闭环顺序

需求整理文档 → 正常聊天整理 → 用户确认整理完成 → 正式 PRD → PRD 确认 → 可选 UI 壳 → 内部开发 → 真机实测 → 问题回写 → 修复复测 → 安全归档。

这是所有具体项目修改任务的先后顺序。每一步必须以前一步的真实产物和确认结果为进入证据；不得跳过需求整理文档、正式 PRD 确认、UI/开发/测试门禁或归档门禁，也不得把多个阶段合并成无法审计的一条“全部完成”动作。

这是一套通用骨架，不是某个固定项目的专用模板。所有提示词都要根据当前项目、当前模块、当前状态和真实文档路径微调，不能写死某个项目名、环境名或专有链路。

普通目标提示词遵守 [templates/通用完整执行提示词规范.md](templates/通用完整执行提示词规范.md)：只保留任务 ID、流程档位、目标 N/M、阶段、读取文件、执行边界、验证、状态回写、完成条件和下一阶段解锁条件，不重复 PRD 或执行文档正文，也不设 3000 字最低门槛。Stitch、外部 AI、Product Design、生图等专项提示词不适用本短格式，继续使用各自完整结构、长度和校验规则。

每条适用的完整目标提示词第一行必须原样写入：`你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。`这是并发上限，不是整个任务的子代理累计数上限。是否启用由主智能体自行判断，不为了形式强制开启；子代理完成、失败或不再需要时必须及时回收，释放名额后可再启用新的子代理。

4.3 运行时合同补充：评分继续使用 `0–100`；`0–35` 为轻量流程，`36–69` 为标准流程，`70–89` 为深度流程，`90–100` 只是完整流程候选。小功能和简单多模块改造默认优先轻量或标准流程；只有项目级条件成立时才可进入完整流程。所有会在选择后立即生成提示词的选项必须从 canonical builder 生成，统一使用 `$liran-plan <原选择项文字>（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`。原生选择框的问题、选项标签和描述必须是正常纯文本，不得使用 Markdown 标题、加粗、反引号、代码块、链接或列表符号包裹。工具不可用时的文字回退也只能用“选项一：……”这类普通段落，不得用 Markdown 列表或代码格式伪装选择框。重路由、重新判断、需求修正、自由输入、澄清问题和状态消息不追加包装；包装也不得进入正式提示词正文。

### 4.3 运行时硬门禁与可恢复流程合同

普通目标提示词使用文件指针型短合同，必须固定任务 ID、流程档位、目标 N/M、当前阶段、读取文件、执行边界、验证、状态回写、完成条件和下一阶段解锁条件。只有仍采用运行时完整流程合同的兼容性目标才携带 `## 流程合同` 和 `## 档位执行门禁`；Stitch 实例级复修提示词是固定模板直出例外，不携带这些字段，改由专用完整性校验负责。兼容性完整合同仍需固定流程档位、评分、目标数量、UI 决策、等待外部输入、验收责任、当前状态、进入证据、阶段门禁、允许动作、禁止动作和上下文恢复证据。

编码解锁门禁是实际阶段门禁，不是说明性口号。提示词出现“已更新”不等于产物存在：执行者必须检查文件存在、正文非占位、产生真实 diff，并记录可核对命令和结果。任一前置条件不成立，禁止编辑 `src`、`frontend`、`backend`、`electron` 或其他实现源码。

- 轻量流程：1 次，单目标完成实现、内部验证、已确认的验收、问题回写和复测，然后交接等待用户检查。
- 标准流程：1 次，单目标完成模块任务、TDD、内部验证、已确认的验收、问题回写和复测，然后交接等待用户检查。
- 深度非 UI：固定 2 次，文档/任务/微观任务/追踪/验收准备 → 开发/内测/真实验收/修复复测 → 交接等待用户检查。
- 深度 UI：固定 3 次，在上述两次之间插入 1 次 UI 目标。用户明确说不需要 UI 时跳过。
- 完整非 UI：固定 3 次，完整文档与全部微观任务 → 开发与内测 → 真实验收、回写、修复复测 → 交接等待用户检查。
- 完整 UI：固定 4 次，在文档目标后插入 1 次 UI 目标，再进入开发和验收。完整流程默认保留 UI 目标；只有客观不涉及 UI 或用户明确跳过时取消。

UI 目标只做文本视觉方案、可选视觉图、UI 壳或外部 AI/Stitch、接收检查、Stitch 强制复修和适用的 Design QA。真实 API、数据流、状态管理、权限、表单提交和业务接线必须留到开发目标。外部 AI/Stitch 等待用户回传时，只将同一 UI 目标标记为等待；收到输入后继续原目标，不新建 `/goal`、不改 N/M。非 UI 的部署、迁移、发布等不自动加目标；只有真正需要独立授权、风险或验收的新范围才能重新路由。

仓库校验器 `scripts/check_adaptive_flow_docs.py` 的 `workflow_prompt_failures()` 和 CLI `--prompt-file <文件> --prompt-tier light|standard|deep|full-docs` 是普通目标提示词交付前的必经检查；普通 Goal 与 `--prompt-kind long` 使用文件指针型短格式，必须包含流程档位、修改前总分、五维评分和评分证据，不设 3000 字最低门槛。Stitch 实例级复修使用 `--prompt-kind stitch-instance-repair`，继续执行专项长度和固定正文完整性检查；Stitch 生成、外部 AI UI、Product Design、生图和其他专项提示词分别使用 `--prompt-kind stitch-generation|external-ai-ui|product-design|image-generation|special-prompt`，不套用普通 Goal 合同。正式 PRD 转换审计使用 `--prd-file <文件> --prd-status formal --prd-source-file <需求整理文档> --score-file <评分记录>`，必须同时验证来源细节和转换后的五维评分。确认载荷用 `--confirmation-file`，阶段文件用 `--artifact-file` 与 `--changed-file` 审计，单次状态转换用 `--state-transition-file`，目标交棒用 `--goal-transition-file`，上下文恢复用 `--contract-file` 校验合同不可变字段。校验失败不得交付普通提示词、跳阶段或解锁编码。

这就是本版本的真实提示词校验合同：每次生成的正文都必须实际调用校验器，不得只依赖静态文档关键词。原生选择框和文字回退统一使用 canonical builder，不能临时另造会生成提示词的选项。可序列化的 `FlowContract` 保存恢复所需字段和升级证据；没有修改后评分和新证据时不得改变档位、目标次数或验收责任。

### 4.4 PRD 生命周期与单任务归档合同

凡是用户提出具体项目修改任务，包括修 Bug、新增/优化/删除功能、重构、续作、需求整理、UI、API、数据、权限、配置、迁移、部署和发布，进入需求整理第一轮就必须创建或复用唯一需求整理文档：`liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`。正式 PRD 使用同任务 ID 的独立 `*-PRD.md`。纯解释、状态查询、只读审查、知识问答，以及用户明确要求不写文件或不记录时不创建。

首轮创建需求整理文档，使用聊天式结构，状态为“需求整理中”；完整用户原话写入 `liran_docs/用户原话.md`，项目事实回写项目、架构或模块文档。首轮不创建正式 PRD、Goal、不拆开发任务、不修改业务源码。后续每轮先读取并更新需求整理文档，再回复本轮新增、变更、确认、待确认项和真实路径。

PRD 只记录产品/功能需求事实、REQ/AC、版本与变更、页面需求、边界和其他执行文档索引；Goal 流程合同、微观任务正文、开发流水、测试执行记录、真机流水、UI 接收过程、命令输出、审计日志和归档操作日志必须放在各自文件，PRD 不得复制。用户说“需求整理好了/需求没问题了/可以按这个做/没有其他补充/进入下一步”后，执行完整性检查，将状态转为“文档状态：正式 PRD、需求状态：已确认、PRD 版本：1.0”，建立关联文档索引。正式 PRD 转换完成后必须评分并确定流程等级，记录五维分数、总分、评分证据、范围上限、安全门禁和最终档位；评分和文档体系检查通过后，才能拆分任务、微观任务或生成目标提示词，检查失败就留在当前阶段。

需求变更必须回到同一 PRD。想法未获确认时记为“候选想法：待评估”；用户明确加入后创建 CHG 编号，记录原话、原因、受影响 REQ/AC/页面/模块/数据/测试/真机/UI/Goal、等级、状态、是否重新确认和是否需要新任务。文字澄清为 0 级；当前范围小增补为 1 级；跨模块或 UI 变化为 2 级，暂停当前阶段并同步全部受影响文档和目标；架构、公共 API、数据库、权限、认证、支付、迁移或独立产品目标为 3 级，暂停、重新分档，必要时创建新任务和新 PRD，旧 PRD 只建立关联。旧 REQ 编号不得重排，修改时保留编号并递增版本。

同一任务的任务 ID 必须贯穿 PRD、模块/功能树、微观任务、Goal、`04-开发追踪.md`、`08-测试用例.md`、`09-真机实测.md`、`10-UI壳接入清单.md`、`ui-shells/` 和归档包。

### 4.5 PRD 转换确认与选项门禁

正式 PRD 必须完整承接需求整理文档中的已确认需求。

需求整理期间每轮结束时必须用正常文本询问：“需求整理好了吗？整理好了的话，请回复‘需求整理好了’。”在收到口令前，只更新需求整理文档，不能生成正式 PRD、Goal、开发任务或源码修改。收到口令后读取需求整理文档和真实事实，重新归纳生成独立正式 PRD，清理不属于 PRD 的过程内容，输出正式 PRD 供用户确认。

正式 PRD 输出后必须再次等待用户确认，固定询问：“正式 PRD 没问题吗？没问题的话，请回复‘PRD 没问题’；需要修改请说明修改点。”用户未明确回复“PRD 没问题”时，继续更新同一 PRD 版本并停留在 PRD 确认阶段，不能生成任何 Goal 或进入后续流程。只有确认通过后，才显示当前档位后续阶段和可复制提示词。

运行时状态用“正式 PRD 待确认”表示这段停留，不得用“提示词已解锁”或“需求已完成”替代；只有收到“PRD 没问题”事件并保留 PRD 转换、索引和输出证据后，才能进入提示词生成和选项确认。

每个需要用户选择的节点都必须提供可操作选项，且只能使用正常纯文本：需求/验收责任与页面样式选择、UI 路线选择、外部 AI/Stitch 是否等待、Codex 真机测试或用户自测、PRD 是否确认。原生 `request_user_input` 可用时必须实际调用；不可用时使用“选项一：……”普通段落回退。选项缺失、格式错误、与当前阶段不匹配或无法序列化时停留当前阶段并标记待处理，不得默认替用户选择。用户完成选择后，同一轮交付当前阶段唯一完整提示词；不要求用户再次输入“继续”或复制第二条提示词。

PRD 确认节点的纯文本选项固定为：选项一：正式 PRD 没问题，继续流程；选项二：正式 PRD 需要修改。需求/验收责任节点、UI 路线节点和 Codex/用户验收节点必须分别使用对应的 canonical 选项集合，不能用一个“默认继续”代替，也不能把流程专用 `$liran-plan` 包装混入 PRD 确认选项。

活动文档只保存当前事实：

- `03-索引.md` 只列活动任务入口和一个归档索引入口。
- `04-开发追踪.md` 只列活动任务状态、依赖顺序与阻塞；无活动任务时显示明确空状态。
- `08-测试用例.md` 只列活动任务用例与精简稳定回归基线；详细执行轮次归档。
- `09-真机实测.md` 只列当前待实测、失败和待复测；已通过轮次归档；无活动任务时显示明确空状态。
- `10-UI壳接入清单.md` 只保留当前有效接线；一次性外部 AI/Stitch 提示词、接收检查、实例级复修和 Design QA 过程归档。
- `00/01/02/05/06/07` 和模块文档只维护当前长期事实，不追加施工流水。模块职责、业务规则、接口和状态长期保留；一次性功能树、模块拆分和微观任务在完成后归档。若模块拆分已经成为当前架构，只压缩历史过程，保留当前结构。

用户明确回复“归档”后，使用 [templates/任务正式归档目标提示词.md](templates/任务正式归档目标提示词.md) 启动独立正式归档，再按 [templates/任务归档.md](templates/任务归档.md) 创建单任务归档包。归档包汇总最终 PRD 及其版本/变更、原话、需求索引、功能树、模块/微观任务、实施计划、目标说明、开发追踪、测试与执行结果、真机与问题回写、Bug 修复复测、临时 UI/外部 AI/Stitch/Design QA、版本和发布资料；截图与大日志只记录真实路径。历史归档默认不参与新任务扫描，只有回归、旧决策追溯、版本调查或用户明确要求时读取。

最后普通目标在真实验收、问题回写、修复复测和修改后评分完成后，必须按 goal_status=active → reclaim_pending → reclaimed 立即回收；同时把项目状态写为待用户检查，把资料归档状态保持为待归档确认。用户检查已经脱离普通目标生命周期，不能继续生成原目标命令。归档失败时原普通目标仍保持 reclaimed，不得重新打开；只有用户明确回复“归档”后才创建独立 archive 目标，archive 不计入普通 N/M。

归档顺序必须是：先更新长期事实 → 创建归档 → 校验归档内容和证据路径 → 更新归档索引 → 只按本任务 ID 移走活动段落或一次性过程文档 → 检查其他活动任务未受影响、当前索引有效、活动区无本任务已完成残留。任一步失败都保留原内容并标记 `归档受阻`，不得进入完成。

状态分支：最后普通目标完成后进入 `待用户检查 → 待归档确认`；用户发现问题回到问题回写、修复和复测，提出新增需求或优化回到需求整理/需求变更，只有用户回复“归档”后才进入 `归档中 → 已归档 → 已完成`。已取消、暂停关闭、被新任务替代分别保存为 `已取消`、`暂停归档`、`被新任务替代`，不得伪装成已完成。待确认、待实测、待用户验收、失败、受阻或未修复问题不得完成归档。

只有每个流程的最后一次 `/goal` 才能执行最终验收、问题回写、修复和复测；最后普通目标本身不执行正式归档。轻量、标准的单目标，深度的第 2 次或第 3 次，完整的第 3 次或第 4 次才是最终普通目标。文档、UI 和开发等中间目标禁止归档，也禁止输出“本次任务已完成并归档”等最终完成话术；最后普通目标使用 `handoff`，正式归档使用独立 `archive`。旧 `final` 按 `handoff` 兼容，`full-first` 按 `non-final` 兼容，不能靠漏传参数绕过用户确认。真实归档快照使用 `--archive-contract-file` 校验。

只有归档真实成功时才能使用固定话术“本次任务已完成并归档”，并同时列出需求、任务/微观任务、`04`、`08`、`09`、UI 过程资料状态，真实归档路径、活动区清理结果和长期事实更新结果。

## 四档自适应流程总入口

### 4.42 普通目标回收补充

最后普通目标回收合同可使用 scripts/check_adaptive_flow_docs.py --goal-reclaim-file <JSON> 校验；该合同只验证普通目标回收，不会创建资料归档。

只输入 `$liran-plan` 或 `/liran-plan` 且没有具体任务时，继续显示六类场景。用户已经给出具体 Bug、功能、删除、迁移、发布或文档任务时，不再先让用户六选一；Codex 先做最小必要的只读调查，再执行修改前评分并直接分档。详细规则以 [references/四档自适应流程.md](references/四档自适应流程.md) 为准。

| 分数 | 流程 | 默认确认与执行方式 |
|---:|---|---|
| `0–35` | 轻量流程 | 一次简短整理、一个 Codex 单选框、一条轻量 `/goal` |
| `36–69` | 标准流程 | 一次模块级整理、一个 Codex 单选框、一条标准 `/goal` |
| `70–89` | 深度流程 | 必要的多轮整理、一次详细集中确认、非 UI 两次或 UI 三次 `/goal` |
| `90–100` | 完整流程候选 | 还需满足项目级条件，再进入完整规划、完整文档和非 UI 三次或 UI 四次 `/goal` |

评分由五项组成，每项 `0–20` 分：项目现状、修改规模、依赖与修改后影响、风险与回滚、验证复杂度。总分为 `0–100`。尚未调查的维度必须标记为“待调查，不计入最终评分”；调查后仍无法确认关键影响时才采用保守高分并说明证据不足。每项必须附代码、调用方、测试、文档或 Git 证据。文件少、代码只改一行都不能代替依赖扫描。

未命中安全门禁时，采用用户指定档位；安全门禁只规定最低档位，不用评分强行覆盖用户指定。数据删除或迁移、认证权限密钥支付、生产操作、公共 API、共享数据结构、核心共享逻辑、复杂多模块跨层改造、Stitch、高保真还原和新 UI 壳最低进入深度流程。总分达到 `90` 只是完整流程候选；只有同时命中新项目、同时新增三个或以上独立功能模块、整体架构重构、大规模数据或技术栈迁移、多个大型模块同时改造、项目事实严重混乱或用户明确要求完整流程等项目级条件，才进入完整流程。简单多模块改造仍属于标准流程，模块数量不能单独触发深度。

小任务档位上限：老项目单文件局部修改最高轻量；老项目单模块小功能和简单多模块改造最高标准；单模块完整改造默认标准、影响扩大时深度；复杂多模块、跨层功能、新 UI 壳和高保真还原进入深度；新项目和项目级改造才进入完整。安全门禁可以把任务提升到深度，但不能仅凭高风险把范围明确的单项任务自动提升到完整。

四档路由决定过程框架的使用深度。Superpowers 等通用流程技能只能按当前档位和真实风险取用，不得把轻量或标准任务机械扩张成完整 brainstorming、完整 writing-plans、完整文档树和完整分支收尾链路；适用的系统化调试、测试和完成前验证仍然必须执行。

修改前评分完成后，回复最前面必须直接使用正常 Markdown 加粗文本，不能放进代码块、`text` 复制框或 Markdown 源码展示：

**当前流程：标准流程（40/100）**

**开始方式：按照标准流程，先整理当前模块和影响范围，确认后生成一条标准 /goal 提示词。**

**选择原因：修改集中在一个模块，但涉及多个关联文件；影响范围可以确认，不涉及公共协议和高风险数据。**

用户指定档位时要写明“用户指定”和 Codex 复核评分。信息不足时先显示 **当前流程：暂未确定，Codex 正在调查项目和修改影响**，只补评分必需的最少信息。

四档都使用一个 Codex 单选框集中确认“需求是否正确”和“改完后由谁测试、是否检查页面样式”，不能拆成两个问题。问题、选项标签和描述全部用正常文本，不得用 Markdown 格式；用户可见选项不得出现“推荐”。`Codex` 代表执行任务的 AI，`我` 代表用户。用户完成选择后已经授权对应真机和页面检查方式，每个阶段的 `/goal` 必须写入同一选择结果，执行时不得再问是否开始、是否继续或使用哪个工具。选择“我自己测试”后，最后目标只能先进入 `待用户验收`；收到用户明确通过结果后进入 `用户验收通过 → 待用户检查 → 待归档确认`，再等待用户回复“归档”。

Codex 原生选择框与自动交付是硬合同：当前环境中 `request_user_input` 可用时必须实际调用，只有工具不可用时才退回“选项一：……”形式的纯文本普通段落。不得使用 `-`、`*`、数字列表、加粗、标题、反引号、代码块或链接包装问题和选项。用户点击或发送某个选项就已经完成确认，Codex 必须在收到选择结果后的同一轮自动生成当前阶段的完整 `/goal` 提示词，不得等待用户再说“请给我提示词”“继续”或任何同义口令。

可复制 `/goal` 的全部内容必须放进一个独立的 Markdown 代码块。代码块外只允许一句简短引导；不能把提示词拆成多个代码块，代码块内部不得嵌套三反引号。当前流程、开始方式、选择原因和升级信息仍在正文中正常加粗显示，不得为了满足复制要求塞进提示词代码块。

所有档位的 `/goal` 都必须带入无人值守执行合同：需要真实 Chrome 会话、登录态、标签页或扩展环境时优先使用 `@Chrome`；`@Chrome` 无法完成时自动切换 `@电脑`，并从当前步骤继续。Codex 自行选择、组合、切换工具，不得要求用户代为操作，不得因为单一工具失败就转为“请用户手动完成”。只有必须由用户提供的登录凭据、验证码、账号权限、付款授权、不可逆操作确认或外部服务客观不可用等真实硬性阻塞，才允许请求用户介入。

用户明确表达“全程不需要我操作”、“全权交给 Codex”或同义授权，且本轮没有明确选择用户自测时，进入**全权托管模式**。该授权等同于预选“Codex 真机测试”和适用的页面样式检查，不再显示验收选择框，不再询问是否开始、是否继续、使用什么工具或由谁验收。用户明确选择“我自己测试”时，以用户自测为准，Codex 完成内部测试后停在 `待用户验收`，不擅自改为 Codex 真机验收。需求已明确时直接生成并执行对应 `/goal`；信息不完整时先自主调查，仍无法确定时采用最保守可回滚假设并在结果中说明。客观无法继续的情况只记录为 `受阻`，不得转交用户操作或变相要求用户确认。

修改完成后必须根据真实 diff、重新搜索到的调用方、公共行为变化和测试结果执行修改后评分。分数或硬门禁提高时自动升级，并用正常 Markdown 加粗文本显示 `流程已升级`、`升级原因` 和接下来的执行方式。流程升级后必须按新档位重建剩余阶段合同，不得把本应独立的文档、UI、开发或验收阶段塞回同一目标。升级到完整流程说明已经出现项目级范围，不能在原目标里静默扩张；必须先完成当前可安全收口部分，说明升级原因，并切回完整流程需求确认。删除数据、不可逆操作、账号权限或需求冲突等超出确认范围的情况同样必须停下确认。

任何档位都不得伪造已经读取的文件、搜索到的调用方、运行过的命令、测试通过结果、页面截图、真机操作、用户反馈或完成状态。没有证据时写“未验证”“待确认”或“受阻”，不能为了凑评分、补提示词或宣布完成而编造事实。

最终回复必须按详细 SOP 的最终报告合同输出：正常加粗显示 `最终流程`，并列出修改前评分、修改后评分、流程变化、升级原因、修改内容、内部测试、真机测试、页面样式检查、文档回写和最终状态。

## 入口与提示词向导

当用户只是引用 `$liran-plan`、`/liran-plan`，说“不知道下一步干嘛”“继续/接着做”，要“提示词/操作指南/下一步”，或没有给出具体任务时，先进入六类场景向导。用户已经给出具体任务时，直接执行上面的四档自适应流程，不机械先问六选一。

必须先读取并执行 [references/提示词向导.md](references/提示词向导.md)。

向导规则分五组：A 需求整理阶段锁定、B 文档与任务拆分收口、C 真实前端 UI 壳五路线分支、D 四档分阶段 `/goal` 节奏、E 提示词质量与阶段收口。

### A. 完整流程需求整理阶段锁定

A1. **无具体任务时先问六选一**：新项目 / 老项目新增功能 / 老项目续作 / 老项目修复 / 老项目删除 / 其他。已有具体任务时跳过本项，直接调查、评分和分档。
A2. 只有已判定进入完整流程时，才默认进入**多轮需求整理阶段**，并且保持在这个阶段，直到用户明确说出“需求整理好了”或“总结好了”。轻量流程只做一次简短整理，标准流程只做一次模块级整理，深度流程按必要程度多轮整理后做一次详细集中确认。
   - 每一轮先更新需求整理文档，再只回复本轮新增、变更、确认、待确认项和真实路径。
   - 不写代码。
   - 不拆任务。
   - 不开 `/goal`。
   - 不生成真机实测。
   - 不输出后续执行命令或下一阶段提示词。
A3. 需求整理阶段每轮回复必须以固定收尾提醒结束：

   ```text
   整理好了吗，还需要补充吗？
   ```

A4. 只有用户明确表达“需求整理好了”或“总结好了”时，才结束需求整理阶段。**如果没有这些收口词，就继续保持整理状态。**
   - 保留这句口令：`[$liran-plan](SKILL.md) 整理好了或者需求整理好了或者总结好了`。用户说出这句或等价表达时，都视为进入总结确认阶段。

### B. 完整流程文档与任务拆分收口

B1. 收到“需求整理好了”后，读取需求整理文档并重新归纳生成独立正式 PRD，建立 PRD 索引并输出供用户确认。正式 PRD 转换完成后必须评分并确定流程等级，记录五维分数、总分、评分证据、范围上限、安全门禁和最终档位；在正式 PRD、评分和文档体系确认前，不生成完整文档树、拆任务或任何 Goal。用户回复“PRD 没问题”且评分与文档检查通过后，才进入集中选择；完整流程的验收责任和页面样式必须在同一个选择问题中确认，不得拖到最后目标前再问。选择框的问题、选项和描述都用纯文本；其中两个核心选项是：

选项一：$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

用户确认后立即生成文档阶段的第一次 `/goal`：深度流程只更新受影响文档、拆分全部任务和微观任务、更新开发追踪与验收准备；完整流程则一次性生成或更新完整 `liran_docs/` 体系并拆完全部已确认需求、任务模块和微观任务。该目标不得修改实现源码、做 UI 施工、做真机验收或归档。文档和微观任务补齐后，再根据客观范围和用户选择决定是否插入一次 UI 目标。
B2. **功能五收口规则**：任务拆分负责把**全部已确认需求**一次性拆成可执行的微观任务，不负责留一部分下次再拆。只有文档阶段真实通过后，才允许解锁 UI 目标或开发目标。

### C. 完整流程真实前端 UI 壳五路线分支

C1. 文档和微观任务一次性补齐后，如果涉及页面、表单、列表、弹窗、按钮、状态切换、空态/加载态/错误态、流程页、设置页、UI 优化、前端重构、深度美化、响应式优化或交互优化，就进入真实前端 UI 壳五路线；纯后端、纯修复、纯删除、纯配置、纯文档且不涉及页面或交互变化时，先明确说明原因，再继续后续步骤，不要卡住。已有项目中途插入 UI 视觉确认时，如果基础文档/功能已存在且用户明确要先看视觉图，可以直接进入 UI 视觉确认分支，不得机械要求先再跑一次文档回写。
C2. UI 壳必须严格根据已确认的文本视觉方案，或“文本视觉方案 + 视觉图 / 原型图”创建。UI 壳是项目真实前端文件里的外观和交互壳，不是独立 `prototype.html`，不是 demo。UI 壳负责页面结构、组件结构、布局、样式、视觉层级、响应式、交互外观、空态/加载态/错误态/成功态等状态外观、项目内可查看入口，以及接口/状态/事件/mock/类型入口预留；不负责真实接口调用、完整业务逻辑、真实数据流、状态管理接线、权限判断落地、表单真实提交和真机验收。
C3. 进入 UI 流程后，先判断当前 UI 状态：没有前端、已有前端代码、已有前端 + 业务代码、已有视觉图/截图/Figma/参考图。最终落地对象默认是真实前端 UI 壳；只有用户明确要求静态演示时，才另行说明例外。
C3.5. 原生 `request_user_input` 每题只能容纳 2–3 个选项，因此 UI 五路线使用两步原生选择：第一步显示“Codex 直接”、“@product-design”、“继续选择外部/Studio 路线”；只有选第三项才显示第二步的“外部 AI”、“Stitch”、“Codex 内嵌模型”。选项问题、标签和说明都是纯文本。只有原生工具不可用时，才一次显示“选项一：……选项五：……”五个纯文本段落。
C4. 让用户选择五条 UI 路线（依 C3.5 使用两步原生选择或五个纯文本回退段落）。下面的选项文字和说明均不使用 Markdown 包裹：

选项一：$liran-plan Codex 直接生成前端 UI 壳（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

说明：Codex 根据已确认视觉依据和 UI 壳接入清单，在真实前端文件中生成 UI 壳并预留接口。

选项二：$liran-plan @product-design（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

说明：@product-design 参与设计和 UI 壳落地，产物仍是项目真实前端 UI 壳，不接业务逻辑。

选项三：$liran-plan @product-design + 外部 AI 生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

说明：先确认视觉方案，Codex 准备接入清单和外部 AI 提示词；外部 AI 只做 UI 壳，回到 Codex 后由开发目标接业务。

选项四：$liran-plan @product-design + $Stitch / Stitch MCP（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

说明：先由 @product-design 整理并确认文本视觉方案，然后生成 Stitch 专用提示词；回传 Stitch MCP 信息后，Codex 依 HTML 做实例级一比一还原并强制复修。

选项五：$liran-plan @product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

说明：先由 @product-design 确认文本视觉方案，再由 Codex 在当前会话内通过 OpenCodex 本地路由选择当前可用模型生成 UI 壳；不需要复制到外部软件，不维护固定模型白名单，不新增强制模型选择框。
C5. 五条路线都必须先确认文本视觉方案；如需视觉方案图/原型图，只能在文本视觉方案确认后再生成或由用户提供。如需生图，优先让用户选择 `$liran-image2` 或自行指定外部工具，禁止使用 `$imagegen`。视觉图确认前不要把文本视觉草案写死进文档。
C6. 造壳前硬门禁：Codex 必须先创建或更新 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md`，决定本次 UI 壳需要哪些真实前端文件，创建合法占位文件（不是随便空文件），安排正式入口或临时预览入口，准备 mock/type/局部样式/注释锚点。没有这些准备，不允许进入 UI 壳落地，也不允许给外部 AI 生成造壳提示词，也不允许开始 Stitch MCP 下载。
C7. 外部 AI 开工前就绪门禁：Codex 必须确认文本视觉方案已确认；如有视觉图/原型图，图已确认；`liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md` 已生成；UI 壳需要的文件已由 Codex 创建为合法占位文件；每个文件用途已写清；允许外部 AI 编辑的文件白名单和禁止编辑范围已写清；查看入口已安排；mock/type/局部样式文件已准备；代码里已有 `TODO(ui-shell)`、`TODO(codex-connect)` 等注释锚点；外部 AI 提示词已生成且可直接复制；提示词明确外部 AI 不许新增文件、不许新增依赖、不许改全局样式、不许接真实接口、不许补业务逻辑；如果外部 AI 发现文件不够，必须停止并让用户回 Codex 补文件。
C7.5. Stitch 路线开工前就绪门禁：Codex 必须确认文本视觉方案已确认；基于需求文档、功能树、模块结构、用户流程和信息架构形成的完整页面清单及页面总数已确认；如有视觉图/原型图，图已确认；Codex 已追问并得到 `视觉方案确认好了吗？` 的明确确认；`liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md` 已生成；UI 壳需要的真实前端文件已由 Codex 创建为合法占位文件；查看入口已安排；mock/type/局部样式/注释锚点已准备；Stitch 专用提示词已生成；用户已提供 `$Stitch` / Stitch MCP 的 Project ID / Screen ID；Codex 已准备好记录 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID、Screen 映射关系、下载目录和 HTML 来源文件；Codex 已准备先做 `控件规格盘点`，再开始真实前端承接。没有这些准备，不允许开始 Stitch 下载和一比一还原。
C8. 文件预创建规则：Codex 需要提前创建或安排页面文件、组件文件、局部样式文件、类型文件、mock 文件、局部工具文件和必要入口挂载文件。外部 AI 不负责猜文件结构，只能编辑 Codex 指定的允许编辑文件清单；不得自行新增、删除、移动、重命名文件。回到 Codex 后，UI 壳接收检查必须对照白名单检查 diff。
C8.5. Stitch 提示词规则：如果用户选择第 4 条路线，先追问并得到 `视觉方案确认好了吗？` 的明确确认后，才能按 [templates/Stitch-页面设计开发提示词.md](templates/Stitch-页面设计开发提示词.md) 从 `liran_docs` 正式 PRD、功能树、模块文档、完整页面清单和已确认文本视觉方案填实，生成给 Stitch 的提示词。交付时只给一个独立的 Markdown 代码块。标题必须是 `# {系统题目} — Stitch 多页面设计提示词`，且一级标题后必须紧接“额外设计约束”（0）至（8）原文，不得改字、拆分、概括或后移。视觉风格写入设计上下文，但额外设计约束优先。提示词必须分端列出 PC 端与移动端页面，并写明 `项目总页面数 = PC 端独立页面数 + 移动端独立页面数`；H5 与微信小程序默认共用一个移动页，不重复计数。页面数量不设置固定上限或下限。页面清单有几个页面，Stitch 就生成几个页面，不得遗漏，也不得自行增加。独立路由或独立业务界面默认计为页面；弹窗、抽屉、面板、组件和 loading / empty / error / success 等状态默认归属页面，不额外计数，除非已确认清单明确把它们定义为独立 Screen。如果 Stitch 单次无法生成全部页面，可以分批生成；所有批次最终必须覆盖完整页面清单，页面总数、名称、职责和关系不得漂移。若某模块与当前产品形态无关，直接标注“不适用”并说明原因。Stitch 不负责预留接口。提示词不要加多智能体开头，也不要写 `## 流程合同`。用户回传 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID 后，Codex 再用 `$Stitch` / Stitch MCP 落到真实前端 UI 壳，再进入实例级细节复修。
C8.6. Stitch MCP 输入规则：用户会给类似 `Project ID`、`Screen ID` 的 `$Stitch` / Stitch MCP 信息。Codex 要根据这些信息下载 Stitch 提供的 HTML、样式、图片、代码、MD 规范等，再根据这些文件实际内容判断如何落到真实前端；不提前对 Stitch 做额外限制，不规定 Stitch 必须怎么写依赖，不擅自否定 Stitch 输出。
C8.7. Stitch 多屏规则：一个 Stitch 项目可以有多个 Screen。Codex 拿到 MCP 信息后再判断一个 Screen 对应页面、弹窗、抽屉、状态页还是组件；如果多个 Screen 属于同一个 UI 壳，就写在同一个单壳清单里；如果属于不同 UI 壳，就拆成多个 `ui-shells/...md`。
C8.8. `实例级尺寸保真规则`：第 4 路线的一比一还原，不能只做到风格接近、结构相似、布局差不多，而必须根据 Stitch 原始产物做实例级视觉规格保真的一比一还原。除了结构、布局、色彩、阴影、边框、圆角和视觉层级，还必须保留原始 HTML 中每个元素自己的 `width / height / min-width / min-height / max-width / max-height`、`padding / margin / gap`、`border-radius / border-width`、`icon width / height`、`font-size / font-weight / line-height / letter-spacing`、单行/多行/截断/不换行、flex 方向、是否 wrap、对齐方式，以及控件在 header / footer / toolbar / card / panel / table action 区里的实际占位和比例关系。
C8.9. Stitch 根因口径：第 4 路线失真，常见根因不是大布局没抄到，而是承接时把原始 HTML 中每个元素自己的实例级尺寸、间距、图标大小、按钮规格、控件规格和文本排版行为，通过通用化抽象抹平了，或者被老项目已有组件默认尺寸、全局样式、公共图标样式、公共按钮样式、公共表格样式悄悄带偏了。以后不得再把这类问题模糊描述成“样式没调好”。
C8.10. Stitch 事实来源优先级：第 4 路线承接时，视觉事实来源优先级必须写死为：1）第一事实来源：Stitch 下载下来的 HTML；2）第二事实来源：Stitch 下载下来的代码 / 样式 / MD 规范；3）第三事实来源：Stitch 下载下来的截图。能从 HTML 直接确认的尺寸、结构、class、层级，不允许靠截图猜；HTML 没写清但代码 / MD 有写清时，才可以用第二层证据；截图只能做补充校对，不是第一依据。能从 HTML 直接读出的实例级尺寸和控件规格，属于硬依据，不得擅自抽象、合并、重解释或改写成另一套通用规格。
C8.11. Stitch 控件规格盘点门禁：Codex 在开始真实前端承接前，必须先做一次 `控件规格盘点`。至少盘点按钮变体、每种按钮的高度/圆角/padding/字体/图标尺寸、图标尺寸层级、输入控件规格、badge / pill / tag 规格、卡片操作区布局、footer / toolbar / header 操作区布局、高密度控件区，以及最容易因为尺寸错误导致排版塌陷的区域。盘点结果必须写入单壳清单，用来防止不同规格被误合并、防止写到一半才发现控件并不是一套尺寸，也防止后续为了省事强行通用化。
C8.12. Stitch 禁止过早抽象 / 通用化：在第 4 路线里，视觉未对齐前，禁止为了工程整洁、复用、组件化、统一规范而主动做会改变视觉结果的抽象。禁止把不同按钮变体合并成统一按钮组件规格；禁止把不同图标场景合并成统一图标尺寸；禁止把不同输入框、下拉框、textarea、表格工具栏、表格行操作统一成一种规格；禁止先抽象成通用组件，再反过来猜尺寸；禁止把 Stitch 实例级 class 差异抹掉；禁止为了“代码更漂亮”破坏视觉精度。只有在已经按 Stitch 原始产物视觉完全对齐之后，才允许做局部抽象，而且抽象后不得改变尺寸结果、比例结果、排版结果、按钮/图标/输入框/表格规格和文本换行与占位行为。
C8.13. Stitch 防默认样式带偏：第 4 路线不仅要防自己抽象过度，还要防真实项目现有样式体系、公共组件默认值和全局规则把控件规格带偏。不能因为项目里已有 Button / Input / Icon / Table 组件就默认沿用；如果沿用现有组件，必须验证最终视觉结果与 Stitch 一致；如果默认规格不一致，必须覆写到一致。样式必须优先局部作用域；高风险控件必须允许实例级覆盖；同时显式防范全局 `button / input / svg / table` 样式、组件库 size variant、reset、主题变量和公共类名干扰。
C8.14. Stitch 高风险元素范围：凡是可能因为通用化抽象、复用默认组件规格或受全局样式影响而丢失原始 HTML 实例级尺寸差异、控件规格差异、间距差异和文本排版行为的 UI 元素，都属于第 4 路线一比一还原的高风险对象。至少包括：图标、纯图标按钮、普通按钮、头部胶囊按钮、卡片底部按钮、footer 主次按钮、toolbar 按钮、输入框、textarea、select、checkbox、radio、switch / toggle、badge / pill / tag、搜索框、tab、dropdown trigger、统计卡图标块、卡片操作区、菜单项、步骤卡片、进度条、分页控件、面板 / 抽屉 / 弹窗 footer 控件、表格、表头、表格行高、单元格 padding、筛选栏、操作列按钮，以及文本字号 / 行高 / 字重 / 字距 / 单行 / 换行 / 截断 / 竖排风险和 header / footer / toolbar / card action / table action 内的控件占位关系。
C8.15. Stitch 例外处理规则：如果真实项目技术栈无法 100% 原样搬运某种 Stitch 表达方式，Codex 必须先说明为什么不能原样表达，记录受影响元素，选择当前项目可行的等价实现方式，并保证最终视觉结果、尺寸结果和排版结果尽量保持一致。例外只能是实现路径例外，不能是视觉结果例外，不允许借“技术栈不一样”为理由自由发挥重设计。
C9. 预留接口规则：UI 壳里的预留点必须严格根据 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md` 创建。必须预留 API 占位、数据结构、loading/error/empty/success/disabled/selected/expanded/pagination/filter 等状态入口、点击/提交/筛选/分页/弹窗开关/行操作/批量操作等事件钩子、权限控制点、路由参数、表单规则、mock 数据位置、类型/interface/schema 和 Codex 后续接线说明。建议统一标记 `TODO(ui-shell)`、`TODO(codex-connect)`、`TODO(codex-state)`、`TODO(codex-permission)`、`TODO(codex-validate)`、`TODO(codex-route)`。如果是 Stitch 路线，Stitch 不负责预留接口；接口、状态、事件、权限、路由、表单、type/mock 等预留必须由 Codex 在真实前端落地时根据接入清单补上。
C10. 样式作用域规则：样式默认只能在当前 UI 壳范围内生效。默认禁止污染老页面、重写全局样式、替换 UI 组件库、修改全局主题变量、修改公共组件样式、修改 CSS reset，除非用户明确批准。Codex 应优先为 UI 壳创建局部样式文件，并在提示词里要求外部 AI 只能写这些局部样式。
C11. 外部 AI 输入包必须包含当前项目背景、技术栈、现有 UI 库/样式规范/设计系统、已确认文本视觉方案、可选视觉图/原型图路径、接入清单路径、允许编辑文件清单、每个文件用途、查看入口、样式作用域要求、预留接口要求、禁止事项和完成后输出格式。目标是用户复制过去，外部 AI 就能直接干活，不需要再猜项目结构、文件路径、入口、接口怎么留。
C11.5. Stitch 依赖规则：普通外部 AI 路线默认禁止新增依赖；但第 4 路线为了还原 Stitch HTML，允许 Codex 围绕 Stitch 输出选择当前项目可行的实现方式，优先跟随 Stitch HTML 用到的依赖、样式结构和资源结构。不能因为“默认禁止新增依赖”把 Codex 逼回模仿路线，但仍不得改后端、数据库、权限、支付等高风险业务逻辑。若项目技术栈不能原样表达某种 Stitch 依赖或写法，必须使用视觉结果等价方案，而不是借机重画。
C11.6. Stitch 静态数据规则：UI 目标直接使用 Stitch MCP 下载 HTML 里的静态数据，不另起 mock；后续开发目标再替换为真实 API 数据。
C12. UI 壳接收检查：外部 AI 或 Codex 生成 UI 壳后，Codex 必须先检查 `git diff`、白名单、依赖、全局样式、公共组件、高风险文件、可打开入口、文本/图像视觉依据与接入清单。检查不通过时留在当前 UI 目标修复和回写，不解锁开发目标。
C12.5. Stitch 初次接收检查口径：只检查 Codex 落到真实项目里的前端 UI 壳文件。结果只允许 `可以进入实例级细节复修` 或 `初次承接受阻`；不得跳过复修直接解锁开发目标。
C12.6. Stitch 强制实例级细节复修：初次接收检查得出 `可以进入实例级细节复修` 后，Codex 必须自动交付 [templates/Stitch-实例级细节复修提示词.md](templates/Stitch-实例级细节复修提示词.md)。提示词必须同等覆盖页面结构与布局、尺寸与间距、字体与文本排版、颜色和视觉样式、控件规格、图片和视觉资源、层级与组合关系、状态表现、响应式与不同视口；控件规格只是其中一个维度。实例级复修提示词属于固定模板直出例外，不走普通 `/goal` 流程合同检验，不添加 `## 流程合同`、`## 档位执行门禁`、目标阶段、目标编号或归档字段。运行时只允许填充或替换项目事实、增加项目专属限制/文件/验证，以及将不存在的元素标记为 `不适用：当前 Stitch 原始产物中不存在该元素。`；项目事实统一追加在固定模板原文之后，并使用明确字段标签，不得插入或改写固定正文；不得删除固定词语、列表项或章节，不得缩短、概括、改写或合并进其他目标。实例级复修提示词也必须保持 3000–10000 个字符，但必须通过固定正文、章节顺序、视觉维度、事实来源、验证和收口完整性检查；复修通过后才允许解锁开发目标。
C13. Product Design Design QA 门禁：其他 Product Design 路线仍保留 Design QA。如果走 `@product-design` 或 Image To Code 等非 Stitch Product Design 路线，仍必须遵守 `product-design:design-qa`，保留同图对比、局部放大、`design-qa.md`、五大保真面、90% 最低相似度线和 actionable P0/P1/P2 收口规则。第 4 条 Stitch 路线不调用 `product-design:design-qa`，不创建 `design-qa.md`，不使用 90% 门槛或 P0/P1/P2/P3 分级；其视觉门禁由 C12.5–C12.6 的初次接收检查和强制实例级细节复修独立承担。
C14. 已触发的 Product Design Design QA 不能挤牙膏：每轮对比图时必须先做批量差异盘点，至少检查整体布局、比例、页面密度；容器尺寸、位置、对齐；卡片、弹窗、面板、dock、工具栏；字体、字号、字重、行高；颜色、透明度、边框、圆角、阴影；按钮、输入框、输出框/结果区；表单、表格、列表、标签、徽标；导航、菜单、标签页、面包屑；图标、图片、头像；Toast/提示、分页、进度条；加载态、空态、错误态；hover / focus / active / disabled / selected 状态；expanded / collapsed、modal open / close、panel switch、screen switch 状态；桌面端、移动端、响应式表现，以及内容变多 / 变少时的排版稳定性。差异清单必须分级为 P0/P1/P2/P3，优先批量修 P0 + P1，并尽量合并处理 P2。QA 不仅要检查页面像不像，还要检查有没有因为图标、按钮、输入控件、表格控件、文本规格失真而破坏整块 UI 的排版流。
C15. QA 和预览工具必须按目标类型选择：普通网页、localhost 或 file 入口优先用内置浏览器；Chrome 扩展、需要真实 Chrome 登录态/插件环境/浏览器扩展状态的页面用 `@Chrome`；桌面 App、系统 UI、插件外壳或必须操作本机应用的场景用 `@电脑`；脚本、CLI、服务、后端任务用命令行、日志、单测、集成测试或项目现有验证命令。Chrome 扩展改完代码后，必须先打开 `chrome://extensions` 找到对应扩展并刷新扩展，再刷新或重新打开插件页面后才截图 QA；插件页面包括 popup、side panel、options page、devtools page 和 content script 对应页面。
C16. 回退机制：开发目标内发现 UI 壳结构、事件、状态、数据入口或样式作用域需修正时，在当前开发目标内回写视觉方案和接入清单，重跑 UI 接收检查后再继续接线和内测，不回退目标编号、不改总目标数。如果必须重做已确认的视觉方向或重新走外部 AI/Stitch，视为超出原确认范围，标记受阻并回到 `$liran-plan` 重新确认。
C17. 禁止幻觉与默认禁止：外部 AI 和 Codex 都不得伪造接口路径、后端返回、权限字段，不得把 mock 写成真实数据，不得把没验证的入口说成可用，不得把 UI 壳完成说成业务完成。不知道的 API、字段、权限、路由、接口返回结构、业务规则，一律标 `待确认` 或 mock/schema 占位。默认禁止新增依赖、替换 UI 组件库、重写全局样式、修改全局主题变量、修改公共组件样式、修改 CSS reset、修改后端代码、修改接口协议、修改数据库/migration、修改认证/权限/支付/数据删除等高风险逻辑、删除文件，除非用户明确批准。仅第 4 路线例外：为了实现 Stitch HTML 一比一还原，Codex 可以围绕 Stitch 输出选择当前项目可行的等价依赖或资源方式，但仍不得借机改后端或高风险业务逻辑。

### D. 四档分阶段 `/goal` 节奏

D1. 文档目标永远在深度/完整流程最前面，只负责文档、任务、微观任务、开发追踪和验收准备，禁止修改实现源码、做 UI 施工、真机验收或归档。
D2. UI 目标如适用只插入一次，位于文档目标和开发目标之间。其负责视觉方案、视觉图、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用的 Design QA，禁止接真实 API、权限、数据流和表单提交。外部输入未返回时暂停原 UI 目标，不生成新目标。
D3. 开发目标负责 TDD 实现、真实业务接线、内部测试和回写。深度流程的最后开发目标同时负责已确认的真实验收、修复复测和用户检查交接；完整流程的开发目标最多到 `内部测试通过`，禁止真机验收和归档。
D4. 完整流程的最后验收目标按已确认的验收责任分支。Codex 真机分支完成真实验收、问题回写、修复和复测；用户自测分支进入 `待用户验收`，收到明确结果后继续原目标。两条分支通过后都进入 `待用户检查 → 待归档确认`；用户回复“归档”后，独立 archive 目标才执行 `归档中 → 已归档 → 已完成`。
D5. 每次目标结束前必须审计本阶段产物和下一阶段前置，再生成下一次目标提示词。中间目标只能说明“本阶段已完成，已解锁下一目标”，禁止使用整体完成或已归档话术。

### E. 提示词质量与阶段收口

最后普通目标使用 `--archive-stage handoff`；用户明确回复“归档”后才启动独立正式归档。

E1. 所有可复制提示词都必须足够详细，但开头必须有明确执行语句，例如：

   ```text
   请直接开始执行下面步骤，先读取对应文档，再输出结果，不要先解释。
   ```

   详细是结构清楚、边界清楚、动作清楚，不是把同一件事重复说很多遍。文档、UI、开发、验收各阶段目标都要有匹配本阶段的具体启动句，不能只靠泛化句式。
   可复制提示词交付时，完整提示词必须只放在一个独立的 Markdown 代码块中；代码块内部不得嵌套三反引号，提示词中的结构改用普通标题、列表和内联反引号。
E2. 每条回复只围绕一个当前阶段/一步的结果展开；同一阶段内必要的结果摘要、文件清单、判断依据和下一步可复制提示词可以放在同一条回复里，但不要把需求整理、文档生成、任务拆分、/goal、真机实测等不同阶段混在一起。
E3. 如果当前目标已由 PRD 需求文档、单任务归档、`liran_docs/04-开发追踪.md`、`liran_docs/09-真机实测.md` 和相关模块文档共同证明 `已归档 → 已完成`，必须明确收口，不再输出下一步提示词。

## 六类入口场景

1. **新项目**：先整理项目目标、用户是谁、解决什么问题、核心功能、边界、不做什么、验收标准。
2. **老项目新增功能**：先整理新增什么、为什么新增、加到哪里、影响哪些旧模块、哪些旧功能不能动、验收标准。
3. **老项目续作**：先整理已经做了什么、哪些是真的完成、哪些只是半成品、当前真实状态、下一段只续哪里、不要重复做什么。
4. **老项目修复**：先整理修什么问题、复现路径、期望结果、影响范围、不能改坏什么、回归验证点、验收标准。
5. **老项目删除**：先整理删什么、为什么删、入口在哪里、依赖谁、影响哪些模块、哪些数据/配置/API 要保留或迁移、删除后怎么验证无残留、不能误删什么。
6. **其他**：前 5 类以外、但确实要用 `liran-plan` 处理的需求。比如发布、部署、迁移、重命名、改 README、改技能规则、改提示词、检查流程、优化规范、清理文档、项目发布说明等。先判断任务类型，再按四档评分结果使用对应需求整理深度；只有完整流程默认多轮整理。

`其他` 不是“随便塞进去”的兜底，它是和前 5 类平级的正式入口。只要需求不落在前 5 类里，但确实需要 `liran-plan` 处理，就走 `其他`。

## 可复制提示词质量门禁

任何给用户复制的提示词，都要像“任务说明书”，不能像一句口号。详细不是写很多空话，而是边界清楚、完成条件清楚、文件路径清楚、禁止事项清楚。

本节的“给用户复制的提示词”按类型处理：普通目标提示词采用文件指针型短格式，必须写清任务 ID、流程档位、目标 N/M、当前阶段、读取文件、允许/禁止范围、验证、状态回写、完成条件和下一阶段解锁条件；专项提示词继续遵守各自完整模板和长度规则。澄清问题、选择框、进度更新、阻塞说明、单句启动语和单条命令不属于普通目标提示词。

提示词至少包含：

1. 任务性质：这一步做什么、不是什么、当前阶段与流程档位。
2. 当前场景：项目、任务类型、已完成前置和当前可信事实。
3. 目标和完成结果：核心目标、最终产物、可验证结果和不属于本轮的内容。
4. 读取要求：项目规则、真实代码、配置、测试、已有文档、Git 状态和长期避坑；只有真实存在或当前档位要求时才列 `liran_docs`。
5. 修改范围：目标模块、文件白名单、新文件/依赖/公共组件/全局样式边界，以及信息不足时如何处理。
6. 执行步骤：调查、复现或失败测试、实现、局部验证、文档回写和最终 diff 检查的顺序。
7. 业务与安全边界：只允许做什么，禁止动哪些接口、数据、权限、认证、支付、删除或不可逆逻辑。
8. UI 专项要求：涉及 UI 时写明事实来源、样式作用域、视觉和接线边界；不涉及时保留本项并写具体不适用原因。
9. 验证要求：语法、lint、typecheck、单测、集成、构建、预览、真机、Git diff 和无关文件检查。
10. 完成后输出：实际读取/修改文件、逐文件变更、验证命令与结果、风险、遗留事项和下一阶段。
11. 收口条件：哪些证据同时成立才能结束，哪些情况必须继续修复，哪些事项要留到下一阶段。
12. 如果本轮涉及 UI，轻量和标准仍在单目标内完成适用的局部页面/组件修改；深度和完整流程则在文档目标后插入独立 UI 目标。该 UI 目标可创建对应接入清单、合法占位文件、入口和 mock/type/局部样式/注释锚点，完成 UI 壳和视觉验收；真实业务接线留到开发目标。Stitch 必须保留初次承接、初次接收检查和强制实例级细节复修，其他明确高保真 Product Design 路线仍按触发条件执行 Design QA。
13. 如果本轮会创建或更新多个文件，必须逐文件写清本轮改什么、补什么、删什么、更新什么，不能只列文件名。

普通目标提示词可以使用“以正式 PRD 当前内容为准”“以模块文档当前内容为准”等文件指针，但必须列出真实路径、执行范围、验证、状态回写和完成条件。专项提示词仍不得用摘要替代固定正文；不适用的专项结构用 `不适用：当前任务不涉及该项，原因是……` 简洁说明。

这些提示词必须尤其详细：

- 生成/更新 `liran_docs` 文档体系并一次性拆完全部已确认需求的合并提示词
- 真实前端 UI 壳五路线提示词
- 文档、UI 和开发阶段 `/goal` 提示词
- 生成/更新 `liran_docs/09-真机实测.md` 提示词
- 最后验收交接与独立归档提示词
- 修复场景提示词
- 删除场景提示词
- 续作场景提示词

如果某些字段当前确实未知，不要硬编；在提示词里写成“待确认”，并要求执行者先从代码、旧文档或用户原话中查证。缺关键信息时，先补文档或列出最小必要问题，不要跳到写代码或 `/goal`。

## 状态机与完成门禁

Codex 负责真机测试时的状态顺序：

`待开发 → 进行中 → 内部测试通过 → 待实测 → 真机测试通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

用户自己测试时的状态顺序：

`待开发 → 进行中 → 内部测试通过 → 待用户验收 → 用户验收通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

补充状态：

`受阻` —— 任意阶段如被依赖、环境、权限或外部条件卡住，均可标记为 `受阻`，但必须写清阻塞原因与依赖项。归档阶段失败时使用 `归档受阻` 并保留活动内容。

状态含义：

- `内部测试通过`：接口、逻辑、页面、UI 壳接线或代码主链路已经完成，并通过内部验证。
- `待实测`：已准备好进入真实环境验证，且已创建或更新 `liran_docs/09-真机实测.md`。
- `真机测试通过`：已用真实环境完成对应清单的实操验证。
- `已完成`：Codex 真机分支已经真机测试通过，或用户自测分支已经用户验收通过，并且问题回写、长期事实更新、单任务归档、归档索引和活动区清理均已完成。
- `待用户验收`：Codex 已完成内部测试，等待用户按约定方式测试。
- `用户验收通过`：用户明确反馈通过，可以在完成必要回写后进入待用户检查，不能跳过归档确认和 `已归档` 直接标记完成。

## 四档 `/goal` 标准节奏

| 流程 | 无 UI | 有 UI |
|---|---|---|
| 轻量 | single（1/1） | single（1/1） |
| 标准 | single（1/1） | single（1/1） |
| 深度 | documentation（1/2） → development-and-acceptance（2/2） | documentation（1/3） → ui（2/3） → development-and-acceptance（3/3） |
| 完整 | documentation（1/3） → development（2/3） → acceptance（3/3） | documentation（1/4） → ui（2/4） → development（3/4） → acceptance（4/4） |

每一次目标都必须写明基础目标数量、第 N/M 次、目标阶段、UI 决策、UI 路线、等待外部输入状态、进入证据、本阶段职责、禁止进入的后续阶段和下一目标解锁条件。中间目标必须使用 `--archive-stage non-final`，最后普通目标必须使用 `--archive-stage handoff`；用户明确回复“归档”后，才使用独立 `archive` 目标执行正式归档。

`/goal` 未达到本轮完成条件时，不要吐下一条命令；只有本轮完成、真实硬性阻塞、或需要切回 `$liran-plan` 准备下一阶段时，才给下一步提示词。

## 核心纪律

核心纪律分五组：F 原话与需求纪律、G 文档结构纪律、H 真机实测纪律、I 提示词质量纪律、J 收口与回退纪律。

### F. 原话与需求纪律

F1. **原话只留一次**：第一次记录用户原话时保留原貌，后续只续记关键点、变更点和确认结果；AI 自己的查证/推断要明确标注区分。
F1a. **具体任务先建需求整理文档**：命中 4.4 触发范围后，在指定目录创建或复用 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`；路径不明就询问，禁止乱放。用户确认“需求整理好了”后，再根据该文件重新生成同任务的独立 `*-PRD.md`。后续先更新当前阶段文件再回复增量回执。
F2. **按档位整理需求，不急于执行**：轻量一次简短整理，标准一次模块级整理，深度按需多轮后集中确认，完整流程才执行六类场景下的完整多轮整理。任何档位在用户确认前都不写代码。
F3. **PM 视角按档位使用**：完整流程做完整产品实用性讨论；深度只讨论会改变跨模块边界的产品问题；轻量和标准不为了形式额外扩张产品讨论。

### G. 文档结构纪律

G1. **完整流程细到独立成文**：完整流程把模块、子模块和叶子交互细到独立文档；深度只更新受影响文档，轻量和标准不为几十字的小改机械新建文件。
G2. **实际改结构时先改已有索引**：只有本轮确实修改 `liran_docs` 模块结构且 `03-索引.md` 存在或当前档位要求创建时，才先更新索引；轻量和无 `liran_docs` 的标准任务不得为了满足本条新建整套体系。
G3. **文档与任务同步产出**：深度和完整流程的第一次目标都只做文档、任务和微观任务。完整流程生成/更新完整文档体系；深度流程只更新受影响文档。两者都必须在解锁 UI 或开发目标前一次性拆完已确认范围。
G4. **活动文档与历史归档分离**：`04/08/09/10` 只保留活动任务和当前事实；任务关闭后按统一任务 ID 归档，归档验证通过后才清理活动区。任务拆分和微观任务不会无限堆积：一次性施工过程归档，仍有效的模块职责与架构事实保留。

### H. 真机实测纪律

H1. **真实完成必须匹配验收责任并完成归档**：Codex 真机分支进入 `已完成` 前必须经过真机实测；用户自测分支只能先进入 `待用户验收`，收到用户明确通过结果后才能进入 `用户验收通过`。两条分支都先进入 `待用户检查 → 待归档确认`，用户明确回复“归档”后再完成 `归档中 → 已归档 → 已完成`。
H2. **真机清单优先套示例再改**：若是普通 Web 项目，优先基于 `references/功能6-真机实测示例-web.md` 复制出 `liran_docs/09-真机实测.md`，再替换成真实模块与步骤。
H3. **Codex 真机分支不问用户继续**：用户选择 Codex 自己真机测试后，真机阶段由 Codex 全程托管，直接选择工具并实操；失败后自动回写、修复、复测，直到跑通。**只要不属于下面四类真实硬性阻塞，就必须继续推进，不能停下来问用户。** 用户选择自己测试时停在 `待用户验收`，不代替用户执行或编造验收结果。只有下面四类真实硬性阻塞才允许标 `受阻` 并请求用户介入：
    - 缺少必须由用户提供的账号、权限、密钥、私有文件或外部系统访问权限
    - 当前环境完全无法运行必要工具，且没有任何替代验证方式

### I. 提示词质量纪律

I1. **提示词必须详细**：详细不是堆废话，而是边界清楚、路径清楚、禁止事项清楚、完成条件清楚。
I2. **有就补，没有就跳过**：如果当前模块或本轮验收确实存在明确技术基线、废弃方案、固定验证顺序或证据边界，就把它们单独写进提示词开头；如果没有，就不要硬编。

### J. 收口与回退纪律

J1. **步骤可修正，目标不悄悄回退**：当前目标内发现问题时，可以在当前范围内回写需求、文档、UI 清单或任务并重新验证。一旦需要跨越已完成阶段、重做视觉方向、重走外部 UI 路线或扩大需求，必须标记受阻并回到 `$liran-plan` 重新确认；不直接改目标编号或 N/M。
J2. **每段结束先判断再给下一棒**：已完成就明确收口，不再给提示词；未完成但目标模式仍在本轮范围内，就继续本轮，不给新命令；需要切阶段时才给下一条详细提示词。**如果还停留在需求整理阶段，就只能继续整理，不能给拆任务/goal/真机的下一棒。**
J3. **最终目标与归档解耦**：无论总数是 1、2、3 还是 4，第 M/M 次普通目标完成开发、测试、验收、回写和复测后，只进入 `待用户检查 → 待归档确认`；所有第 N/M 且 N<M 的中间目标均禁止归档和整体完成话术。只有用户明确回复“归档”后，独立 archive 目标才能执行安全归档；归档失败保持 `归档受阻`，不得使用“本次任务已完成并归档”。
