# liran-plan

> 版本：`4.52`


## 4.52 这次修了什么

Stitch 页面生成提示词改为按 `templates/Stitch-页面设计开发提示词.md` 从 `liran_docs` 填实，视觉方案确认后只交付一个可复制代码块。额外设计约束必须紧接标题，并按 PC/移动分端覆盖完整页面清单；Stitch 不预留接口，回传 Project Title/ID 与 Screen Name/ID 后由 Codex 落到真实前端 UI 壳。实例级复修模板未改。
> 作者：`里燃（liran）`

`liran-plan` 是一个面向 Codex 的项目规划 skill，用来把口语化需求整理成可接力、可验证、可真机验收的 Markdown 事实源和分阶段执行提示词。4.52 将 Stitch 页面生成提示词接到分端清单和 MCP 回传口径；4.42 增加正式 PRD 转换后的五维评分门禁；4.22 将最后普通目标与正式归档解耦；4.10 重新平衡四档评分：0–35 轻量、36–69 标准、70–89 深度、90–100 完整流程候选。

核心三句话：

```text
需求没整理清楚前，不开干。
目标模式没收口前，不吐下一条命令。
已确认的 Codex 真机测试或用户验收没通过前，不标完成。
归档没有真实成功前，也不标完成。
```

## 4.8 这次修了什么

- **实例级复修提示词独立校验**：Stitch 实例级复修直接输出固定模板，只允许填充项目事实，不添加流程合同、档位字段或归档字段，且必须保持 3000–10000 个字符；仍检查固定正文、章节、视觉维度、事实来源和验证完整性。
- **普通目标提示词采用文件指针型**：普通 `/goal` 按任务复杂度保持必要长度，只写任务 ID、阶段、目标 N/M、读取文件、执行边界、验证、状态回写和完成条件；Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整规则。
- **校验器分流与回归测试**：增加实例级复修提示词类型入口和专用完整性校验，保留普通 workflow 默认门禁，并覆盖超长实例提示词、合同误注入和固定正文损坏场景。

- **Stitch 页面不再限量**：先依据需求、功能树、模块、用户流程和信息架构确认完整页面清单；清单有几页就生成几页，不得遗漏或自行增加。单次能力不足时可以分批，但最终页面总数、名称、职责和关系必须与清单一致。
- **固定页数回归门禁**：主技能、功能三、提示词向导和常用提示词教程必须同时携带完整页面清单合同；校验器会拒绝旧的固定页数限制和任一入口缺失。
- **固定目标矩阵**：轻量/标准都是 1 次；深度非 UI 2 次、UI 3 次；完整非 UI 3 次、UI 4 次。
- **文档目标独立**：深度和完整的第一次都只更新文档体系、任务/微观任务、开发追踪和验收准备，不写实现源码。
- **UI 目标只插入一次**：位于文档和开发之间，负责视觉方案、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用的 Design QA；真实 API、状态、权限和表单接线留到开发目标。
- **UI 跳过规则**：深度流程在用户明确不需要 UI 时跳过；完整流程默认保留，只有任务客观不涉及 UI 或用户明确跳过时取消。
- **外部等待不加目标**：外部 AI/Stitch 需要用户回传时暂停同一 UI 目标，收到输入后续跑原目标，N/M 不变。
- **阶段合同**：每个目标必须声明基础目标数、第 N/M 次、阶段、UI 决策、UI 路线、等待状态、前置、职责、禁止进入的后续阶段和解锁条件。documentation 未选路线时可写 `pending`，进入 ui 前必须锁定。
- **最后目标先交接**：中间目标禁止归档；最后普通目标完成真实验收、问题回写和修复复测后进入“待用户检查 → 待归档确认”，不自动归档。

- **最后目标立即回收**：最后普通目标完成真实验收、问题回写、修复复测和修改后评分后，先记录 goal_status=reclaim_pending，再确认并写入 goal_status=reclaimed；项目进入待用户检查，资料保持待归档确认。用户检查不再占用原目标，归档失败也不得重新打开原目标。
- **纯文本选择框**：原生选择框的问题、选项和描述禁止 Markdown 包装；文字回退使用“选项一：……”的普通段落。

4.9 的需求整理文档与正式 PRD 分离、聊天式整理、确认后重新生成正式 PRD、执行文档归位和单任务归档构成完整闭环。

唯一闭环顺序：创建需求整理文档 → 正常聊天整理 → 用户确认整理完成 → 重新生成正式 PRD → PRD 确认 → 可选 UI 壳 → 内部开发 → 真机实测 → 问题回写 → 修复复测 → 安全归档。

需求收口口令固定为“需求整理好了吗？整理好了的话，请回复‘需求整理好了’”。收到后读取需求整理文档，重新归纳生成独立正式 PRD、建立索引并在对话中输出正式 PRD 供用户确认；用户回复“PRD 没问题”后，才继续 UI、开发、真机和归档。每个需要选择的节点必须提供正常纯文本选项，缺少选项就停在当前阶段。

## 4.4 延续能力

- **需求整理文档先行**：具体任务首轮在 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md` 创建或复用需求整理文档；用户确认整理完成后，再生成独立正式 PRD。
- **聊天式持续整理**：每轮先更新需求整理文档，记录补充、修改、确认、否决和待确认内容；正式 PRD 只在用户确认整理完成后重新归纳生成。
- **指定目录优先**：需求文件和归档目录按用户指定、项目 `AGENTS.md`、`03-索引.md`、既有同类目录/同任务活动文件定位；仍不明确就询问，不猜路径。
- **统一任务 ID**：需求、任务拆分、微观任务、`04/08/09/10`、UI 清单和归档使用同一 ID；后续讨论先更新文件，再回复增量回执。
- **活动文档瘦身**：`04` 只留活动任务，`08` 只留当前任务和精简稳定回归基线，`09` 只留待实测/失败/待复测，`03` 只留当前入口和一个归档索引入口，`10` 只留当前有效 UI 接线。
- **用户确认后独立归档**：用户明确回复“归档”后才调用 `templates/任务正式归档目标提示词.md`，再把原话、需求、功能树、模块/微观任务、计划、目标说明、开发追踪、测试、真机、修复复测、UI/Stitch/Design QA、版本和发布资料汇总进单任务归档。
- **单任务自动归档**：这里的“自动”仅指用户明确回复“归档”后，独立 archive 目标按固定顺序自动执行；普通最后目标不会自动触发归档。
- **先归档后清理**：先更新长期事实，再创建并校验归档、更新归档索引，最后按任务 ID 清理活动区并检查其他任务和索引。失败则保留原文并标 `归档受阻`。
- **状态机收紧**：最后普通目标完成后先进入 `待用户检查 → 待归档确认`；用户明确回复“归档”后才进入 `归档中 → 已归档 → 已完成`；取消、暂停和替代任务不得伪装完成。
- **目标阶段区分**：4.5 已将旧的“深度单目标/完整两目标”替换为固定的 1/2/3/4 次阶段矩阵，4.6 继续沿用。
- **可执行校验**：新增任务文档字段、路径优先级、归档确认、归档顺序、任务 ID、失败保留、历史默认忽略、handoff/archive 提示词和正式 PRD 细节覆盖校验，不增加第三方依赖。

4.3 的运行时流程合同、17 个选项规范和第五条 UI 路线继续保留：

- **统一选择项格式**：17 个会立即生成提示词的选项全部使用 `$liran-plan <原选择项文字>（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`。
- **严格空格与次数**：`$liran-plan` 后固定一个半角空格，每个选择项只出现一次前缀，细节句固定在末尾。
- **明确排除范围**：重路由、重新判断、需求修改、自由输入、澄清、状态和不会立即生成提示词的选项不加前后包装。
- **正式提示词隔离**：`/goal`、UI、外部 AI、Stitch、真机和通用执行模板正文不加入选择项专用前缀或后缀。
- **自动校验**：校验 17 项数量、前缀位置与次数、后缀位置、排除项和全部正式模板。
- **新增 Codex 内嵌模型路线**：`@product-design` 负责视觉方案，Codex 通过 OpenCodex 本地路由在当前会话内选择 Gemini 或其他实际可用模型生成真实前端 UI 壳；该路线与外部 AI 路线分开，不要求复制提示词到外部软件，不维护固定模型白名单，不新增强制模型选择框，继续受 UI 壳接收检查和非 Stitch Design QA 约束。
- **验证范围**：这是技能规则修改，仅运行仓库测试和文档校验，不执行页面检查或真机测试。

- **运行时流程合同**：每条完整提示词都固定流程档位、修改前评分、目标提示词数量、验收责任、页面样式检查、当前阶段、当前状态、进入证据、已完成/待完成门禁、允许下一动作、禁止动作、总结确认、提示词状态、真实产物审计、阻塞原因、编码解锁条件、允许升级条件和上下文恢复规则。
- **四档编码前门禁**：轻量先做依赖扫描和 RED；标准先写持久化模块任务清单并产生文档真实 diff；深度先完成受影响文档、全部微观任务、`04-开发追踪.md` 和真机/用户验收准备；完整先审计完整文档与任务产物，门禁通过后才可编辑源码。
- **真实提示词校验**：使用 `workflow_prompt_failures()` 或 `--prompt-file ... --prompt-tier ...` 检查真实交付文件，而不是只检查仓库静态参考文档；校验失败不得交付。
- **选项 canonical builder**：原生选择框与文字回退复用同一选项生成器，禁止临时另造会生成提示词的裸选项；固定细节后缀只属于选项，不进入正式 `/goal` 正文。
- **上下文压缩恢复**：`FlowContract` 提供 JSON 往返，保存档位、评分、目标次数、验收责任、页面检查、阶段、UI 路线、进入证据、已解锁门禁、阻塞原因和升级证据；无新评分及证据不得静默升级或改变目标提示词数量。
- **四档独立状态门禁**：轻量、标准、深度、完整各自使用独立状态序列；每次状态转换必须有当前状态、已完成门禁、待完成门禁、允许下一动作、禁止动作和可核对证据。
- **PRD 转换确认门禁**：用户说“需求整理好了/总结好了”后，根据需求整理文档重新生成独立正式 PRD；用户回复“PRD 没问题”后，才确认验收责任、页面样式并生成目标提示词。
- **真实交付审计**：每条真实提示词交付前必须运行运行时校验；标准、深度、完整流程还必须审计真实文件、非占位内容和本轮 diff。

3.9 的多智能体开头和评分路由调整继续保留：

- **统一目标提示词开头**：每条完整执行提示词第一行都必须让执行者自行判断是否需要多智能体协作。
- **并发上限而非累计上限**：启用时只允许一个主智能体统筹，任一时刻最多同时运行五个子代理；不限制整个任务历史上累计使用的子代理数量。
- **子代理回收**：子代理完成、失败或无需继续时必须及时回收，释放并发名额后可再启用新的子代理。
- **禁止代理嵌套**：子代理不得再派生子代理，所有协调、回收和任务分配均由唯一主智能体负责。
- **自动校验**：新增完整提示词首行校验和 Stitch 固定复修模板校验，缺少、移位或缩写统一开头都会失败。
- **评分扩大到 0–100**：`0–35` 轻量、`36–69` 标准、`70–89` 深度、`90–100` 仅为完整流程候选；简单多模块改造按标准流程，复杂多模块改造按深度流程，完整流程必须同时命中项目级硬门槛。
- **模块数量不能单独触发深度**：简单多模块改造仍按标准流程，只有复杂多模块、跨层、共享逻辑或高风险影响才进入深度流程。
- **选择项包装**：所有会立即生成提示词的用户选择项统一添加 `$liran-plan ` 前缀和“（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）”后缀；两者只属于选择项，正式 `/goal`、UI 和外部 AI 提示词正文不得带入。
- **本次验证范围**：本次仅修改和校验技能规则、脚本、测试与文档，不执行真机测试或页面样式检查。

3.7 的 Stitch 强制复修、Product Design Design QA 分流、`3000–10000` 字符完整提示词门禁和十一项标准结构继续保留。

- **Stitch 三段式门禁**：初次真实前端承接后先做初次接收检查，再强制做实例级细节复修，复修通过后才能接业务。
- **固定复修提示词**：新增 `templates/Stitch-实例级细节复修提示词.md`，保留原九章结构和收口条件，并增量补充完整视觉维度与项目微调门禁，只允许项目级事实微调。
- **Stitch 取消 Design QA**：第 4 路线不再调用 `product-design:design-qa`，不创建 `design-qa.md`，不使用 90% 门槛和 P0/P1/P2/P3 分级。
- **其他 Product Design 路线不受影响**：同图对比、局部放大、五大保真面和 actionable P0/P1/P2 门禁继续保留。
- **业务接线锁**：接入清单默认记录“否，等待实例级细节复修通过”，防止初次承接后直接进入 `/goal`。
- **自动校验**：校验脚本检查固定正文、Stitch Design QA 残留、两种初检结果、复修门禁和其他 Product Design QA 的反向保护。
- **3.7 同版本补强**：Stitch 固定复修提示词从控件尺寸重点升级为完整视觉维度保真，新增原固定正文不可删词和项目微调不可删章节；4.8 将实例级复修改为 3000–10000 字符门禁。结构、布局、尺寸、间距、字体、文本排版、颜色、视觉样式、控件、资源、层级、状态和响应式必须同等核对。
- **3.7 提示词质量补强（专项规则保留）**：完整专项提示词继续按各自模板和长度规则校验；普通目标提示词在 4.9 改为文件指针型短格式，不再套用 3000 字最低门槛。

影响范围：技能入口、过程框架优先级、需求整理深度、`/goal` 交棒方式、UI 分流、开发追踪状态、真机模板、教程、全局 slash prompt 和发布校验。

用户操作变化：有具体任务时直接描述问题即可；能显示 Codex 选择框时直接点击，选择框内只显示正常文本，不用 Markdown 包装。选择后无需再催提示词，Codex 会立即交付当前阶段的详细 `/goal`；后续目标在前一阶段真实通过后生成。

遗留风险：

- 自动评分依赖仓库中可读取的代码、测试、文档和 Git 证据；外部系统事实缺失时会保守提高分数。
- `90–100` 只是完整流程候选，仍需项目级语义判断，不能只看总分；新项目或项目级改造即使低于 90 分也可以进入完整流程。
- 真机和页面样式检查仍受账号、权限、设备、登录态和外部服务可用性限制；无法真实操作时必须如实标记 `受阻` 或 `待用户验收`。
- 等待外部 Stitch 产物仍需要用户在外部系统完成生成和回传标识；技能保持同一次 UI 目标的 N/M 与现场，不因等待额外新建目标。
- 评分是路由和解释工具，不替代安全审查、测试和人工业务判断。
- 运行时产物审计依赖执行者提供实际文件路径和本轮 diff 清单；脚本不能代替真实设备操作、用户验收或外部账号授权。

## 适合解决什么问题

- 新项目不知道怎么从需求开始规划。
- 老项目要新增功能，但怕改乱旧功能。
- 老项目已经做了一部分，当前状态混乱，需要续作。
- 老项目有功能要修复，需要先定位范围和回归点。
- 老项目有功能要删除，需要确认入口、依赖、数据和残留。
- 涉及 UI 时，希望先确认文本视觉方案，再按真实前端 UI 壳五路线推进。
- 需要把 `/goal` 前置资料、UI 壳接入清单、真机清单和问题回写组织完整。

   - `$liran-plan @product-design + $Stitch / Stitch MCP（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
   - `$liran-plan @product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
4. 开发追踪与顺序：通过 `03-索引.md` 和 `04-开发追踪.md` 维护真实状态。
5. 任务微观化与提示词：把全部已确认需求一次性拆成可执行小任务。
6. 真机实测与回写：按验收责任由 Codex 真机测试或进入用户验收；只在最后普通目标完成真实验收、回写和复测，然后等待用户检查与归档确认。
7. 四档路由与自动升级：基于证据评分，匹配任务强度，并在真实影响扩大时自动升级。
8. 任务文档与归档：具体任务先建工作 Markdown，验收后按任务 ID 归档并清理活动文档。

## 四档自适应流程

| 分数 | 流程 | 需求整理与执行 |
|---:|---|---|
| `0–35` | 轻量流程 | 一次简短整理、一个 Codex 单选框、一条轻量 `/goal` |
| `36–69` | 标准流程 | 一次模块级整理、一个 Codex 单选框、一条标准 `/goal` |
| `70–89` | 深度流程 | 必要多轮整理、一次详细集中确认、非 UI 2 次或 UI 3 次 `/goal` |
| `90–100` | 完整流程候选 | 还需满足项目级条件，再进入完整规划、完整文档和非 UI 3 次或 UI 4 次 `/goal` |

评分五项各 `0–20` 分：

1. 项目现状
2. 修改规模
3. 依赖与修改后影响
4. 风险与回滚
5. 验证复杂度

已确认没有影响才可以打 `0`；尚未查清至少打 `1`；关键影响未知打 `2`。关键影响未知时先显示暂未确定并继续调查，执行前仍无法查清时最低按深度处理。每项都要附代码、调用方、测试、文档或 Git 证据。文件数量和修改行数只能作为辅助证据。

未命中安全门禁时采用用户指定档位；安全门禁只规定最低档位。数据删除/迁移、认证权限密钥支付、生产操作、公共 API、共享核心逻辑、跨多个独立模块、Stitch、高保真和新 UI 壳最低进入深度流程；新项目、同时新增三个或以上独立功能模块、整体架构重构、大规模数据或技术栈迁移、多个大型模块同时改造、项目事实严重混乱或用户明确要求完整流程时进入完整流程。

小任务上限：老项目单文件局部修改最高轻量；老项目单模块小功能最高标准；单模块完整改造默认标准、必要时深度；跨模块功能、新 UI 壳和高保真还原进入深度；新项目和项目级改造才进入完整。高风险安全门禁只规定深度最低档，不会把范围明确的小任务机械升级为完整。

## 第一次使用会发生什么

如果用户只输入：

```text
$liran-plan
```

或：

```text
/liran-plan
```

它不会直接写代码，不会直接开 `/goal`。因为没有具体任务，它会先问六选一：

```text
1. 新项目
2. 老项目新增功能
3. 老项目续作
4. 老项目修复
5. 老项目删除
6. 其他
```

新项目进入完整流程；其他场景先调查评分。具体修改任务会先在指定目录创建或复用一份需求整理文档。只有完整流程默认多轮需求整理；轻量只做一次简短整理且不扩张完整文档树，标准做一次模块级整理，深度按实际影响做必要的多轮整理。

需要集中确认时，环境有 `request_user_input` 就调用原生选择框；问题、选项和描述只用纯文本。没有该工具时，用“选项一：……”普通段落回退，不使用 Markdown 列表。用户选完后同一轮直接得到当前阶段 `/goal`，整条提示词只放一个代码块。深度与完整先跑文档目标，如适用再插入 UI 目标，然后才进入开发和最终验收。

UI 五路线不会硬塞进一个超限选择框：原生工具使用 3+3 两步选择，第一步的“继续选择外部/Studio 路线”只打开第二步，不生成目标；只有原生工具不可用时才一次显示五个纯文本段落。

```text
整理好了吗，还需要补充吗？
```

完整流程中，当用户明确说“需求整理好了”或“总结好了”后，技能会根据独立需求整理文档重新生成正式 PRD、建立索引并在对话中输出；用户回复“PRD 没问题”后，再用同一个纯文本选择问题确认验收责任和页面检查。

选项一：$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

确认后立即交付文档阶段目标，同时完成：

1. 生成或更新整套 `liran_docs/`
2. 一次性拆完全部已确认需求的微观任务

如果用户一开始就给出具体 Bug 或功能，Codex 会跳过六选一，先调查和评分，然后在回复最前面直接以正常 Markdown 加粗文本显示：

**当前流程：标准流程（40/100）**

**开始方式：按照标准流程，先整理当前模块和影响范围，确认后生成一条标准 /goal 提示词。**

**选择原因：修改集中在一个模块，但涉及多个关联文件；影响范围可以确认，不涉及公共协议和高风险数据。**

这些关键状态必须正常显示，不能放进代码块。

## UI 流程

页面任务也按档位处理：

- 轻量：已有页面的局部样式、小交互或单一状态修复，不创建完整 UI 壳。
- 标准：整页或整组件调整，不走完整五路线；状态验证必做，页面样式检查按用户选择执行。
- 深度：新页面、复杂状态、跨页面交互或 UI 与业务联动，创建受影响 UI 壳清单；Design QA 按用户选择执行。
- 完整：新项目或多个大型 UI 模块整体推进，进入真实前端 UI 壳五路线。

完整五路线为：

1. `$liran-plan Codex 直接生成前端 UI 壳（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
2. `$liran-plan @product-design（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
3. `$liran-plan @product-design + 外部 AI 生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
4. `$liran-plan @product-design + $Stitch / Stitch MCP（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`
5. `$liran-plan @product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`

共同门禁：

- 先确认文本视觉方案，必要时再确认视觉图 / 原型图。
- 造壳前必须先生成 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md`。
- 由 Codex 先规划真实前端文件、创建合法占位文件、安排入口、准备 mock/type/局部样式/注释锚点。
- 外部 AI 只允许在 Codex 指定文件里造 UI 壳，不得自行新增文件、依赖、全局样式或业务逻辑。

Stitch 第 4 路线额外规则：

- 先由 `@product-design` 确认文本视觉方案和可选视觉图。
- Codex 必须追问：`视觉方案确认好了吗？`
- 用户确认后，Codex 生成固定结构的 Stitch 提示词。
- Stitch 页面数量以已确认的完整页面清单为唯一依据，不设固定上下限；清单有几页就生成几页，不得遗漏或自行增加。单次无法完成时可以分批，但最终必须完整覆盖同一清单。
- 用户回传 `$Stitch` / Stitch MCP 信息后，Codex 根据下载下来的 HTML、代码 / 样式 / MD、截图做**实例级视觉规格保真的一比一还原**。
- HTML 是第一事实来源；禁止自由发挥、禁止模仿式重画、禁止把不同按钮 / 图标 / 输入框 / 表格规格抹平成项目默认组件。

## `/goal` 节奏

轻量流程：一条短 `/goal` 连续完成修复、内部测试、复评、已确认验收、问题回写和复测，随后等待用户检查；正式归档由独立 archive 目标执行。

标准流程：一条标准 `/goal` 连续完成模块开发、回归、定向文档、复评、已确认验收、问题回写和复测，随后等待用户检查；正式归档由独立 archive 目标执行。

深度流程：非 UI 固定 2 次，先更新受影响文档、任务/微观任务、追踪和验收准备，再做开发、内测、已确认的真实验收、修复复测和用户检查交接。有 UI 时在中间插入 1 次 UI 目标，总数为 3。

完整流程：非 UI 固定 3 次，依次为完整文档与微观任务、开发与内部测试、真实验收、回写、修复复测与用户检查交接。有 UI 时在文档后插入 1 次 UI 目标，总数为 4。

UI 目标只负责视觉方案、视觉图、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用的 Design QA。等待外部产物时暂停同一 UI 目标，收到输入后继续原目标，不改 N/M。

每次目标都声明基础目标数、第 N/M 次、阶段、UI 决策、UI 路线、等待状态、前置和下一阶段解锁条件。所有 N<M 的中间目标禁止归档；M/M 最后普通目标只做真实验收、回写和修复复测，然后进入待用户检查与待归档确认。

修改后必须重新评分。发现新的公共调用方、跨模块影响或更复杂验证时，要正常加粗显示 `流程已升级` 和 `升级原因`，并按新档位重建剩余阶段，不得把应独立的阶段塞回同一目标。

用户选择自己测试时，Codex 完成内部测试后进入 `待用户验收`，提供测试入口、步骤和期望结果；没有用户明确通过结果时不得标记完成。

本仓库每次可发布变更都必须：

1. 版本号递增 `0.1`

3. 同步 `~/.codex/skills/liran-plan`

5. 如有需要，同步 `~/.codex/prompts/liran-plan.md`
6. 运行相关校验
7. `git commit`
8. `git push`

Codex UI / 前端流程相关变更的必跑校验：

```bash
python3 scripts/check_codex_ui_flow_docs.py
```

四档路由相关变更的必跑校验：

```bash
python3 scripts/check_adaptive_flow_docs.py
```

真机清单结构检查：

```bash
python3 scripts/check_real_test_checklist.py <目标项目>/liran_docs/09-真机实测.md
```

准备标记 `真机测试通过` 前的完成门禁：

```bash
python3 scripts/check_real_test_checklist.py <目标项目>/liran_docs/09-真机实测.md --require-complete
```

最后普通目标交接与真实归档合同检查：

```bash
python3 scripts/check_adaptive_flow_docs.py --prompt-file <真实提示词> --prompt-tier <档位> --archive-stage handoff
python3 scripts/check_adaptive_flow_docs.py --archive-contract-file <归档合同.json>
```

所有中间目标改用 `--archive-stage non-final`，最后普通目标改用 `--archive-stage handoff`；正式归档使用 `--prompt-kind archive`。`final` 只按 handoff 兼容，`full-first` 按 non-final 兼容，不能绕过用户确认。

目标交棒文件可用 `--goal-transition-file <交棒合同.json>` 校验 N/M、阶段顺序和外部等待状态。
