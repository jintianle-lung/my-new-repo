> 这是一份复制用备忘单。4.52 核心：正式 PRD 转换后先评分分级，再生成携带评分和流程等级的目标提示词；轻量/标准各 1 次目标，深度非 UI 2 次、UI 3 次，完整非 UI 3 次、UI 4 次；最后普通目标先交接，用户回复“归档”后才执行独立归档。

> 本清单中的短句、口令和启动句用于触发流程，不是最终完整执行提示词。真正交付给 Codex 或外部 AI 独立执行的成品，必须按 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 结合当前项目展开，不能把下方短句直接当成成品。

> 3.9 起，每条完整目标提示词第一行都要求执行者自行判断是否需要多智能体。启用时只有一个主智能体，任一时刻最多同时五个子代理；子代理完成后必须回收，释放名额后可按需再启用新的子代理，因此五个是并发上限而不是累计上限。子代理不得再派生代理。

用户明确说“全权交给你”、“全程不需要我操作”或同义话时，直接进入全权托管模式：默认 Codex 真机和页面检查，不再显示验收选择框，不提供“我自己测试”，客观无法继续时只标记 `受阻`。

## 4.4 建档与归档怎么用

最后普通目标真实验收和修复复测完成后会立即回收，状态为 goal_status=reclaimed，项目进入待用户检查；这一步不创建归档、不清理活动区。只有用户明确回复“归档”后，才调用独立 archive 目标，archive 不计入普通 N/M；归档失败时保留活动资料和 reclaimed 状态。

用户直接说“修 Bug”“整理需求”“优化/新增/删除功能”“重构/续作/迁移/发布”即可。Codex 会先按用户指定、项目 `AGENTS.md`、`03-索引.md`、既有同类目录/同任务文件定位需求目录，创建或复用任务 Markdown；目录仍不明确时才询问。纯解释、状态查询、只读审查、知识问答或用户明确不让写文件时不会建档。

后续补需求时，Codex 先更新同一任务 ID 的文件，再只告诉你新增、变更、待确认项和路径。M/M 最后普通目标完成验收、回写和复测后先等待你检查；你明确回复“归档”后，独立 archive 目标才更新长期事实、创建并校验单任务归档并清理 `04/08/09/10` 中本任务的过程记录。

## 四档流程怎么用

用户不需要自己算分。把具体任务直接告诉 Codex，它会根据项目现状和修改后影响完成修改前评分，并在回复最前面正常加粗显示当前流程、开始方式和选择原因。

| 得分 | 流程 | 适合情况 |
|---:|---|---|
| `0–35` | 轻量流程 | 独立小 Bug、局部样式、小逻辑 |
| `36–69` | 标准流程 | 单模块多个文件、单页面或简单多模块业务链 |
| `70–89` | 深度流程 | 复杂多模块、共享逻辑、新页面复杂状态、高风险 |
| `90–100` | 完整流程候选 | 新项目、三个或以上独立功能模块、整体架构重构或大规模数据或技术栈迁移 |

直接修 Bug 可以发：

```text
$liran-plan 请修复这个 Bug：<问题现象>。复现方式：<步骤>。当前结果：<错误结果>。期望结果：<正确结果>。请先只读调查项目和调用方，完成修改前评分，正常加粗显示当前流程、开始方式和选择原因，再按对应档位整理需求。request_user_input 可用时实际调用 Codex 原生选择框，不可用时才显示文字编号；我选择后同一轮自动生成一条对应档位的 /goal，并把整条提示词放进一个代码块。
```

用户也可以指定档位：

```text
$liran-plan 我希望按标准流程处理这个任务：<任务>。请先复核评分和安全门禁；如果指定档位不够安全，直接升级并用大白话说明原因。
```

确认框的问题、选项和描述都是纯文本，不用 Markdown 包装。轻量和标准页面任务的一个确认问题是“需求整理得对不对？改完后怎么测试？”，文字回退使用普通段落：

选项一：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，也检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，不检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项三：$liran-plan 需求没问题，改完后我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）
涉及页面的深度流程使用两个 Codex 真机选项和“完成后我自己测试”，不拆成第二个问题。需要重新判断流程时使用选择框自由输入。

Stitch 路线不调用 Product Design Design QA，但不能跳过初次接收检查和强制实例级细节复修；其他明确高保真 Product Design 路线仍不能跳过已触发的页面样式检查。用户选择自己测试后，Codex 只能进入 `待用户验收`，不能直接标记完成。单选框选择已经是正式授权，执行 `/goal` 时不再重复询问是否真机、是否检查页面或使用哪个工具。

Stitch 复修不是只修控件大小，而是完整核对结构布局、尺寸间距、字体排版、颜色样式、控件、图片资源、层级、状态和响应式。固定正文不得删词、删句、删列表项或删章节；项目微调只允许补充或替换项目事实，不适用项仍保留并明确标记。实例级复修提示词也必须保持 3000–10000 个字符，不走普通流程合同；其他原本使用 3000–10000 字符校验的长提示词改为 3000–10000。

选择后不需要再说“请给我提示词”。Codex 立即交付当前阶段目标；深度和完整先跑 documentation，如适用再跑唯一 ui，然后进入开发和最终验收。

任何提示词都不得要求 Codex 编造文件、调用方、接口、测试、截图、真机、归档或完成证据；没有证据时写“未验证”“待确认”“受阻”或“归档受阻”。

## 没有具体任务时的入口

```text
你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。

请直接开始执行下面步骤，先读取对应文档，再输出结果，不要先解释。
$liran-plan
```

或：

```text
/liran-plan
```

只有没有具体任务时，它才会先问六选一：

```text
1. 新项目
2. 老项目新增功能
3. 老项目续作
4. 老项目修复
5. 老项目删除
6. 其他
```

新项目进入完整流程；其他场景先调查评分。只有完整流程默认多轮整理，轻量和标准只整理一次，深度按实际需要整理。


如果你回复“需求整理好了”或“总结好了”，我会读取需求整理文档，重新归纳生成独立正式 PRD、建立 PRD 索引并输出给你确认；你回复“PRD 没问题”后，再用同一个纯文本确认问题确认验收责任和页面检查。确认后立即生成当前 documentation `/goal`；深度后续按非 UI 2 次或 UI 3 次接力，完整后续按非 UI 3 次或 UI 4 次接力，不再把文档、UI、开发和验收压在一条提示词中。

已有项目中途插入 UI 视觉确认时，如果基础文档/功能已存在且用户明确要先看视觉方向图，不要先给 `liran_docs` 回写提示词。先按“文本视觉方案确认 → 用户明确选择生图工具 → 生成视觉方向图 → 用户确认图”的顺序走；视觉图确认后，再回写文档、微观任务、开发追踪和验收标准，并进入 UI 壳接入清单与合法占位文件准备。

第五路线是 `@product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI`：Codex 在当前会话内通过 OpenCodex 本地路由选择实际可用模型生成真实前端 UI 壳，不要求用户把提示词复制到外部软件，也不维护固定模型白名单或新增强制模型选择框。
