# 功能二 · 需求讨论 + 分层文档 SOP

## 目的
站在**产品经理**角度，和用户讨论需求与**产品实用性**（而非一上来就拆开发任务），把讨论结果沉淀为**分层、递归、有索引、互相关联**的文档体系。这是整个技能的主体。

## 4.9 需求整理文档与正式 PRD 生命周期

具体任务首轮必须在 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md` 创建需求整理文档，使用正常聊天式结构；完整用户原话写入 `liran_docs/用户原话.md`，项目事实回写项目、架构或模块文档。需求整理文档状态为“需求整理中”，不使用正式 PRD 的固定章节、REQ/AC、版本号或执行流水。

需求讨论期间每一轮先读取并更新需求整理文档，记录用户补充、修改、确认、否决和待确认内容，再在聊天中回报本轮增量。用户说“需求整理好了”等确认语句后，读取需求整理文档和真实事实，重新归纳生成独立正式 PRD。正式 PRD 转换完成后必须评分并确定流程等级，记录五维分数、总分、评分证据、范围上限、安全门禁和最终档位；用户确认“PRD 没问题”且正式 PRD、任务拆分、微观任务、索引和用户原话检查通过后，才建立执行文档索引、拆任务或生成 /goal。

PRD 只保存需求事实、版本和变更，以及 Goal、模块、04、08、09、10、UI 和归档文件的路径索引；这些执行文件的正文、流水、命令输出和审计日志不得复制进 PRD。

## 4.4 文档先行规则

修 Bug、新增/优化/删除功能、重构、续作、需求整理、UI、API、数据、权限、配置、迁移、部署和发布，从需求整理首轮起都创建或复用上述需求整理文档。纯解释、状态查询、只读审查、知识问答，以及用户明确禁止写文件时不创建。四档都执行，但轻量流程只创建需求整理文档，不生成完整分层文档树。

同一任务只使用一个任务 ID，并写入 PRD、任务拆分、微观任务、开发追踪、测试、真机、UI 清单和归档。路径定位顺序是用户指定、项目 `AGENTS.md`、`03-索引.md`、既有同类目录/同任务文件；仍不明确就询问，绝不乱放。

## 核心纪律
- **PM 视角按档位使用**：完整流程主动讨论产品实用性；深度只讨论会改变跨模块边界的问题；轻量和标准不为形式额外扩张产品讨论。
- **完整分层文档纪律只在完整流程**：完整流程细到模块、子模块和叶子交互独立成文；深度只更新受影响文档，轻量和标准不为几十字的小改机械新建文件。
- **完整文档不是碎文件，是网络**：完整流程中的每个文档都要能通过索引和上下游标注前后追溯、互相关联。

## 四档需求整理深度

功能二不再要求所有任务都创建完整分层文档。先按 [四档自适应流程](四档自适应流程.md) 判断本轮深度：

4.3 起，轻量、标准、深度和完整流程都必须使用各自独立的状态门禁；标准、深度和完整流程的文档准备必须落到真实文件并产生本轮 diff，聊天中的需求摘要不算持久化任务基线。深度流程还必须在编码前完成全部微观任务、开发追踪和验收准备，并通过 `check_adaptive_flow_docs.py` 的运行时产物审计。

| 流程 | 需求整理 | 文档动作 |
|---|---|---|
| 轻量流程 | 一次简短整理，写清 Bug、复现、当前结果、期望结果、边界和验收方式 | 创建或复用一份需求整理文档，不创建完整 `liran_docs`；只有公共行为、已有追踪或长期避坑变化时才定向回写 |
| 标准流程 | 一次模块级整理，写清完整业务链、影响范围、实施步骤和回归点 | 更新已有的开发追踪、受影响模块、测试、API 或数据文档；没有 `liran_docs` 时不强制补整套 |
| 深度流程 | 深入调查跨模块影响，必要时多轮整理，最后输出一次详细需求、边界、影响和验收总结 | documentation 目标只更新受影响文档、全部任务/微观任务、追踪和验收准备；后续目标再开发和验收 |
| 完整流程 | 六类入口、多轮整理、详细总结确认 | documentation 目标创建或补齐完整 `liran_docs` 并一次性拆完全部需求，然后按可选 UI、开发、验收阶段接力 |

轻量和标准不得机械进入完整多轮整理。深度流程可以多轮澄清；需求整理收口与正式 PRD 各完成一次明确确认，验收责任和页面检查在对应选择框集中确认，之后按非 UI 2 次或 UI 3 次的固定阶段节奏执行。

## 分层结构（从宏观到微观，逐层收敛）
1. `00-项目说明书.md` —— 项目是什么、为谁做、解决什么、目标与边界。**源头**。
2. `01-需求文档.md` —— 产品需求总览：功能清单、优先级、用户场景。由说明书推导。
3. `02-架构文档.md` —— 技术架构、技术栈、模块划分、数据流。把需求分配到模块。
4. `03-索引.md` —— 全局导航：模块树 + 横向依赖总表。**单一事实来源**。
5. `modules/` —— 微观实现文档，可无限递归。
6. 扩展：`05-术语表` `06-数据字典` `07-API文档` `08-测试用例`，按项目需要填充。

## 操作步骤
1. **先判断档位，再决定讨论深度**：轻量和标准只做一次必要整理；深度按跨模块影响补足问题；完整流程再做完整 PM 式多轮追问。期间按真实需要留存关键原话（功能一）。
2. **完整流程自顶向下建骨架**：只有完整流程默认先写说明书 → 需求 → 架构，明确一级模块。
3. **实际改结构时更新已有索引**：只有本轮确实修改 `liran_docs` 模块结构，且 `03-索引.md` 已存在或完整流程正在创建时，才先更新索引。
4. **完整流程逐层细化模块**：完整流程在 `modules/模块X/` 下建 `_X.md`，再往下拆子模块和叶子；其它档位只处理受影响的现有文档。
5. **完整流程标注关联**：完整流程中的文档头部写 `上级 / 下级 / 依赖`；深度只维护本轮受影响的既有关联。
6. **校验通顺**：对本轮实际更新的链路做上下游检查，确认逻辑连得上、无断链。
7. **按档位进入 UI 流程**：轻量局部 UI 修复不创建完整 UI 壳；标准单页面或单组件不走完整五路线，状态验证必做，页面样式检查按用户选择执行；深度的新页面、复杂状态、跨页面交互或 UI 与业务联动创建受影响 UI 壳清单，Design QA 按用户选择执行；完整流程才走完整五路线。
8. **需要回退就回退**：如果后面发现方向不对，允许回到前面的任一步重新整理需求、补文档、重做 UI 壳或重拆任务。
9. **文件要写清改动**：无论是新建还是更新 `liran_docs`，都要列出会动到的具体文件，并分别说明每个文件本轮补什么、改什么、删什么、更新什么，不能只写“更新文档体系”。

## 关联关系规范（C 方案）
- **纵向**：模块→子模块→子子模块，无限递归，用目录层级体现。
- **横向**：跨模块的调用/触发，用 `依赖:` 字段 + 索引依赖总表双重记录。
- **中心索引**：`03-索引.md` 为准；文档内标注为辅。两者必须一致。

## 文档头部模板
```
上级：[[父模块文档名]]
下级：[[子文档1]]、[[子文档2]]
依赖：[[其它模块-某流程]]   ← 横向，可空
---
（正文：模块用概述+职责；叶子用 场景/触发/逻辑）
```

## 完成标志
用户能从"项目为什么存在"一路点链接追到"这个按钮点了干嘛"，中间不断链。
