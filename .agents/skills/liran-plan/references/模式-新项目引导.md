# 模式 · 新项目引导式 SOP

## 适用
目标项目是**全新的**（没有或几乎没有代码、文档）。从零开始，按完整流程走一遍。

新项目命中完整流程硬门禁，不仅依赖分数。`90–100` 只是完整流程候选；新项目属于项目级条件，即使总分低于 90 也直接进入完整流程。Codex 仍要完成修改前评分并说明证据，但不得为了分数较低把从零建设降为轻量、标准或深度流程。

新项目流程中供用户直接复制执行的普通 Goal 提示词，必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同；专项提示词继续使用各自完整模板和校验规则。流程触发口令、澄清问题、选择框和进度说明不属于完整提示词。

## 判断是不是新项目
- 目录基本为空，或只有脚手架/README。
- 没有 `liran_docs/` 文档体系。
- 用户描述的是"我想做一个……"而非"我这个项目……"。

## 引导流程（按序）
1. **任务文档与多轮需求整理**：先在项目指定目录创建聊天式需求整理文档并分配任务 ID，再按六选一入口进入需求整理；用户未说“需求整理好了/总结好了”前，不写代码、不拆任务、不开 `/goal`。如果目录还不能从用户指定、`AGENTS.md`、`03-索引.md` 或既有同类目录确定，先询问路径，禁止乱放。
   - 每轮先更新需求整理文档，再只回复新增、变更、待确认点和真实路径，末尾问“整理好了吗，还需要补充吗？”；用户要求全文或进入集中确认时才输出完整总结。
   - 用户说“需求整理好了/总结好了”后，读取需求整理文档重新归纳生成独立正式 PRD、建立 PRD 索引并在对话输出，等待用户回复“PRD 没问题”；确认后在同一个纯文本选择问题里让用户选择 `$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）` 或 `$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`，然后才进入 `liran_docs` 一次性补齐流程。
   - 保留这句口令：`[$liran-plan](../SKILL.md) 整理好了或者需求整理好了或者总结好了`。用户说出这句或等价表达时，都视为进入总结确认阶段。
2. **建文档骨架**：在项目根创建 `liran_docs/`，先放入 `用户原话.md`。
3. **功能一·原话留存**：开场即开始记录，并贯穿全程。
4. **功能二 + 功能五（合并为一步）：需求讨论 + 分层文档 + 一次性拆完全部任务**：
   - 以 PM 视角追问目标/用户/场景/实用性。
   - 自顶向下：项目说明书 → 需求文档 → 架构文档 → 索引 → 递归模块树 → `04-开发追踪.md`。
   - 在 documentation 目标里把全部已确认需求一次性拆成可执行的微观任务，不分批、不留尾巴。文档和微观任务没有补齐前，不解锁 UI 或开发目标。
5. **功能三·真实前端 UI 壳五路线**：文档和微观任务一次性补齐后，再判断是否需要 UI / 前端设计流程；只要涉及页面、表单、列表、弹窗、按钮、状态切换、空态/加载态/错误态、流程页、设置页、UI 优化、前端重构、深度美化、响应式优化或交互优化，就进入真实前端 UI 壳五路线；纯后端、纯修复、纯删除、纯配置、纯文档且不涉及页面或交互变化时，直接跳过并说明原因。
   - 默认产物是真实前端 UI 壳，不是独立 HTML 或 demo。UI 壳必须严格根据确认好的文本视觉方案，或“文本视觉方案 + 视觉图 / 原型图”创建。
   - 五条路线为：`Codex 直接生成前端 UI 壳`、`@product-design`、`@product-design + 外部 AI 生成前端 UI`、`@product-design + $Stitch / Stitch MCP`、`@product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI`。第五路线由 `@product-design` 先确认文本视觉方案，再由 Codex 通过 OpenCodex 本地路由在当前会话内选择 Gemini 或其他实际可用模型生成 UI 壳；不复制提示词到外部软件、不维护固定模型白名单、不新增强制模型选择框，并继续执行 UI 壳接入清单、文件白名单、样式隔离、接收检查和非 Stitch Design QA。
   - 造壳前 Codex 必须先生成 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md`，规划文件、创建合法占位文件、安排正式入口或临时预览入口、准备 mock/type/局部样式/注释锚点，并写清允许编辑文件清单。
   - 外部 AI 只在 Codex 指定文件里生成 UI 壳，不得自行新增、删除、移动、重命名文件，不得新增依赖、重写全局样式、替换 UI 库、接真实接口或补业务逻辑；如果文件不够，必须停下来让用户回 Codex 补文件。
   - 如果走 Stitch 路线，必须按 `实例级尺寸保真规则` 承接真实前端：先追问“视觉方案确认好了吗？”，确认后生成 Stitch 提示词；拿到 `$Stitch` / Stitch MCP 信息后，先更新接入清单和合法占位文件，再下载 Stitch 原始产物。开始真实前端承接前，必须先做 `控件规格盘点`，并按事实来源优先级读取：第一事实来源是 Stitch 下载下来的 HTML，第二事实来源是 Stitch 下载下来的代码 / 样式 / MD 规范，第三事实来源才是截图。真实落地时禁止把不同按钮、图标、输入控件、表格规格统一掉，禁止先组件化再凭感觉回调视觉，禁止被老项目默认 Button / Input / Icon / Table 规格和全局样式带偏。
   - Stitch 初次接收后的固定复修必须覆盖完整视觉维度：结构布局、尺寸间距、字体排版、颜色样式、控件规格、图片资源、层级组合、状态和响应式。项目微调只能补充或替换事实，不得删除固定正文；不适用元素仍保留规则并标记。实例级复修提示词也必须保持 3000–10000 个字符，也不走普通流程合同。
   - UI 壳里的预留接口、状态、事件、mock 和类型入口必须严格根据 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md` 创建，建议使用 `TODO(ui-shell)`、`TODO(codex-connect)`、`TODO(codex-state)`、`TODO(codex-permission)`、`TODO(codex-validate)`、`TODO(codex-route)`。
   - 样式默认只能在当前 UI 壳范围内生效，不能污染老页面或全局样式。
   - 如果是非 Stitch Product Design 路线且有真实图片或视觉方向图，最终真实前端 UI 壳截图必须达到 90% 以上高还原；布局主要结构、样式、配色、字体字号、间距、层级和状态要贴近原图；按钮、输入框、输出框/结果区、表单、表格、列表、卡片、导航、菜单、弹窗、图标、图片、提示、加载/空/错误状态和交互状态等所有可见前端元素都要纳入 QA。QA 不能挤牙膏：每轮先批量差异盘点，按 P0/P1/P2/P3 分级，优先批量修 P0 + P1 并尽量合并处理 P2，不能只改一个问题就重新 QA；Product Design 路线必须更新 design-qa.md，只有没有 actionable P0/P1/P2 才能 passed。Stitch 路线不执行 Product Design Design QA；初次接收后必须自动交付固定实例级细节复修提示词，复修通过后才允许进入业务接线。
   - UI 壳完成后 Codex 必须先做接收检查；不通过时留在同一 UI 目标修复，不解锁 development。
   - 如果设计方案、视觉图或 UI 壳带来了需求、交互、页面结构或状态修订，回到文档体系和微观任务做补充或修订（这是修订，不是重新一次性拆分）。
6. **development 目标：内部闭环**：只有 documentation 和适用的 ui 目标通过后才能开始，只做内部开发、真实业务接线、内部验证和必要修复，最多推进到 `内部测试通过`，禁止归档。
7. **acceptance 目标：按验收责任收口并交接**：Codex 真机分支使用 `liran_docs/09-真机实测.md` 真实操作；用户自测分支准备真实入口并进入 `待用户验收`。验收通过后完成回写、修复和复测，进入 `待用户检查 → 待归档确认`；用户回复“归档”后才启动独立正式归档并进入 `已归档 → 已完成`。

## 节奏纪律
- 每一步产出后先自检，再继续下一步；只有硬性阻塞或关键信息缺口时才停下来让用户介入，避免一路狂奔跑偏。
- 全程持续记录原话。
- 没有内部验证、没有完成已确认的验收责任或没有完成安全归档时，不要把模块标记为 `已完成`。Codex 真机分支必须达到 `真机测试通过`；用户自己测试分支必须收到用户明确反馈并达到 `用户验收通过`；两条分支都必须再达到 `已归档`。
- 用户可随时打断、回退或单独调用某功能，但不得跳过安全、需求总结确认、已触发的 Product Design Design QA、Stitch 强制实例级细节复修和最终验收门禁。
- 如果后面发现方向不对，可以回到前面的任一步重新整理需求、补文档、重做 UI 壳或重拆任务。
