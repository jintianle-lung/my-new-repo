# 四档自适应流程 SOP

## 目的

让 `liran-plan` 根据项目实际情况选择轻量流程、标准流程、深度流程或完整流程，并按 4.6 固定阶段矩阵生成 `/goal`。

## 入口规则

1. 用户只输入 `$liran-plan` 或 `/liran-plan`，且没有具体任务时，继续显示六类场景。
2. 用户已经给出具体 Bug、功能、删除、迁移、发布或文档任务时，先做最小必要的只读调查，再直接评分分档。
3. 六类场景和四档流程分离。新项目默认完整流程；老项目新增、续作、修复、删除和其他任务按证据评分。
4. 用户可以指定流程。没有命中安全门禁时，采用用户指定档位；命中安全门禁时，最低升级到门禁要求的档位。
5. 信息不足时，只询问完成评分所需的最少问题。

## 四档定义

| 得分 | 流程 | 用户操作 | 默认执行边界 |
|---:|---|---|---|
| 0–35 | 轻量流程 | 一次简短整理、一个 Codex 单选框、一个短 `/goal` | 一个明确问题 |
| 36–69 | 标准流程 | 一次模块整理、一个 Codex 单选框、一个标准 `/goal` | 一个模块或简单多模块业务链 |
| 70–89 | 深度流程 | 必要多轮整理、一个 Codex 单选框、非 UI 2 次或 UI 3 次 `/goal` | 复杂多模块、跨层或高风险局部工作 |
| 90–100 | 完整流程候选 | 完整规划、完整文档、非 UI 3 次或 UI 4 次 `/goal` | 项目级工作 |

`90–100` 只是完整流程候选，还必须同时满足项目级语义条件。高风险但范围明确的单项任务采用深度流程，不机械重建整个项目体系。简单多模块改造默认仍采用标准流程，只有复杂多模块改造才进入深度流程。

## 4.3 运行时阶段门禁（不是说明性文字）

每条完整 `/goal` 必须在正文开头保存可恢复的 `## 流程合同`：流程档位、修改前评分、基础目标数、目标总数、当前第 N/M 次、目标阶段、UI 决策、UI 路线、等待外部输入状态、验收责任、进入证据、阶段职责、禁止后续阶段和下一目标解锁条件。UI 已启用但尚未选路线时，只有 documentation 目标可临时写 `pending`；进入 ui 前必须锁定 canonical 路线，不得靠调用方临时猜是否 Stitch。恢复时 N/M、阶段、UI 决策、UI 路线和验收责任均不得无证据漂移。

编码前门禁必须验证真实文件产物：提示词出现“已更新”不算证据，必须确认文件存在、内容非占位、相应文件产生真实 diff，并且任务编号、影响文件、依赖、测试和完成条件完整。门禁未通过前，禁止编辑实现源码。运行时校验器可用以下入口执行并以非零退出码阻止交付：`python3 scripts/check_adaptive_flow_docs.py --prompt-file <真实提示词> --prompt-tier <light|standard|deep|full-docs>`；标准、深度和完整阶段还应配合 `--artifact-file` 与 `--changed-file` 做产物审计。

四档目标节奏固定为：

- 轻量：依赖扫描完成 → 失败测试已确认 RED → 编码解锁 → 内部验证 → 按已确认验收责任 → 修改后评分。
- 标准：持久化模块任务清单 → 受影响文档真实 diff → 编码解锁 → TDD 实现 → 内部验证回写 → 按已确认验收责任 → 验收结果再次回写 → 修改后评分。
- 深度非 UI 固定 2 次：documentation → development-and-acceptance。
- 深度 UI 固定 3 次：documentation → ui → development-and-acceptance。
- 完整非 UI 固定 3 次：documentation → development → acceptance。
- 完整 UI 固定 4 次：documentation → ui → development → acceptance。

UI 目标只插入一次，负责视觉方案、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用的 Design QA，禁止接真实 API、权限、状态和表单。等待外部输入时暂停原 UI 目标，收到输入后继续原目标，不改第 N/M 次。

任何执行者都不得把聊天中的任务列表、读取过的文档或“最后统一补文档”当成前置产物。

全流程唯一顺序：需求整理文档 → 正常聊天整理 → 用户确认整理完成 → 正式 PRD → PRD 确认 → 可选 UI 壳 → 内部开发 → 真机实测 → 问题回写 → 修复复测 → 安全归档。

需求整理收口采用两次明确确认：先询问“需求整理好了吗？整理好了的话，请回复‘需求整理好了’”；收到口令后读取需求整理文档，重新归纳生成独立正式 PRD，建立 PRD 索引，在对话中输出正式 PRD 供用户核对，再询问“正式 PRD 没问题吗？没问题的话，请回复‘PRD 没问题’”。用户未确认前不得生成 Goal 或进入 UI/开发。所有需要选择的节点（需求/验收责任、页面样式、UI 路线、外部输入、Codex 真机测试或用户自测）必须提供纯文本选项；选项不可用时停留当前阶段。

## 4.10 需求整理文档、正式 PRD 与归档门禁

本节延续 4.9 需求整理文档、正式 PRD 与归档门禁，并只在本版本补充四档评分与多模块路由规则。

具体项目修改任务在需求整理首轮创建或复用 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`；用户确认整理完成后再生成同任务的独立 `*-PRD.md`。纯解释、状态查询、只读审查、知识问答和用户明确禁止写文件时不创建。四档都执行，轻量只建需求整理文档，不扩张为完整文档树。目录按“用户指定 → `AGENTS.md` → `03-索引.md` → 既有同类目录/同任务文件”定位，不明确就询问，禁止猜测。

需求讨论期间每轮先更新需求整理文档，再回复增量回执；用户说“需求整理好了”等确认语句后，读取整理文档和真实事实，重新归纳生成正式 PRD 1.0，并只建立 Goal、模块/微观任务、04、08、09、10 和归档路径索引。PRD 不复制这些文件的正文、流水、命令输出或审计日志。统一任务 ID 贯穿需求整理文档、正式 PRD、任务拆分、微观任务、`04`、`08`、`09`、UI 清单和归档。

最后普通目标完成最终验收、问题回写和复测后，先进入 `待用户检查 → 待归档确认`，并固定通知用户检查软件；任一步普通目标都不自动归档。只有用户明确回复“归档”后，才按“更新长期事实 → 创建归档 → 校验内容和证据路径 → 更新归档索引 → 按任务 ID 清理活动区 → 检查其他活动任务未受影响”执行。任一步失败都保留原文并进入 `归档受阻`。

只有最后目标负责最终验收交接。

## 四档独立状态序列

四档流程共享“需求整理 → 详细总结确认 → 集中确认 → 提示词校验”的入口门禁，但编码前后的状态序列彼此独立，不能用较弱档位的状态覆盖较强档位：

- 轻量：`未开始 → 只读调查中 → 修改前评分已完成 → 需求整理中 → 待详细总结确认 → 正式 PRD 待确认 → 待集中确认 → 提示词生成中 → 提示词待校验 → 提示词已解锁 → 编码已解锁 → 开发中 → 内部测试通过 → 验收准备中 → 待实测或待用户验收 → 修改后复评中 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`。
- 标准：在上述确认链后增加 `持久化任务清单已完成 → 受影响文档真实 diff 已完成`，然后才能到 `编码已解锁`；验收后增加 `回写中 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`。
- 深度：在上述确认链后依次经过 `文档准备中 → 任务拆分中 → 开发追踪已更新 → 验收准备中`，然后才能到 `编码已解锁`；验收阶段必须经过 `待实测或待用户验收 → 回写中 → 修改后复评中 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`。
- 完整：在确认链后依次经过 documentation，适用时插入 ui，再进入 development 和 acceptance。文档、UI 和开发中间目标均禁止归档；acceptance 经过真实验收、回写、修改后复评后进入 `待用户检查 → 待归档确认`，用户明确回复“归档”后才进入 `归档中 → 已归档 → 已完成`。

每次转换都必须记录 `当前状态`、`进入证据`、`已完成门禁`、`待完成门禁`、`允许下一动作`、`禁止动作` 和证据；进入 `受阻` 时还必须记录具体阻塞原因。状态事件必须与目标状态匹配，不能只改文字。用户说“需求整理好了/总结好了”只能进入 `待详细总结确认`；同一条消息不能同时伪造详细总结输出和用户确认。

## 流程合同与档位执行门禁的落地要求

运行时提示词必须在 `## 流程合同` 中保存档位和阶段字段，并在 `## 档位执行门禁` 中列出顺序。真实文件产物与真实 diff 未审计前禁止编辑实现源码。状态转换用 `--state-transition-file`，目标交棒用 `--goal-transition-file`，两者都必须保留 N/M 和进入证据。

## 修改前评分

评分前先读取项目规则、相关代码、测试、文档和 Git 状态，搜索调用方并推演修改后影响。五个维度各 `0–20` 分，总分 `100` 分；尚未调查的维度标记为“待调查，不计入最终评分”。

| 维度 | 0–4 分 | 5–8 分 | 9–14 分 | 15–20 分 |
|---|---|---|---|---|
| 项目现状 | 入口、调用方、测试和文档清楚 | 局部信息缺失但边界可确认 | 多处事实冲突，需要额外调查 | 状态混乱、根因入口不清或依据不可信 |
| 修改规模 | 单文件或单点局部修改 | 单模块局部或小功能 | 简单多模块协同修改 | 复杂多模块、跨层或项目级改造 |
| 依赖影响 | 私有实现、无外部影响 | 一个或少量明确调用方 | 有限调用链且影响可列出 | 公共能力、多个消费者、共享状态、公共协议或影响未知 |
| 风险回滚 | 容易撤销且无持久化影响 | 有限状态、兼容、缓存或配置影响 | 异步、第三方、数据一致性或回滚复杂 | 数据删除/迁移、认证、权限、密钥、支付、生产或不可逆 |
| 验证复杂度 | 一个定向测试即可验证 | 模块测试加有限回归 | 多模块集成、异步或多状态验证 | 真实环境、多设备、真机、复杂回归或用户验收 |

评分纪律：

- 每个维度取命中的最高分，不取平均。
- 已确认没有影响才可以打 `0`。
- 尚未查清时标记为“待调查，不计入最终评分”，不能直接计入最高风险。
- 调查后仍无法确认关键影响时，采用保守高分并明确证据不足。
- 关键影响未知时，不能只因总分仍在 `0–35` 就进入轻量流程。先显示“暂未确定”并继续最小调查；执行前仍无法查清时，最低按深度流程处理。
- 每项评分必须附代码、引用、测试、文档或 Git 证据。
- 文件数量只能作为辅助证据。
- 不得因为只改一行就降低依赖影响。
- 不得先决定档位再编造评分理由。
- 同时符合两个档位时选择更高档位，但范围上限仍然生效；简单多模块不能仅因模块数量进入深度流程。
- 评分只是解释工具，安全门禁始终优先。

## 档位资格与硬门禁

轻量流程：总分 `0–35`，且没有命中最低深度或完整流程硬门禁。

标准流程：总分 `36–69`，且没有命中最低深度或完整流程硬门禁。老项目单模块改造和简单多模块改造默认属于标准流程。

深度流程：总分 `70–89`，或命中最低深度流程硬门禁。复杂多模块改造、跨层改造、共享逻辑和高风险局部任务属于深度流程。

`90–100` 先标记为完整流程候选。只有同时满足项目级完整流程条件时才进入完整流程；如果只是高风险但范围明确的单项任务，不重建整个项目体系，按深度流程执行。新项目或项目级改造即使总分未达到 90，也可以直接进入完整流程。

以下任务最低进入深度流程：

- 数据删除、数据库迁移和批量数据修改。
- 登录、认证、权限、密钥和支付。
- 生产环境操作和难以回滚的发布。
- 公共 API、共享数据结构和核心共享逻辑修改。
- 复杂多模块、跨前后端数据库、公共协议、共享核心逻辑或多个独立业务链改造。
- Stitch、高保真还原和新 UI 壳。

以下任务进入完整流程：

- 新项目。
- 同时新增三个或以上独立功能模块。
- 整体架构重构。
- 大规模数据或技术栈迁移。
- 多个大型模块同时改造。
- 项目代码、文档和真实进度严重混乱。
- 用户明确要求完整流程。

任务范围上限：

- 老项目单文件局部修改最高轻量流程。
- 老项目单模块改造最高标准流程。
- 老项目简单多模块改造最高标准流程。
- 老项目复杂多模块改造最高深度流程。
- 新项目或项目级改造允许完整流程。

简单多模块必须同时满足：涉及不超过三个相关模块、接口基本不变、不修改公共数据结构、不新增复杂跨模块状态、不涉及高风险操作、不涉及多个独立业务链，并且可以通过有限集成测试完成验证。否则按复杂多模块或安全门禁重新评估。

### 小任务档位上限

| 任务范围 | 默认最高档位 | 说明 |
|---|---|---|
| 老项目单文件局部修改 | 轻量流程 | 不因分数或安全门禁以外的形式要求进入完整流程 |
| 老项目单模块小功能 | 标准流程 | 可修改同模块关联文件，但不重建项目级文档体系 |
| 老项目单模块完整改造 | 标准流程 | 影响扩大或验证复杂时升级到深度流程 |
| 跨模块功能、新 UI 壳、高保真还原 | 深度流程 | 需要跨模块调查、回归或 UI 接收门禁，但不自动进入完整流程 |
| 新项目、项目级改造 | 完整流程 | 命中项目级硬门槛后才进入完整流程 |

## 显式宣布当前流程

评分完成后，回复最前面必须直接使用正常 Markdown 加粗文本。禁止把关键状态放进三反引号代码块、`text` 复制框或 Markdown 源码展示。

**当前流程：标准流程（40/100）**

**开始方式：按照标准流程，先整理当前模块和影响范围，确认后生成一条标准 /goal 提示词。**

**选择原因：修改集中在一个模块，但涉及多个关联文件；影响范围可以确认，不涉及公共协议和高风险数据。**

要求：

- 当前流程、开始方式、选择原因都加粗。
- 原因只说最重要的两到三个，使用大白话。
- 用户指定流程时写明“用户指定”和 Codex 复核评分。
- 信息不足时显示：**当前流程：暂未确定，Codex 正在调查项目和修改影响**

## 轻量流程

流程：最小调查和依赖扫描 → 整理 Bug、复现、期望、边界和评分 → 显式宣布 → 一个 Codex 单选框 → 一条轻量 `/goal` → 修复、内部测试、diff、复评和验收。

规则：

- 不进行多轮需求整理。
- 需求整理首轮创建或复用一份聊天式需求整理文档，但不创建完整 `liran_docs`。
- 不创建完整 `liran_docs`。
- 不单独拆微观任务。
- 页面任务只处理已有页面中的局部样式修复、小交互或单一状态 patch；一旦需要整页或整组件调整，至少进入标准流程。
- 必须完成相关内部测试和最终 diff 检查。
- 只有公共行为、已有追踪或长期避坑变化时才定向回写。
- 没有真实硬性阻塞时，一个 `/goal` 连续完成。

## 标准流程

流程：调查相关模块和完整业务链 → 整理需求、影响、边界和实施步骤 → 显式宣布 → 一个 Codex 单选框 → 一条标准 `/goal` → 开发、回归、定向文档、复评和验收。

规则：

- 适用于一个模块或一条有限业务链。
- 可以修改多个关联文件。
- 页面任务可以做整页或整组件调整，但不走完整 UI 壳五路线；新页面、复杂状态、跨页面交互或 UI 与业务联动至少升级到深度流程。
- 一次 `/goal` 必须能够安全闭环。
- 更新已有的开发追踪、受影响模块、测试、API 或数据文档。
- 项目没有 `liran_docs` 时不强制创建完整体系。
- 仍要在已定位的指定目录创建或复用本任务需求整理文档。
- 覆盖正常路径、失败路径和主要回归路径。
- 无法一次安全闭环时升级为深度流程。

## 深度流程

深度非 UI 固定 2 次：documentation 1/2 只更新受影响文档、全部任务/微观任务、开发追踪和验收准备；development-and-acceptance 2/2 再做系统化调试、TDD 实现、内部测试、已确认的真实验收、回写和修复复测，然后等待用户检查与归档确认。

深度 UI 固定 3 次：documentation 1/3 → ui 2/3 → development-and-acceptance 3/3。用户明确不需要 UI 时跳过 ui，回到非 UI 的 2 次节奏。

深度流程中的 UI 壳与 Stitch 必须使用独立 UI 目标。该目标只做视觉方案、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用的 Design QA，不接真实业务。如缺外部产物，标记等待并暂停同一 UI 目标；收到 Project ID / Screen ID 后继续原目标，不新增目标或改变 2/3。

Stitch 初次接收检查只允许得出 `可以进入实例级细节复修` 或 `初次承接受阻`。前者必须立即自动交付 `templates/Stitch-实例级细节复修提示词.md`；后者只记录阻塞证据，不得进入业务接线。复修通过后完成当前 UI 目标，再解锁后续 development 或 development-and-acceptance 目标做业务实现。全权托管可以自动执行这条固定提示词，但不能跳过等价门禁。

## 完整流程

完整非 UI 固定 3 次：documentation 1/3 生成完整 `liran_docs` 并拆完全部微观任务；development 2/3 完成开发和内测；acceptance 3/3 按已确认验收责任做真实验收、回写和修复复测，然后等待用户检查与归档确认。

完整 UI 固定 4 次：documentation 1/4 → ui 2/4 → development 3/4 → acceptance 4/4。完整流程默认保留 UI 目标；只有客观不涉及 UI 或用户明确跳过 UI 时才使用 3 次非 UI 节奏。

不得削弱 Stitch 初次接收检查、强制实例级细节复修、真机清单和完成门禁；其他 Product Design 路线仍保留 Design QA。

## 一个问题的 Codex 单选框

一个流程确认只能显示一个问题。不得拆成“需求是否确认”和“怎么测试”两个问题。选项不得出现“推荐”；用户可见文字使用大白话；`Codex` 代表执行任务的 AI，`我` 代表当前用户。

当前环境提供 `request_user_input` 时必须实际调用。问题、选项标签和描述必须是纯文本，不得用 Markdown 标题、加粗、反引号、代码块、链接或列表符号包裹。工具不可用时，使用“选项一：……”纯文本普通段落回退。用户选择后，Codex 必须在收到选择结果后的同一轮自动生成当前阶段的完整 `/goal` 提示词，不得等待用户再说“请给我提示词”“继续”或同义口令。

UI 五路线是单独的路由选择：原生工具每题只支持 2–3 项，因此使用 3+3 两步选择。第一步显示 Codex 直接、@product-design、继续选择外部/Studio 路线；只有选第三项才显示外部 AI、Stitch、Codex 内嵌模型。“继续选择”只导航、不生成 `/goal`；原生工具不可用时才一次显示五个纯文本段落。

生成的可复制 `/goal` 必须完整放在一个独立的 Markdown 代码块中；代码块外只保留一句必要引导，代码块内部不得嵌套三反引号，也不得把一条提示词拆成多个代码块。正常加粗的流程状态仍放在代码块外。

上述可复制普通 `/goal` 必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同：写清任务 ID、流程档位、目标 N/M、当前阶段、读取文件、修改边界、验证、状态回写、完成条件和下一阶段解锁条件。普通 Goal 不设 3000 字最低门槛，也不复制 PRD 或执行文档正文。Stitch、外部 AI、Product Design 和生图等专项提示词继续使用各自完整结构、长度和固定正文校验；专项完整提示词仍覆盖十一项标准结构。

完整 `/goal` 的第一行必须是固定多智能体判断句。主智能体自行判断是否启用协作；启用时仅一个主智能体统筹，任一时刻最多同时五个子代理。子代理完成、失败或不再需要时必须回收，回收后可按需启用新的子代理，所以五个是并发上限而不是累计上限。子代理不得继续派生代理。

## 页面检查与验收责任

- “Codex 自己真机测试”：Codex 负责真实入口、真实状态和真实操作验证。
- “也检查页面样式是否符合方案”：执行正式 Design QA。
- “不检查页面样式是否符合方案”：仍验证功能、状态、错误和交互，但不做视觉方案对比，不声明视觉还原通过。
- “我自己测试”：Codex 完成内部测试后转为 `待用户验收`。

## 状态机

Codex 测试分支：

`待开发 → 进行中 → 内部测试通过 → 待实测 → 真机测试通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

用户测试分支：

`待开发 → 进行中 → 内部测试通过 → 待用户验收 → 用户验收通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

用户选择自己测试后，Codex 不得直接标记 `已完成`。

## 修改后评分与自动升级

修改完成后必须检查真实 diff、重新搜索调用方、检查公共行为变化、读取测试结果并重新评分。

没有升级时直接显示：

**修改后评分：40/100，继续按照标准流程收口。**

**没有升级的原因：实际修改仍限制在当前模块；没有发现新的公共调用方；现有测试覆盖了受影响路径。**

升级时直接显示：

**流程已升级：标准流程 → 深度流程（40/100 → 70/100）**

**升级原因：修改过程中发现该逻辑被多个模块共同调用，并且需要跨模块回归和真机测试。**

**接下来按照深度流程继续：补充受影响文档和任务，完成跨模块测试，并按已确认验收责任执行 Codex 真机闭环或进入待用户验收。**

升级规则：

- 关键状态使用正常 Markdown 加粗文本，禁止代码块。
- 原因使用大白话，只写最关键的两到三个。
- 轻量或标准升级到深度且仍在确认范围内时，Codex 自动继续并补足深度要求。
- 不要求用户重新复制提示词。
- 升级到完整流程说明已经出现项目级范围，不能在原轻量、标准或深度目标里静默扩大。先完成当前可以安全收口的部分，再正常加粗显示升级原因，并切回完整流程需求确认。
- 超出已确认需求范围时重新找用户。
- 删除数据、不可逆操作、账号权限和需求冲突必须停下确认。
- 修改后评分降低时不进行形式化降级，不撤销已触发的安全检查。

## 事实证据与禁止幻觉

- 不得伪造已经读取的文件、搜索到的调用方、执行过的命令、测试通过结果、页面截图、真机操作、用户反馈或完成状态。
- 不得伪造测试通过，不得伪造真机操作；计划执行和实际执行必须明确区分。
- 评分证据必须来自当前实际读取、搜索或验证结果；没有证据时写“未验证”“待确认”或“受阻”。
- 不得把计划运行的测试写成已经通过，不得把结构校验写成真实操作，不得把用户尚未反馈的验收写成通过。
- 页面和真机结论必须能对应真实入口、真实操作和真实结果；无法打开或无法操作时如实记录限制。

## 统一 `/goal` 合同

轻量、标准和深度普通目标提示词都必须先满足文件指针型短合同，再包含当前阶段真正需要的动作、验证、回写和收口条件；不复制完整需求正文。专项提示词仍按各自完整结构和长度规则校验，不得因为普通 Goal 缩短而删减专项内容。

## 最终报告合同

最终回复中的关键状态继续使用正常 Markdown 加粗文本，不放进代码块：

**最终流程：深度流程**

- 修改前评分：40/100
- 修改后评分：70/100
- 流程变化：标准流程升级为深度流程
- 升级原因：发现多个公共调用方
- 修改内容：说明实际改动文件和行为
- 内部测试：列出真实运行的命令和结果
- 真机测试：已执行 / 按用户选择未执行 / 受阻
- 页面样式检查：已执行 / 按用户选择未执行 / 不涉及页面
- 文档回写：列出更新的文档、追踪和避坑记录
- 归档状态：未开始 / 归档中 / 已归档 / 归档受阻 / 已取消 / 暂停归档 / 被新任务替代
- 真实归档路径：列出任务归档位置；未归档时写明原因
- 最终状态：已完成 / 待用户验收 / 受阻 / 归档受阻

## 压力场景

以下场景是确定性回归清单，修改本技能时不得删除：

- `S01-独立小Bug进入轻量流程`：独立判断、单一调用方、定向测试可验证，必须为轻量。
- `S02-单模块多文件进入标准流程`：同一模块多个文件、影响有限，必须为标准。
- `S03-一行共享逻辑进入深度流程`：代码只改一行但有多个公共调用方，必须为深度。
- `S04-新项目进入完整流程`：没有实质代码和文档的新项目，必须为完整。
- `S05-未知依赖不能打零分`：未查清调用方时依赖影响至少为 1，关键未知为 2。
- `S06-低档位命中门禁自动升级`：用户指定轻量但涉及权限或数据迁移，必须升级。
- `S07-修改后发现调用方自动升级`：标准执行中发现共享调用方，必须显式升级到深度并继续。
- `S08-用户自测进入待用户验收`：用户选择自己测试时不得标完成。
- `S09-UI小修不创建完整UI壳`：局部样式或小交互修复不进入完整五路线。
- `S10-单页面调整进入标准流程`：单页面/组件且影响有限，进入标准。
- `S11-新页面复杂状态进入深度流程`：新页面、复杂状态或 UI 与业务联动进入深度。
- `S12-真机测试但不检查页面样式`：仍做功能真机，不生成视觉通过结论。
- `S13-Stitch不得跳过细节复修`：Stitch 必须经过初次接收检查和强制实例级细节复修；其他明确高保真 Product Design 工作仍按规则执行 Design QA。
- `S14-关键状态使用正常加粗文本`：当前流程、开始方式、选择原因、升级原因不得进入代码块。
- `S15-选择框不用推荐且使用Codex和我`：用户选项不出现“推荐”，主体使用 `Codex` 和 `我`。
- `S16-深度文档目标解锁开发目标`：文档、微观任务、追踪和验收准备真实通过后才解锁开发。
- `S17-完整流程纪律不得覆盖轻量标准`：完整文档树和 3/4 次分阶段目标只作用于完整流程。
- `S18-深度页面允许用户自己测试`：深度页面选择框必须保留用户自己测试分支。
- `S19-深度Stitch使用独立UI目标`：Stitch 不与文档或业务接线混在同一阶段。
- `S20-完整非UI任务不依赖UI壳`：完整流程非 UI 任务以架构、API、数据和测试文档为基线。
- `S21-事实证据不得靠幻觉补齐`：读取、调用方、测试、截图、真机和用户反馈都必须有真实证据。
- `S22-升级到完整流程必须切回确认`：项目级扩张不能在原目标中静默继续。
- `S23-局部样式与整页调整边界明确`：轻量只做局部 patch，整页或整组件至少进入标准流程。
- `S24-完整流程最后目标按验收责任分支`：acceptance 目标同时支持 Codex 真机和用户自己测试。
- `S25-深度UI只执行已触发QA`：深度页面选择不检查样式或用户自测且未命中强制 QA 时，不得被下游执行句重新强制 Design QA。
- `S26-完整流程总结一次确认验收责任`：完整流程必须在详细总结的同一个确认问题里选定 Codex 真机或用户自己测试，不得拖到最后目标前再问。
- `S27-顶层核心原则不得强制完整整理`：顶层原则中的每轮完整需求总结必须限定在完整流程需求整理阶段。
- `S28-其他入口不得强制多轮整理`：发布、部署、文档和技能规则等“其他”任务先评分，再按当前档位选择整理深度。
- `S29-原生选择框可用时必须实际调用`：存在 `request_user_input` 时必须调用工具，工具不可用时才退回文字编号。
- `S30-选择后同轮自动交付提示词`：用户点击或发送选项后立即生成对应 `/goal`，不得再等一句“请给我提示词”。
- `S31-提示词使用单一完整代码块`：整条可复制提示词只放一个外层代码块，内部不嵌套三反引号。
- `S32-深度两阶段职责不混用`：documentation 不编码，development-and-acceptance 不重做需求拆分。
- `S33-Chrome无法操作时自动切换电脑`：需要真实 Chrome 状态时优先 `@Chrome`；无法完成时必须自动切换 `@电脑` 继续，不得把可执行操作交给用户。
- `S34-全权托管跳过确认与用户交接`：用户明确全权授权后，默认 Codex 验收，不显示验收选择框，不提供用户自测分支，客观阻塞只记录而不转交操作。
- `S35-明确用户自测覆盖托管默认`：用户明确选择“我自己测试”时，以用户自测为准，不得因为全权托管默认改为 Codex 真机测试。
- `S36-真实提示词交付前必须运行时校验`：每条实际生成的完整提示词都必须通过 `--prompt-file` 运行时校验，失败不得交付。
- `S37-深度编码前必须审计真实产物与diff`：文档、任务、追踪和验收准备必须存在、非占位并出现在真实 diff 中，未通过不得编辑源码。
- `S38-上下文恢复不得无证据改变档位`：`FlowContract` 恢复后没有修改后评分和新证据不得升级、改变目标次数或验收责任。
- `S39-立即生成提示词选项必须来自canonical builder`：原生选择框和文字回退使用同一选项集合，临时包装或裸选项必须失败。
- `S40-具体修改首轮创建任务文档`：四档修改任务都创建或复用单份需求工作 Markdown，轻量不得扩张完整文档树。

### 4.11 最后普通目标回收合同

最后普通目标完成真实验收、问题回写、修复复测和修改后评分后，必须按 goal_status=active → reclaim_pending → reclaimed 立即回收。回收后项目状态是待用户检查，资料归档状态仍是待归档确认；用户检查不再占用普通目标执行状态。普通目标回收不等待“归档”，不创建归档包、不更新归档索引、不清理活动区，也不输出归档完成话术。

用户发现原需求问题时创建新的复修目标，不能把原目标重新设为 active；用户提出新增需求或优化时回到需求整理或需求变更。用户明确回复“归档”后，才创建独立 archive 目标；archive 不计入普通 N/M。归档失败时原普通目标保持 reclaimed，活动资料保留，不能把项目标记为已归档或已完成。重复回收和归档重试必须幂等并保留真实证据。
