# 提示词向导

## 全权托管模式

用户明确要求全程不参与操作、不再确认或全权交给 Codex，且没有明确选择用户自测时，该要求已完成验收责任授权。不再显示验收选择框，直接按 Codex 真机测试和适用的页面样式检查生成并执行 `/goal`。用户明确选择“我自己测试”时，以用户自测为准，不得被托管默认覆盖。需要真实 Chrome 状态时优先 `@Chrome`，无法完成时自动切换 `@电脑`。客观无法继续时只记录为 `受阻`，不得要求用户代操作或补确认。

> 目标：用户不用翻教程。没有具体任务时显示六类场景；已有具体任务时先调查、评分并进入四档流程。需求收口与正式 PRD 各完成一次明确确认，验收责任和页面检查在对应选择框集中确认，随后按固定 N/M 阶段交棒。

## 4.6 固定阶段目标合同

当前口径优先于本文中任何历史的“深度一条”或“完整两条”示例：

- 轻量：single 1/1。
- 标准：single 1/1。
- 深度非 UI：documentation 1/2 → development-and-acceptance 2/2。
- 深度 UI：documentation 1/3 → ui 2/3 → development-and-acceptance 3/3。
- 完整非 UI：documentation 1/3 → development 2/3 → acceptance 3/3。
- 完整 UI：documentation 1/4 → ui 2/4 → development 3/4 → acceptance 4/4。

深度在用户明确不需要 UI 时跳过 ui。完整流程默认保留 ui，但客观不涉及 UI 或用户明确跳过时取消。UI 目标只做视觉方案、可选视觉图、UI 壳、外部 AI/Stitch、接收检查、Stitch 强制复修和适用 Design QA；真实 API、数据流、权限、状态和表单接线留到开发目标。等待外部输入时暂停同一 UI 目标，恢复后第 N/M 次不变。

每个目标必须声明基础目标数、当前第 N/M 次、目标阶段、UI 决策、UI 路线、等待外部输入状态、前置条件、本阶段职责、禁止后续阶段和下一目标解锁条件。documentation 已知需要 UI 但路线未选时可写 `pending`；进入 ui 前必须改为 canonical 路线，Stitch 路线必须依合同强制复修。所有中间目标禁止归档；只有最后目标负责最终验收交接，最后普通目标只负责真实验收、问题回写和修复复测，然后进入待用户检查与待归档确认。

原生 `request_user_input` 选择框的问题、选项和描述必须使用纯文本，不得用 Markdown 包装。工具不可用时，使用普通段落回退：

选项一：$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

## 4.3 真实提示词交付前门禁

每次选择后准备交付普通目标提示词时，必须先调用仓库校验器：`python3 scripts/check_adaptive_flow_docs.py --prompt-file <真实提示词文件> --prompt-tier <light|standard|deep|full-docs>`。普通 Goal 按文件指针型短合同校验，不设 3000 字最低门槛；Stitch 实例级复修使用 `--prompt-kind stitch-instance-repair`，继续校验专项长度、固定正文和事实追加；Stitch 生成、外部 AI UI、Product Design、生图和其他专项提示词分别使用 `--prompt-kind stitch-generation|external-ai-ui|product-design|image-generation|special-prompt`，不套用普通 Goal 合同。执行者还要用 `--artifact-file`、`--changed-file` 审计真实文档、任务和追踪产物。

所有会立即生成提示词的选项只能从统一 canonical builder 生成：`$liran-plan ` 只出现一次，固定细节后缀严格位于末尾；前缀和后缀不得进入正式 `/goal` 正文。重路由、自由输入、澄清和状态选项继续不带包装。原生 `request_user_input` 和文字回退必须复用完全相同的选项集合，禁止临时另写“Codex 真机测试”或“我自己测试”。

运行时档位执行门禁要求：流程合同和档位执行门禁未通过前禁止编辑实现源码；标准、深度和完整流程必须审计真实 diff。

## 4.9 需求整理文档与正式 PRD

具体项目修改任务进入需求整理首轮时，先创建或复用 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`；用户确认整理完成后再生成独立正式 PRD。纯解释、状态查询、只读审查、知识问答和用户明确禁止写文件时跳过。

后续每轮先更新需求整理文档，再只回复新增、变更、待确认项和路径。用户说“需求整理好了”后，根据整理结果重新生成正式 PRD 并建立执行文档索引；PRD 只保存最终需求事实和索引，不复制 Goal、模块/微观任务、开发、测试、真机、UI 或归档正文。任务 ID 贯穿需求整理文档、正式 PRD、任务/微观任务、`04/08/09/10` 和归档。

收口口令与转换确认必须严格按两步执行：先问“需求整理好了吗？整理好了的话，请回复‘需求整理好了’”；收到后读取需求整理文档，重新归纳正式 PRD、建立索引并在对话输出正式 PRD 供用户确认。正式 PRD 转换完成后必须评分并确定流程等级，记录五维分数、总分、证据和路由结果；用户回复“PRD 没问题”且评分、文档体系、任务拆分和索引检查通过后才生成下一阶段提示词。每个需要选择的节点必须出现可操作的纯文本选项，不能默认替用户选择或跳过选项。

此时状态固定为“正式 PRD 待确认”；未收到“PRD 没问题”不得进入“提示词生成中”。

最后普通目标不包含正式归档合同，只使用 handoff；所有中间目标禁止归档。用户明确回复“归档”后，才读取独立 archive 模板，按先更新长期事实、再创建并验证归档、更新归档索引、按任务 ID 清理活动区的顺序执行。失败时保留原文并标 `归档受阻`。只有真实成功才能说“本次任务已完成并归档”。

## 什么时候使用

当用户出现下面任一情况，优先进入本向导：

- 只输入 `$liran-plan`
- 只输入 `/liran-plan`
- 说“我不知道下一步干嘛”
- 说“继续”“接着做”“下一步是什么”
- 想用本技能，但没有明确说要执行哪一个功能
- 想要提示词、命令、操作指南、下一棒接力话术
- 已经给出具体 Bug、功能或任务，需要 Codex 判断应走哪个流程

核心三句话：

```text
需求没整理清楚前，不开干。
目标模式没收口前，不吐下一条命令。
已确认的 Codex 真机测试或用户验收没通过前，不标完成。
提示词要信息完整但不重复，不能因为追求简短导致 Codex 跑偏。
```

## 第一步：先判断有没有具体任务

### 具体任务直接分档

用户已经给出具体 Bug、功能、删除、迁移、发布或文档任务时，不先问六选一。Codex 先做最小必要的只读调查，读取项目规则、相关代码、测试、文档和 Git 状态，搜索调用方并推演修改后影响，再按五项 `0–20` 分模型完成修改前评分。

六类场景和四档流程分离：修复、删除、新增、续作和其他任务都可能进入轻量、标准、深度或完整流程。新项目默认完整流程；老项目新增少量功能不自动完整化。

未命中安全门禁时采用用户指定档位；安全门禁只规定最低档位。关键影响未知时不能只按低总分进入轻量流程，先继续最小调查，执行前仍无法查清时最低按深度流程处理。

评分后，回复最前面直接用正常 Markdown 加粗文本显示当前流程、开始方式和选择原因，禁止放进代码块。然后按档位整理需求：

- 轻量流程：一次简短整理，创建或复用单份需求整理文档，不进行多轮需求讨论，不创建完整 `liran_docs`。
- 标准流程：一次模块级整理，写清影响范围和实施步骤，定向更新已有文档。
- 深度流程：必要的多轮整理后做一次详细集中确认，非 UI 生成 2 次分阶段 `/goal`，UI 生成 3 次。
- 完整流程：进入下面的六类场景和完整需求整理。

轻量、标准和深度都只显示一个 Codex 单选框。一个问题同时确认需求和测试方式，不能拆成两个问题。

原生选择框优先规则：当前环境中 `request_user_input` 可用时必须实际调用 `request_user_input`，不能把普通文字编号说成 Codex 选择框；只有工具不可用时才退回普通文字编号。用户点击或发送选项后，Codex 必须在收到选择结果后的同一轮自动生成对应档位的完整 `/goal`，不得等待用户再说“请给我提示词”“继续”或同义口令。

提示词交付规则：可复制 `/goal` 的全部内容放在一个独立的 Markdown 代码块中，代码块外只保留一句简短引导。代码块内部不得嵌套三反引号，不把一条提示词拆成多个代码块；提示词内部使用普通标题、列表和内联反引号组织。

普通目标提示词必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同：写清任务 ID、流程档位、目标 N/M、当前阶段、真实读取文件、允许/禁止范围、验证、状态回写、完成条件和下一阶段解锁条件。普通 Goal 不设 3000 字最低门槛，也不复制 PRD 或执行文档正文。Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整结构、长度和校验规则。

生成任何完整目标提示词时，代码块内第一行必须原样放入统一多智能体判断句，然后再写“请直接开始执行”和项目正文。主智能体自行判断是否启用；启用后任一时刻最多同时五个子代理，子代理完成后必须回收，回收后可再启用新的子代理，子代理不得再派生代理。

选择框里不得出现“推荐”。`Codex` 表示执行任务的 AI，`我` 表示当前用户。

选择框自由输入用于指出需求不准确，或要求 Codex 重新判断流程。用户完成选择后，已经确认需求、验收责任和页面样式检查方式；生成的 `/goal` 要写入选择结果，执行时不得再次询问是否开始真机测试、是否检查页面或使用哪个工具。

收到选择结果后直接交付，不要回复“确认后我再生成”“请再说一声给我提示词”或其它等待语。只有选择内容是在修正需求或要求重新评分时，才回到整理/评分步骤，而不是生成旧需求的 `/goal`。

Stitch 路线不调用 Product Design Design QA；无论页面样式检查选项如何，都必须执行初次接收检查和强制实例级细节复修。其他明确高保真 Product Design 路线仍按原规则执行 Design QA。

Stitch 固定复修提示词必须同等覆盖页面结构与布局、尺寸与间距、字体与文本排版、颜色和视觉样式、控件规格、图片和视觉资源、层级和组合关系、状态表现、响应式与不同视口。控件规格不得遮蔽其他视觉维度。项目微调只能填充或替换项目事实、增加项目专属限制/文件/验证，不能删除固定正文任何词语、句子、列表项或章节；不存在的元素保留并标记 `不适用：当前 Stitch 原始产物中不存在该元素。`，实例级复修提示词也必须保持 3000–10000 个字符且不走普通流程合同校验。其他原本使用 3000–10000 字符校验的长提示词改为 3000–10000。

任何档位都不得伪造已经读取的文件、调用方、命令、测试、截图、真机操作、用户反馈或完成状态。没有事实证据时写“未验证”“待确认”或“受阻”，不能为了补评分或宣布完成而编造。

### 没有具体任务时问六选一

如果用户没有明确场景，先不要写文档、读代码、拆任务或开 `/goal`。先问：

```text
你现在属于哪种情况？

1. 新项目
2. 老项目新增功能
3. 老项目续作
4. 老项目修复
5. 老项目删除
6. 其他

你回复 1 / 2 / 3 / 4 / 5 / 6 就行。Codex 会先调查并判断流程；新项目进入完整流程，其他场景按项目实际情况评分。
```

## 第二步：按流程整理需求

轻量流程做一次简短整理，标准流程做一次模块级整理，深度流程按需要多轮整理后输出一次详细总结。只有完整流程默认进入下面的完整多轮需求整理阶段；这个阶段允许用户慢慢说、分多轮补充，不把第一次回答当成最终需求。

每轮只做：

1. 说明当前是在整理需求，不是在执行。
2. 先更新同一任务 ID 的PRD 需求文档。
3. 只回复本轮新增、变更、待确认点和真实路径；用户要求全文或进入集中确认时才输出完整总结。
4. 标出可能影响开发、修复、删除、验收的风险点。
5. 明确当前不做：不写代码、不拆任务、不开 `/goal`、不生成真机实测、不输出拆任务提示词、不输出真机提示词。
6. 固定收尾。

固定收尾必须使用下面这段或非常接近的说法：

```text
整理好了吗，还需要补充吗？
```

六类场景整理重点：

- 新项目：项目目标、用户是谁、解决什么问题、核心功能、边界、不做什么、验收标准。
- 老项目新增功能：新增什么、为什么新增、加到哪里、影响哪些旧模块、哪些旧功能不能动、验收标准。
- 老项目续作：已经做了什么、哪些是真的完成、哪些只是半成品、当前真实状态、下一段只续哪里、不要重复做什么。
- 老项目修复：修什么问题、复现路径、期望结果、影响范围、不能改坏什么、回归验证点、验收标准。
- 老项目删除：删什么、为什么删、入口在哪里、依赖谁、影响哪些模块、哪些数据/配置/API 要保留或迁移、删除后怎么验证无残留、不能误删什么。

### 完整流程中三个容易跑偏场景的详细入口提示词

续作场景不要直接继续写代码，先用这段：

```text
$liran-plan 这是一个老项目，我最近已经做了一部分功能，但当前状态可能有点乱。请先不要继续写代码，不要拆任务，不要开 /goal，不要进入真机实测；先进入多轮需求整理和真实状态盘点。

当前场景：老项目续作。
当前目标：先把“真实已经完成了什么、还剩什么、下一段只续哪里”整理清楚。

请重点整理：
1. 我已经说过或已经做过的内容是什么。
2. 哪些是真的完成，哪些只是半成品、临时方案或未验证状态。
3. 当前代码、旧 docs、现有 liran_docs 和开发追踪是否一致。
4. 下一段只应该续作哪个模块或哪条主线。
5. 哪些内容不要重复做，哪些内容不要扩散碰。
6. 后续验收标准是什么。

只允许做：
1. 归纳我的原话和当前状态。
2. 标出已确定需求、未确定问题、风险点和待确认项。
3. 如需读取项目文件，只能用于理解现状和整理需求，不要改文件。

明确禁止：
1. 不写代码。
2. 不生成或修改 liran_docs。
3. 不拆任务。
4. 不开 /goal。
5. 不进入真机实测。
```
