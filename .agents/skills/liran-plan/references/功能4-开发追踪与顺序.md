# 功能四 · 开发追踪 + 顺序梳理 SOP

## 目的
1. **开发顺序梳理**：依据模块树 + 横向依赖，推导合理的开发先后。
2. **开发追踪**：记录每个模块的开发状态，实时更新，让人和 AI 随时知道整体进度 + 当前该做哪个。
3. **状态门禁**：根据验收责任进入 Codex 真机分支或用户验收分支，防止未实测就提前收口。

## 4.4 活动追踪与归档边界

`04-开发追踪.md` 只保留活动任务的任务 ID、PRD 路径、依赖顺序、状态、阻塞和下一步。已关闭任务的详细状态流水进入单任务归档；没有活动任务时保留文件并写明“当前没有活动开发任务”。归档只能按任务 ID 清理本任务记录，不得影响其他活动任务。PRD 只做需求事实和执行文档索引，不承载本文件的开发流水。

## 4.6 多目标阶段追踪

### 最后普通目标回收与项目归档分离

最后一个普通目标完成真实验收、回写、复测和修改后评分后，先记录 goal_status=reclaim_pending，确认回收成功后写入 goal_status=reclaimed，再把项目状态写为待用户检查。待用户检查和待归档确认不再占用普通目标执行状态。

用户检查期间不得继续执行原目标。用户发现原需求问题时创建新的复修目标；新增需求或优化回到需求整理/需求变更。用户明确回复“归档”后创建独立 archive 目标，archive 不计入 N/M。归档失败保持原普通目标 reclaimed，只有归档成功后项目才能进入已归档 → 已完成。

每个活动任务除了任务 ID 和状态，还必须持续记录基础目标数、当前第 N/M 次、当前阶段、UI 目标决策、是否等待外部输入、本阶段解锁条件和禁止越界项。上下文恢复时以这组合同为准，不重新猜档位或目标数。

- 轻量、标准：1 次目标。
- 深度非 UI：2 次，文档 → 开发与验收。
- 深度 UI：3 次，文档 → UI → 开发与验收；用户明确不需要 UI 时跳过 UI 目标。
- 完整非 UI：3 次，文档 → 开发与内部测试 → 验收交接，归档由独立 archive 目标执行。
- 完整 UI：4 次，文档 → UI → 开发与内部测试 → 验收交接，归档由独立 archive 目标执行。

外部 AI 或 Stitch 的等待与恢复属于同一次 UI 目标，不增加编号。非最后目标只能记录阶段完成和下一目标解锁，不得执行最终归档或使用“整体已完成”话术。

## 4.3 编码解锁前的持久化任务基线

每次状态变化同时记录进入证据；进入 `受阻` 时必须填写具体阻塞原因，恢复时必须提供新的验证或外部状态证据。

标准、深度和完整流程必须把任务编号、任务名称、依据文档、影响文件/模块、依赖、测试方式、完成条件、当前状态和是否影响真机清单写入真实 `04-开发追踪.md` 或对应持久化任务文件，并产生本轮真实 diff。只在聊天或思考中记录任务不能解锁编码；深度流程还必须一次性写回全部微观任务并完成 `09-真机实测.md` 或用户验收准备。

## 开发顺序推导规则
- **被依赖者先做**：A 依赖 B，则 B 先于 A。
- **底层先于上层**：基础设施/公共模块 → 业务模块 → UI 交互。
- **纵向自底向上**：叶子能力先于聚合它们的父模块（视情况）。
- 顺序的依据来自 `liran_docs/03-索引.md` 的依赖总表，**不要凭空排**。若存在循环依赖，标记出来并提示用户拆解。

## 状态字段
每个模块/任务用统一状态：
- `待开发` / `进行中` / `内部测试通过` / `待实测` / `真机测试通过` / `待用户验收` / `用户验收通过` / `归档中` / `已归档` / `已完成` / `受阻` / `归档受阻`

### 状态含义与迁移
- `待开发`：尚未开始。
- `进行中`：正在开发或修复。
- `内部测试通过`：接口、逻辑、页面、UI 壳接线或代码主链路已经完成，并通过内部验证。
- `待实测`：已创建或更新 `liran_docs/09-真机实测.md`，等待进入真实环境验证。
- `真机测试通过`：已完成对应清单的真实操作验证。
- `待用户验收`：用户选择自己测试，Codex 已完成内部测试并等待用户反馈。
- `用户验收通过`：用户明确反馈测试通过。
- `已完成`：Codex 真机测试通过或用户验收通过，且问题回写、长期事实、单任务归档、归档索引和活动区清理均已同步。
- `受阻`：存在外部依赖、权限、环境或其它真实阻塞，必须写清原因与依赖项。

Codex 真机测试分支：

`待开发 → 进行中 → 内部测试通过 → 待实测 → 真机测试通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

用户自己测试分支：

`待开发 → 进行中 → 内部测试通过 → 待用户验收 → 用户验收通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`

补充规则：
- 真机实测失败但仍可继续修复时，状态回退到 `进行中`。
- 真机实测失败且被外部条件卡住时，状态改为 `受阻`。

## 操作步骤
1. 读 `liran_docs/03-索引.md` 的模块树与依赖总表。
2. 做拓扑排序，得出推荐开发顺序，写入 `liran_docs/04-开发追踪.md` 的"开发顺序"区。
3. 为每个模块建一行追踪条目，**直接链接到对应的微观文档**（`modules/...`）。
4. 标注初始状态（一般为 `待开发`）。
5. 当某个模块达到"UI 壳接收通过或开发完成"的可验证节点后，先做内部验证，通过后把状态更新为 `内部测试通过`。
6. 如果用户选择 Codex 真机测试，创建或更新 `liran_docs/09-真机实测.md` 并把状态更新为 `待实测`。
7. 如果用户选择自己测试，完成内部测试后把状态更新为 `待用户验收`，不得直接标记完成。
8. Codex 真机通过后更新为 `真机测试通过`；用户明确反馈通过后更新为 `用户验收通过`。失败则回退到 `进行中`、保持 `待用户验收` 或改为 `受阻`。
9. 问题回写和必要复测完成后先进入 `待用户检查 → 待归档确认`；只有用户明确回复“归档”后，才创建并校验归档，再从活动追踪移走本任务记录。
10. 归档成功后更新为 `已归档 → 已完成`；失败则保留原记录并标 `归档受阻`。
11. 状态变化时同步检查是否解除了别的模块的"受阻"。

## 纪律
- 追踪表的每条都要可点进对应文档——AI 接活时顺着追踪表即可定位完整上下文。
- 顺序与依赖不一致时，以索引依赖总表为准，回头修顺序。
- 每一轮只推进当前最前的模块，不要顺手把相邻模块一起改掉；如果要换棒，先回写追踪再继续。
- `已完成` 是门禁状态，不得跳过 `真机测试通过` 或 `用户验收通过`，也不得跳过 `已归档` 直接标记。
- `待实测` 前必须已有内部验证证据；`真机测试通过` 前必须已有 `liran_docs/09-真机实测.md` 的对应通过记录。
- 单独调用场景（"更新一下开发追踪"）：直接重算顺序 + 刷新状态即可，不必重走全程。
