# 功能五 · 任务微观化拆分 + AI 友好提示词 SOP

## 目的
把开发任务**微观化、细节拆分，然后实现**。因为人和 AI 有"代沟"，本功能把已确认的文档翻译成**让 AI 更易理解的"源数据"提示词**，让 AI 在被约束、有细节的前提下精确执行。

轻量和标准各使用一次 `/goal`。深度和完整流程把微观任务放在第一次 documentation 目标，不再与开发、UI 施工或验收混在同一阶段。

4.9 起，四档在需求整理首轮都先创建或复用独立需求整理文档 `liran_docs/requirements/<任务ID>-<任务名称>-需求整理.md`，需求讨论每轮用聊天式记录；用户确认“需求整理好了”后，根据整理结果重新生成独立正式 PRD。正式 PRD 只保存最终需求事实和执行文档索引，任务拆分和微观任务属于当前施工资料，任务关闭后进入同一单任务归档。

## 四档 `/goal` 交付

### 轻量 /goal

用于单点 Bug 或明确小改动。不创建完整 `liran_docs`，不为形式单独拆微观任务；但正式 PRD 转换完成后仍必须完成五维评分和流程分级，评分总分、评分证据和最终流程等级必须写入目标提示词；必须把用户已确认的 Bug、复现、期望、边界、测试选择和完成条件完整写进提示词。

固定执行顺序：

1. 读取项目规则、目标代码、调用方、相关测试、已有文档和 Git 状态，复核修改前评分。
2. 先写或更新一个能复现问题的失败测试；不适合自动化时记录可重复的最小内部验证。
3. 实现最小修复，不扩散重构。
4. 运行定向测试、相关回归和最终 diff 检查。
5. 按已确认验收责任执行 Codex 真实操作验证，或准备入口和步骤进入 `待用户验收`；页面样式检查按选项执行。
6. 只有公共行为、既有追踪或长期避坑受影响时，定向回写现有文档。
7. 根据真实 diff、调用方和测试结果做修改后评分，如需升级就在同一目标补足要求。
8. 验收通过后先进入待用户检查和待归档确认；用户明确回复“归档”后，才执行独立单任务归档。

轻量提示词必须包含：当前档位、修改前评分与证据、复现方式、当前结果、期望结果、影响边界、允许改动范围、禁止事项、测试命令、验收责任、页面样式检查选择、修改后评分和最终输出字段。

### 标准 /goal

用于一个模块或一条有限业务链。项目没有 `liran_docs` 时不强制创建完整体系，但必须先整理受影响模块、任务和已有文档基线，再开始实现。

固定执行顺序：

1. 读取规则、模块代码、完整调用链、测试、已有文档和 Git 状态，复核修改前评分。
2. 在实现前定向更新受影响的已有模块文档、开发追踪和测试任务；没有对应文档时只记录本轮模块任务清单，不补完整文档树。
3. 判断 UI 影响：已有页面/组件调整按标准流程处理；发现新页面、复杂状态、跨页面交互、UI 与业务联动或需要 UI 壳时，在同一目标升级到深度流程。
4. 按 TDD 完成实现，覆盖正常路径、失败路径和主要回归路径。
5. 运行模块测试、集成检查、必要构建和最终 diff 检查。
6. 回写真实实现和内部测试结果到受影响文档、任务与追踪。
7. 按已确认验收责任执行 Codex 真机测试、页面检查，或进入 `待用户验收`；失败后修复复测。
8. 再回写验收结果和问题，完成修改后评分与用户检查交接；正式归档由独立 archive 目标执行。

标准提示词必须包含：模块现状、完整影响范围、任务清单、UI 判断、实施步骤、正常/失败/回归路径、定向文档动作、测试命令、验收责任、页面检查、自动升级和最终输出字段。

### 深度 /goal

用于跨模块、共享逻辑、高风险或验证复杂任务。

深度非 UI：2 次。

1. 文档目标 documentation 1/2：一次性更新受影响文档体系，包括更新受影响的 `liran_docs`，拆分并写回全部任务模块和微观任务，更新开发追踪，准备真机或用户验收清单。禁止编辑实现源码、真机验收和归档。
2. 开发与验收目标 development-and-acceptance 2/2：审计前置产物，做系统化调试、TDD 实现、内部测试、已确认的真实验收、问题回写、修复复测、修改后评分和用户检查交接。

深度 UI：3 次。在上述两次之间插入 ui 2/3，只做视觉方案、可选视觉图、UI 壳、外部 AI/Stitch、接收检查、强制复修和适用 Design QA。用户明确不需要 UI 时不插入。外部产物未返回时暂停同一 ui 目标，不改目标数量和 N/M。

## 4.4 最终目标交接与独立归档

最后普通目标收口时必须保存 goal_status：完成门禁满足后为 reclaim_pending，回收成功后为 reclaimed。同时保存 task_state_after_goal=待用户检查、archive_state_after_goal=待归档确认和用户检查通知证据。回收失败不得伪造 reclaimed，重复回收必须幂等；archive 目标独立运行且不计入普通目标数量。

目标回收合同可通过 scripts/check_adaptive_flow_docs.py --goal-reclaim-file <JSON> 校验；该校验只处理普通目标回收，不会启动资料归档。

只有最后 M/M 普通目标必须完成最终验收、问题回写和复测并进入待用户检查；它不要求归档目录或归档状态。所有 N<M 的文档、UI 和开发目标禁止归档与整体完成话术。用户明确回复“归档”后，独立 archive 目标才读取归档模板并执行归档。

最后普通目标必须写清“当前目标暂不执行正式归档”“等待用户检查”“有问题回到修复流程”“新增需求回到需求整理或变更流程”和“用户明确回复归档后才启动正式归档”。中间目标用 `archive_stage="non-final"`，最后普通目标用 `archive_stage="handoff"`，正式归档用 `prompt-kind archive`。

### 4.3 编码前硬门禁（运行时必须可核对）

上面的顺序不是建议，而是编码解锁状态机。执行者必须在编辑任何 `src`、`frontend`、`backend`、`electron` 或其他实现源码前，逐项核对并记录真实证据：

1. 受影响 `liran_docs` 已逐文件更新并产生真实 diff；
2. 全部确认需求已一次性拆成带编号的任务模块和微观任务，每项写明影响文件、依赖、测试和完成条件；
3. `04-开发追踪.md` 已写入全部任务、依赖顺序和当前状态；
4. Codex 真机分支的 `09-真机实测.md` 已建立或更新，或用户自测分支已经写明真实入口、最短步骤、期望结果和反馈方式；
5. 已运行产物审计，确认文件存在、内容不是占位、真实 diff 与任务清单一致。

任一条件不成立，必须停留在文档目标，禁止先写源码再补文档。提示词中出现“已更新”“已拆完”“已准备”不等于真实产物已经存在；必须检查文件、内容、diff、命令和输出。

所有深度目标必须包含 `## 流程合同` 与 `## 档位执行门禁`；真实 diff 审计和编码解锁未通过前，禁止编辑实现源码。

文档目标通过后必须生成后续开发或 UI 目标的详细提示词，但不得未经产物审计跳阶段。用户已确认验收方式，不再重复询问。

## 统一提示词交付格式

普通目标提示词遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md)：使用文件指针型短格式，写清任务 ID、阶段、目标 N/M、真实读取文件、允许/禁止范围、验证、回写和完成条件。普通 Goal（包括 `--prompt-kind long` 兼容入口）按任务复杂度决定长度；Stitch、外部 AI、Product Design、生图等专项提示词继续使用自己的完整结构和长度规则，适用时仍保持 `3000–10000` 字符。

普通澄清问题、Codex 原生选择框、进度/状态/阻塞说明、单句启动语和单条命令不属于完整执行提示词。普通 Goal（包括 `--prompt-kind long` 兼容入口）使用文件指针型短格式，按任务复杂度决定长度；Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整模板和长度门禁。

所有完整目标提示词都必须以统一多智能体判断句作为第一行。该句要求执行者自行判断是否启用多智能体；启用时只有一个主智能体，任一时刻最多同时五个子代理，完成后必须回收。回收后可按需继续启用新子代理，不限制历史累计数；子代理不得再派生代理。

轻量、标准和深度 `/goal` 都必须包含同一条无人值守工具合同：涉及真实 Chrome 会话、登录态、标签页或扩展时优先使用 `@Chrome`；`@Chrome` 无法完成时自动切换 `@电脑`，从当前步骤继续。Codex 可按需组合命令行、`@浏览器`、`@Chrome` 和 `@电脑`，不得要求用户代为操作，不得再问工具选择、是否继续或是否由用户手动完成。只有登录凭据、验证码、账号权限、付款授权、不可逆操作确认或外部服务客观不可用等真实硬性阻塞才能暂停。

所有可复制 `/goal` 都必须完整放在一个独立的 Markdown 代码块中。代码块外只允许一句引导；代码块内部不得嵌套三反引号，也不得拆成多个代码块。

每条提示词都按同一字段顺序组织，并额外声明基础目标数、目标总数、当前 N/M、目标阶段、UI 决策、等待状态、前置条件、本阶段职责、禁止后续阶段和下一目标解锁条件。

## 完整流程阶段

**以下章节只适用于完整流程。** 完整非 UI 是 documentation 1/3、development 2/3、acceptance 3/3；完整 UI 是 documentation 1/4、ui 2/4、development 3/4、acceptance 4/4。

documentation 必须一次性生成/更新完整 `liran_docs`、全部任务和微观任务；ui 只做视觉与 UI 壳；development 只做实现、接线和内测；acceptance 按已确认责任做真实验收、问题回写和修复复测，然后进入用户检查交接；用户明确回复“归档”后才由独立 archive 目标执行正式归档。不得要求用户复制第二条提示词作为重复确认；后续提示词由前一阶段通过后自动交付。

## 开头执行语句

无论方式 A 还是方式 B，提示词开头都先放一句类似：

```text
你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。

请直接开始执行下面步骤，先读取对应文档，再输出结果，不要先解释。
```

如果是 documentation、ui、development 或 acceptance 目标，开头要换成匹配当前阶段的具体启动句，但仍保持“先执行、后解释”。

UI 壳启动句示例：

```text
你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。

请直接开始执行下面步骤，先读取对应微观文档、已确认文本视觉方案、liran_docs/10-UI壳接入清单.md 和对应 liran_docs/ui-shells/...，再准备真实前端 UI 壳落地，不要先解释。
```

完整流程 development 目标启动句示例：

```text
你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。

请直接开始执行下面步骤，先读取已通过的 documentation 和 ui 阶段产物，再执行当前 development 目标的业务接线与内部测试，不要先解释。
```

完整流程非 UI 任务不创建空 UI 壳清单。documentation 1/3 读取并更新真实索引、追踪、架构、API、数据、模块和测试文档；development 2/3 完成实现与内测；acceptance 3/3 再按已确认验收责任完成真实验收、回写和修复复测，然后进入用户检查交接；用户明确回复“归档”后才执行独立正式归档。

## 完整流程操作步骤
1. 确认前置条件已满足（用户已确认需求整理总结）；这一步和文档生成/更新在同一条提示词里同步执行，不是等文档单独跑完再另起一轮。
2. 按 `liran_docs/04-开发追踪.md` 的开发顺序，取下一个待开发模块。
3. 把该模块的微观文档拆成一串极细任务。
4. 为每个任务生成提示词（默认方式 A；用户要自动化则把当轮任务组合成方式 B 的可验证完成条件版）。
5. 提示词里务必带上：关联文档路径、改动范围、完成判定标准，以及"完成后建议更新到哪个状态"。
6. 任务完成后，回到功能四更新开发追踪状态；若只是内部验证完成，最多更新到 `内部测试通过` 或 `待实测`，不得直接标 `已完成`。
7. **功能五的终点是 documentation 目标可通过审计**：必须把全部已确认需求拆到可执行、可验证，不留到后续目标再补。
8. 有 UI 时解锁唯一 ui 目标，无 UI 时解锁 development 或 development-and-acceptance。
9. development 目标只有达到 `内部测试通过` 才能解锁完整流程 acceptance。
10. 最后目标按已确认验收责任执行 Codex 真实验收或用户验收交接，通过后等待用户检查；收到“归档”后再执行独立正式归档。
