# 功能三 · 真实前端 UI 壳五路线 SOP

## 目的
当微观实现文档梳理完成后，把抽象的"场景/触发/逻辑"具象成可确认、可落地、可接线的真实前端 UI 壳。UI 阶段默认不再产出独立 HTML 或 demo，而是在目标项目真实前端结构里准备 UI 壳施工：先确认文本视觉方案，必要时确认视觉图/原型图，再由 Codex 生成接入清单、规划文件、创建合法占位文件、安排入口、准备 mock/type/局部样式/注释锚点，并根据路线生成外部 AI 输入包、Stitch 提示词或由 Codex/@product-design 直接造壳。

本 SOP 中供用户直接复制给 Codex 的普通 Goal 提示词，必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同；外部 AI、Product Design、生图和 Stitch 等专项提示词继续使用各自完整模板与校验规则。不得把本文档中的短启动句、结构示例或字段骨架当成可直接交付的成品提示词。

## 四档 UI 分流

页面任务先按四档自适应流程判断，不再只要碰到页面就机械进入完整 UI 壳五路线：

| 流程 | UI 范围 | QA 与文档要求 |
|---|---|---|
| 轻量流程 | 已有页面中的局部样式、小交互或单一状态修复 | 不创建完整 UI 壳；按用户选择做定向真机和局部样式检查 |
| 标准流程 | 单页面或单组件调整 | 不走完整五路线；状态验证必做，页面样式检查按用户选择执行 |
| 深度流程 | 新页面、复杂状态、跨页面交互、UI 与业务联动 | 创建受影响 UI 壳清单；Design QA 按用户选择执行 |
| 完整流程 | 新项目或多个大型 UI 模块整体推进 | 执行本 SOP 的完整 UI 壳五路线 |

边界判断：

- `局部样式修复` 是在已有页面和已有组件结构内调整一个明确视觉问题，不新增页面、不重排整块布局、不改变跨组件状态和业务接线，属于轻量候选。
- `整页或整组件调整` 会改变一个页面或组件的完整布局、状态集合或交互结构，至少属于标准候选。
- 新页面、复杂状态、跨页面交互、UI 与业务联动或新 UI 壳最低进入深度流程。

涉及页面的轻量和标准流程仍只有一个 Codex 单选框。用户可以选择：

选项一：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，也检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，不检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项三：$liran-plan 需求没问题，改完后我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

涉及页面的深度流程同样只显示一个问题，选项为：

选项一：$liran-plan 需求没问题，直接生成完整提示词，改完后让 Codex 自己真机测试，也检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 需求没问题，直接生成完整提示词，改完后让 Codex 自己真机测试，不检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项三：$liran-plan 需求没问题，直接生成完整提示词，完成后我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选择框自由输入用于指出需求不准确或要求 Codex 重新判断流程。选择“不检查页面样式是否符合方案”时，Codex 仍要验证页面功能、状态、错误和交互，但不做普通视觉方案对比，也不能声明视觉还原通过。Stitch 路线不调用 Product Design Design QA；它无论属于深度还是完整流程，都必须在独立 UI 目标中保留初次承接、初次接收检查和强制实例级细节复修三个逻辑阶段。

## 深度流程中的 UI 壳与 Stitch

深度流程只创建本轮受影响的 UI 壳接入清单，不补完整项目 UI 壳树。如涉及 UI，在 documentation 和 development-and-acceptance 之间插入一次独立 UI 目标；普通 Product Design 路线按用户选择执行 Design QA，Stitch 路线在该 UI 目标中依次完成初次承接、初次接收检查、强制实例级细节复修和复修通过门禁。真实业务接线、内测和验收留到后续目标。

已有 Stitch Project ID、Screen ID 或可读取产物时，直接在当前 UI 目标继续。缺少外部产物时将同一 UI 目标标为等待外部输入；收到输入后恢复原目标，不新增 `/goal`、不改 N/M。

完整流程核心分工：

```text
Codex 负责：整理方案、生成接入清单、规划文件、创建合法占位文件、安排查看入口、写明允许编辑范围、准备 mock/type/局部样式/注释锚点、生成外部 AI 输入包或 Stitch 提示词、根据 Stitch 下载文件一比一还原真实前端、后续接业务和验证。
外部 AI 负责：只在 Codex 指定文件里，根据确认方案生成真实前端 UI 壳，并按接入清单预留接口。
Stitch 负责：生成高保真原型、HTML 样式、静态数据、图片、代码和 MD 规范；不负责预留接口。
完整流程 development 目标负责：Codex 接真实接口、状态、业务逻辑和内部验证。
完整流程 acceptance 目标负责：按已确认验收责任执行 Codex 真机或用户验收交接、问题回写和复测，然后等待用户检查与归档确认；正式归档由独立 archive 目标执行。
```

轻量和标准在 single 目标中完成 UI、开发和验收。深度和完整使用独立 UI 目标，后续开发目标再接真实业务。

## UI 壳定义

UI 壳必须严格根据已确认的文本视觉方案，或“文本视觉方案 + 视觉图 / 原型图”创建。它是项目真实前端文件里的外观和交互壳，不是独立 `prototype.html`，不是 demo，也不是可以绕开项目结构的静态展示。

UI 壳负责：页面结构、组件结构、布局、样式、视觉层级、响应式、交互外观、空态/加载态/错误态/成功态等状态外观、项目内可查看入口，以及接口/状态/事件/mock/类型入口预留。

UI 壳不负责：真实接口调用、完整业务逻辑、真实数据流、状态管理接线、权限判断落地、表单真实提交和真机验收。这些由后续 development 或 development-and-acceptance 目标按接入清单接上。

## 何时执行

完整流程中文档和微观任务一次性补齐后，只要涉及页面、表单、列表、弹窗、按钮、状态切换、空态/加载态/错误态、流程页、设置页、UI 优化、前端重构、深度美化、响应式优化或交互优化，就进入真实前端 UI 壳五路线。轻量、标准和深度按上表执行；纯后端、纯配置、纯文档且不涉及页面或交互变化时，明确说明原因后跳过。

已有项目例外保留：如果当前是老项目续作、已有文档/已有功能基础上的 UI 视觉方案迭代，并且用户明确要先生成视觉方向图，可以先进入 UI 视觉确认分支。正确顺序是：文本视觉方案确认 → 用户明确选择生图工具 → 生成视觉方向图 → 用户确认图 → 再回写 `liran_docs`、微观任务、开发追踪和验收标准。视觉图确认前不要把文本视觉草案写死进文档。

## 完整流程

```text
需求和 liran_docs 文档补齐
→ 判断需要 UI 阶段
→ 整理并确认文本视觉方案
→ 可选生成并确认视觉图 / 原型图
→ Codex 生成 liran_docs/10-UI壳接入清单.md
→ Codex 生成对应 liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md
→ Codex 决定本次 UI 壳需要哪些真实前端文件
→ Codex 创建合法占位文件，不是随便空文件
→ Codex 安排正式入口或临时预览入口
→ Codex 准备 mock/type/局部样式/注释锚点
→ 选择五条 UI 路线之一
→ 如果是外部 AI 路线：Codex 生成外部 AI 输入包和可复制提示词
→ 如果是 Stitch 路线：Codex 追问“视觉方案确认好了吗？”并生成 Stitch 专用提示词
→ 外部 AI / Stitch 开工前通过对应就绪门禁
→ 外部 AI 只在指定文件里造 UI 壳并预留接口，或由 Codex 通过 Stitch MCP 下载后做 HTML 样式一比一还原
→ Codex 做 UI 壳接收检查
→ 如果是 Stitch 路线：初次接收结果只能是“可以进入实例级细节复修”或“初次承接受阻”
→ 如果是 Stitch 路线：Codex 自动交付固定复修提示词，完成强制实例级细节复修
→ 如果是 Stitch 路线：复修通过后才解锁业务接线
→ 解锁 development 或 development-and-acceptance 目标：接真实接口、状态、业务逻辑和内部验证
→ 最后普通目标：按已确认验收责任完成真机或用户验收、问题回写和复测，进入待用户检查与待归档确认
→ 独立 archive 目标：用户明确回复“归档”后执行正式归档
```

## 五条 UI 路线

### 1. $liran-plan Codex 直接生成前端 UI 壳（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

Codex 根据确认后的文本视觉方案/视觉图，以及 UI 壳接入清单，直接在项目真实前端文件里造 UI 壳并预留接口。造壳前仍必须先生成 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md`，并根据项目技术栈创建合法占位文件。

### 2. $liran-plan @product-design（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

`@product-design` 参与设计方案和/或 UI 壳落地。产物仍然是项目真实前端 UI 壳，只做外观和交互壳，不接业务逻辑，预留接口必须依据 UI 壳接入清单。

### 3. $liran-plan @product-design + 外部 AI 生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

先由 `liran-plan` / `@product-design` 确认文本视觉方案，必要时确认视觉图。Codex 先生成接入清单、文件、入口、mock/type/样式隔离和外部 AI 提示词。用户拿提示词去其他 AI 软件生成真实前端 UI 文件。外部 AI 只做 UI 壳，后续回到 Codex 接业务。

### 4. $liran-plan @product-design + $Stitch / Stitch MCP（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

先由 `@product-design` 整理文本视觉方案，必要时确认视觉图。你确认文本视觉方案和可选视觉图后，Codex 必须追问：

```text
视觉方案确认好了吗？
```

你明确确认后，Codex 必须按 [templates/Stitch-页面设计开发提示词.md](../templates/Stitch-页面设计开发提示词.md) 从 `liran_docs` 填实，生成一份可复制给 Stitch 的提示词，放在一个独立 Markdown 代码块中。标题必须是 `# {系统题目} — Stitch 多页面设计提示词`，且一级标题后必须紧接“额外设计约束”（0）至（8）原文。你去 [https://stitch.withgoogle.com/](https://stitch.withgoogle.com/) 按完整页面清单生成高保真原型，再把 `$Stitch` / Stitch MCP 的 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID 交给 Codex。Codex 在调用 Stitch MCP 前，先生成接入清单和真实前端合法占位文件，再根据 Stitch 下载下来的 HTML、样式、静态数据、图片、代码和 MD 规范，把 UI 壳一比一落到真实前端文件，并由 Codex 自己补后续接口预留。Stitch 不负责预留接口。

## 生图规则

### 5. $liran-plan @product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

先由 `@product-design` 参与并确认文本视觉方案，必要时在文本方案确认后确认视觉方向图或原型图。随后 Codex 通过 OpenCodex 本地路由，在当前会话内根据环境实际可用模型和任务需要自行选择 Gemini 或其他可用模型，直接生成项目真实前端文件中的 UI 壳；不要求用户把提示词复制到外部软件，不维护固定模型白名单，也不新增强制模型选择框。该路线与外部 AI 路线明确分开，仍必须先准备 `liran_docs/10-UI壳接入清单.md`、对应单壳清单、合法占位文件、入口、mock/type、局部样式、注释锚点和文件白名单，并执行样式隔离、UI 壳接收检查及非 Stitch Product Design Design QA。UI 壳阶段不接真实 API、完整业务逻辑、真实数据流、权限落地、真实表单提交或最终真机验收。


生图不是独立阶段，只能发生在文本视觉方案确认之后。如果需要视觉方案图，让用户明确选择：

```text
1. image2 生图：走 $liran-image2
2. 用户自行提供或指定外部工具生成视觉图
```

禁止使用 `$imagegen`。如果用户不需要视觉方案图，就不要生图，直接根据文本视觉方案进入 UI 壳接入清单和造壳准备。

## 造壳前硬门禁

生成 UI 壳前，Codex 必须完成：

1. 创建或更新 `liran_docs/10-UI壳接入清单.md`。
2. 创建或更新对应 `liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md`。
3. 决定本次 UI 壳需要哪些真实前端文件。
4. 创建这些文件。不能只是随便空文件，必须是符合项目技术栈的合法占位文件，例如 React/Vue/Svelte 组件最小骨架、默认 export、局部样式文件、mock 文件、type/interface 文件和必要注释锚点。
5. 安排查看入口：默认优先正式入口；如果正式入口暂时受权限、数据、接口或旧流程限制，允许临时预览入口。入口文件如果需要外部 AI 修改，也必须加入允许编辑文件清单，并限制可修改范围。
6. 准备 mock/type/局部样式/注释锚点。
7. 生成外部 AI 输入包、Stitch 提示词或对应路线的可复制提示词。

没有这些准备，不允许进入 UI 壳落地，也不允许给外部 AI 生成造壳提示词。

## 外部 AI 开工前就绪门禁

Codex 在把提示词交给外部 AI 前，必须确认：

1. 文本视觉方案已确认。
2. 如有视觉图 / 原型图，图已确认。
3. `liran_docs/10-UI壳接入清单.md` 已生成。
4. 对应 `liran_docs/ui-shells/...md` 已生成。
5. UI 壳需要的文件已由 Codex 创建为合法占位文件。
6. 每个文件用途已写清。
7. 允许外部 AI 编辑的文件白名单已写清。
8. 禁止编辑范围已写清。
9. 查看入口已安排：正式入口或临时预览入口。
10. mock/type/局部样式文件已准备。
11. 代码里已有注释锚点：`TODO(ui-shell)`、`TODO(codex-connect)` 等。
12. 外部 AI 提示词已生成，且可直接复制使用。
13. 提示词明确：外部 AI 不许新增文件、不许新增依赖、不许改全局样式、不许接真实接口、不许补业务逻辑。
14. 如果外部 AI 发现文件不够，必须停止，不能自行扩展。
15. 外部 AI 完成后必须按固定格式回报文件、入口、mock、预留接口、状态、事件和未完成业务逻辑。

## Stitch 路线开工前就绪门禁

Codex 在开始 Stitch MCP 下载前，必须确认：

1. 文本视觉方案已确认。
2. 如有视觉图 / 原型图，图已确认。
3. 基于需求文档、功能树、模块结构、用户流程和信息架构形成的完整页面清单及页面总数已确认。
4. 已追问并得到 `视觉方案确认好了吗？` 的明确确认。
5. `liran_docs/10-UI壳接入清单.md` 已生成或更新。
6. 对应 `liran_docs/ui-shells/...md` 已生成或更新。
7. UI 壳需要的真实前端文件已由 Codex 创建为合法占位文件。
8. 查看入口已安排：正式入口或临时预览入口。
9. mock/type/局部样式/注释锚点已准备。
10. Stitch 专用提示词已生成，且按 `templates/Stitch-页面设计开发提示词.md` 填实；一级标题后紧接额外设计约束原文。
11. 用户已提供 `$Stitch` / Stitch MCP 的 Project ID / Screen ID。
12. Codex 已准备记录 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID、Screen 映射关系、下载目录和 HTML 来源文件。
13. Codex 已明确第 4 路线的目标是根据 Stitch 下载文件里的 HTML 样式一比一还原，禁止自由发挥、禁止只模仿大概风格、禁止重新设计。
14. Codex 已写清 `实例级尺寸保真规则`，确认要根据 Stitch 原始产物做实例级视觉规格保真的一比一还原。
15. Codex 已写清事实来源优先级：第一事实来源是 Stitch 下载下来的 HTML，第二事实来源是 Stitch 下载下来的代码 / 样式 / MD 规范，第三事实来源才是截图。
16. Codex 已计划先做 `控件规格盘点`，至少覆盖按钮变体、图标尺寸、输入控件规格、badge / pill / tag、表格 / 表头 / 单元格 / 筛选栏 / 操作列按钮规格、高密度控件区和容易塌陷区域。
17. Codex 已写清视觉未对齐前禁止过早抽象 / 通用化。
18. Codex 已写清必须防老项目默认 Button / Input / Icon / Table 规格、全局样式和公共组件样式带偏。

## Stitch 提示词规则

如果选择第 4 条路线，先追问并得到 `视觉方案确认好了吗？` 的明确确认后，才能按 [templates/Stitch-页面设计开发提示词.md](../templates/Stitch-页面设计开发提示词.md) 从 `liran_docs` 填实生成给 Stitch 的提示词。交付时只给一个独立 Markdown 代码块，不要写成项目根提示词文件，也不要套用普通 `/goal` 的多智能体开头或 `## 流程合同`。

提示词标题必须是：

```text
# {系统题目} — Stitch 多页面设计提示词
```

一级标题后必须紧接“额外设计约束”（0）至（8）原文，不得改字、拆分、概括、重排或后移。已确认文本视觉方案写入视觉风格，但额外设计约束优先。

提示词必须分端列出 PC 端与移动端独立页面，并写明 `项目总页面数 = PC 端独立页面数 + 移动端独立页面数`。H5 与微信小程序默认共用一个移动页，不重复计数。没有某一端时写 0 页，不得伪造。

页面数量必须以已确认的完整页面清单为唯一依据。页面清单由需求文档、功能树、模块结构、用户流程和信息架构共同确定。页面数量不设置固定上限或下限。页面清单有几个页面，Stitch 就生成几个页面，不得遗漏，也不得自行增加。独立路由或独立业务界面默认计为页面；弹窗、抽屉、面板、组件和 loading / empty / error / success 等状态默认归属页面，不额外计数，除非已确认清单明确把它们定义为独立 Screen。如果 Stitch 单次无法生成全部页面，可以分批生成；所有批次最终必须覆盖完整页面清单，页面总数、名称、职责和关系不得漂移。若某模块与当前产品形态无关，直接标注“不适用”并说明原因。

输出要求：

- 所有描述使用具体词，不使用抽象词；
- 尺寸必须写死为具体数值；
- 页面区块必须分层书写；
- Stitch 不负责预留接口。

用户回传 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID 后，Codex 再用 `$Stitch` / Stitch MCP 落到真实前端 UI 壳，再进入实例级细节复修。

## Stitch MCP 输入与多屏规则

用户会给类似下面的信息：

```text
## Stitch Instructions

Get the images and code for the following Stitch project's screens:

## Project
Title: <Project Title>
ID: <Project ID>

## Screens:
1. <Screen Name>
   ID: <Screen ID>
```

Codex 要根据这些 Project ID / Screen ID：

1. 使用 `$Stitch` / Stitch MCP 获取 Stitch 产物；
2. 下载 HTML、样式、图片、代码、MD 规范等；
3. 判断有几个 Screen；
4. 判断每个 Screen 是页面 / 弹窗 / 抽屉 / 状态页 / 组件；
5. 把 Screen 和真实前端文件的映射写进 `liran_docs/10-UI壳接入清单.md` 和对应单壳清单。

如果多个 Screen 属于同一个 UI 壳，就写在同一个单壳清单里；如果多个 Screen 属于不同 UI 壳，就拆成多个 `ui-shells/...md`。这里不强制用户提前决定，由 Codex 拿到 MCP 信息后再分辨。

单壳清单里建议直接使用小标题或表头写出 `Stitch Screen 映射`，逐条记录 Screen 类型、目标文件和真实页面/组件关系。

## 文件预创建规则

Codex 需要提前创建或安排页面文件、组件文件、局部样式文件、类型文件、mock 文件、局部工具文件和必要入口挂载文件。外部 AI 不负责猜文件结构，只能编辑 Codex 指定的文件。

如果外部 AI 觉得文件不够，必须停止，说明缺哪些文件，让用户回到 Codex 补文件、接入清单和提示词。外部 AI 不得自行新增、删除、移动、重命名文件。

Codex 必须在两个地方写清允许编辑文件清单：`liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md` 和外部 AI 提示词。回到 Codex 后，UI 壳接收检查必须对照白名单检查 diff。

## UI 壳接入清单结构

建议结构：

```text
liran_docs/
├── 10-UI壳接入清单.md
└── ui-shells/
    ├── 某页面-UI壳接入清单.md
    ├── 某弹窗-UI壳接入清单.md
    └── 某面板-UI壳接入清单.md
```

`10-UI壳接入清单.md` 是总索引，记录 UI 壳、模块/页面/入口、当前状态、单壳清单、预览入口、后续开发目标接线项和验收影响。

每个 `ui-shells/...md` 是单个 UI 壳施工合同，记录视觉依据、文件白名单、入口、API/状态/事件预留、mock/type/schema、禁止业务逻辑、后续开发目标任务、验收影响、接收检查和回退记录。Stitch 路线还必须记录 Project/Screen 标识、映射、下载目录、HTML 样式与静态数据来源。

## 预留接口规则

UI 壳里的预留点必须严格根据 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/<某UI壳>-UI壳接入清单.md` 创建。

必须预留 API 占位、数据结构、loading/error/empty/success/disabled/selected/expanded/pagination/filter 等状态入口、点击/提交/筛选/分页/弹窗开关/行操作/批量操作等事件钩子、权限控制点、路由参数、表单规则、mock 数据位置、类型/interface/schema 和 Codex 后续接线说明。

建议统一标记：

```text
TODO(ui-shell): 外部 AI 在这里实现 UI 壳
TODO(codex-connect): 接入真实接口
TODO(codex-state): 接入状态管理
TODO(codex-permission): 接入权限判断
TODO(codex-validate): 接入表单校验
TODO(codex-route): 接入真实路由参数
```

这些标记要同时体现在代码和 `liran_docs/ui-shells/...md` 里，不能只靠代码注释。

## Stitch 一比一还原硬规则

第 4 路线最重要的规则是：

```text
必须根据 Stitch MCP 下载下来的文件里的 HTML 样式一比一还原。
必须根据 Stitch 原始产物做实例级视觉规格保真的一比一还原。
禁止自由发挥。
禁止只模仿大概风格。
禁止重新设计。
禁止让 Codex 自己凭感觉做。
```

原因必须写进执行规则：

```text
Stitch 已经生成好了样式，Codex 的任务不是再设计，而是把 Stitch HTML 样式搬到真实前端 UI 壳中。
```

这次要防的根因也必须写清楚：

```text
Stitch 路线的一比一还原失败，常见根因不是大布局没抄到，而是承接时把原始 HTML 中每个元素自己的实例级尺寸、间距、图标大小、按钮规格、控件规格和文本排版行为，通过通用化抽象抹平了，或者被老项目已有组件默认尺寸、全局样式、公共图标样式、公共按钮样式、公共表格样式悄悄带偏了。
```

一比一还原对象包括：

- Stitch MCP 下载文件中的 HTML；
- HTML 中的 class / style / layout；
- HTML 里的静态数据；
- HTML 对应图片和资源；
- Stitch 输出的代码 / MD 规范中能证明样式的内容。

Codex 必须跟着 Stitch 文件来，而不是把 Stitch 当参考图自己重画。

### 实例级尺寸保真规则

把这条规则固定命名为 `实例级尺寸保真规则`。

它的含义是：除了结构、布局、色彩、阴影、边框、圆角和视觉层级，还必须还原原始 HTML 中每个元素自己的：

- `width / height / min-width / min-height / max-width / max-height`
- `padding / margin / gap`
- `border-radius / border-width`
- `icon width / height`
- `font-size / font-weight / line-height / letter-spacing`
- 单行 / 多行 / 截断 / 不换行
- flex 方向 / 是否 wrap / 对齐方式
- 控件在 header / footer / toolbar / card / panel / table action 中的实际占位和比例关系

也就是说，第 4 路线不能只看“大概像不像”，而要看每个实例级元素是不是保住了原始 HTML 的规格差异。

### 事实来源优先级

Stitch 路线承接时，视觉事实来源优先级必须写死：

1. 第一事实来源：Stitch 下载下来的 HTML
2. 第二事实来源：Stitch 下载下来的代码 / 样式 / MD 规范
3. 第三事实来源：Stitch 下载下来的截图

执行规则：

- 能从 HTML 直接确认的尺寸、结构、class、层级，不允许靠截图猜。
- HTML 没写清但代码 / MD 有写清时，可以用第二层证据。
- 截图只能做补充校对，不是第一依据。
- 能从 HTML 直接读出的实例级尺寸和控件规格，属于硬依据，不得在真实前端承接时擅自抽象、合并、重解释或改写成另一套通用规格。

### 控件规格盘点

拿到 Stitch HTML 后，不能直接开写，必须先做一次 `控件规格盘点`。至少盘点：

- 有几种按钮变体
- 每种按钮的高、圆角、padding、字体、图标尺寸
- 有几种图标尺寸
- 有几种输入控件规格
- 有几种 badge / pill / tag 规格
- 有几种卡片操作区布局
- 有几种 footer / toolbar / header 操作区布局
- 哪些区域属于高密度控件区
- 哪些区域最容易因为尺寸错误导致整体排版塌陷

这一步的作用是：

- 防止不同规格被误合并
- 防止写到一半才发现控件并不是一套尺寸
- 防止后续为了省事强行通用化

### 禁止过早抽象 / 通用化

视觉未对齐前，禁止为了工程整洁、复用、组件化、统一规范而主动做会改变视觉结果的抽象。

明确禁止：

- 把不同按钮变体合并成统一按钮组件规格
- 把不同图标场景合并成统一图标尺寸
- 把不同输入框、下拉框、textarea 做成统一控件高度
- 把头部按钮、卡片按钮、footer 按钮、纯图标按钮统一处理
- 把表格筛选栏、表格行高、操作列按钮、分页控件统一套成老项目默认规格
- 先抽象成通用组件，再反过来猜尺寸
- 把 Stitch 实例级 class 差异抹掉
- 为了“代码更漂亮”破坏视觉精度

只允许在已经按 Stitch 原始产物视觉完全对齐之后做局部抽象，而且抽象后：

- 不得改变尺寸结果
- 不得改变比例结果
- 不得改变排版结果
- 不得改变按钮 / 图标 / 输入框 / 表格规格
- 不得改变文本换行与占位行为

### 防老项目默认样式 / 组件规格带偏

第 4 路线不仅要防自己抽象过度，还要防真实项目现有样式体系、公共组件默认值和全局规则把控件规格带偏。

重点防这些情况：

- 复用项目现有 Button，默认高度和 Stitch 不一致
- 复用项目现有 Input，默认 padding 和 Stitch 不一致
- 复用项目现有图标组件，默认尺寸和 Stitch 不一致
- 复用项目现有 Table，默认行高、单元格 padding、工具栏规格和 Stitch 不一致
- 被全局 `button / input / svg / table` 样式覆盖
- 被公共组件库的 size variant 自动接管
- 被 reset / 主题变量 / 公共类名带偏

因此要明确：

- 样式必须优先局部作用域
- 高风险控件必须允许实例级覆盖
- 不能因为项目里已有组件就默认沿用它的规格
- 如果沿用现有组件，必须验证其最终视觉结果与 Stitch 一致
- 如果现有组件默认规格不一致，必须覆写到一致，而不是妥协

### 高风险对象范围

不能只盯图标、按钮、输入框。以下都属于 Stitch 路线一比一还原的高风险对象：

- 图标
- 纯图标按钮
- 普通按钮
- 头部胶囊按钮
- 卡片底部按钮
- footer 主按钮
- footer 次按钮
- toolbar 按钮
- 输入框
- textarea
- select
- checkbox
- radio
- switch / toggle
- badge / pill / tag
- 搜索框
- tab
- dropdown trigger
- 统计卡图标块
- 卡片操作区
- 菜单项
- 步骤卡片
- 进度条
- 分页控件
- 面板 / 抽屉 / 弹窗 footer 控件
- 表格 / 表头 / 单元格 / 筛选栏 / 操作列按钮
- 文本字号 / 行高 / 字重 / 字距
- 单行 / 换行 / 截断 / 竖排风险
- header / footer / toolbar / card action / table action 内的控件占位关系

### Stitch 真实前端承接提示词固定段

如果 Codex 后续要生成“根据 Stitch 文件落真实前端 UI 壳”的执行提示词，必须显式加入下面这段约束，不能只写“请根据 Stitch HTML 一比一还原”：

```text
实例级尺寸保真规则：
1. 必须优先保留 Stitch 原始 HTML 的实例级尺寸和间距。
2. 禁止把不同按钮合并成通用按钮尺寸。
3. 禁止把不同图标合并成统一图标尺寸。
4. 禁止把不同输入控件合并成统一规格。
5. 禁止把不同表格工具栏、表格行高、单元格 padding、操作列按钮规格统一掉。
6. 禁止为了封装牺牲原始 HTML 的 size / spacing / layout 差异。
7. 禁止先组件化再凭感觉回调视觉。
8. 如果原始 HTML 中某图标分别是 w-3 h-3、w-4 h-4、w-6 h-6，真实承接时必须保留这种差异。
9. 如果原始 HTML 中不同按钮属于不同变体，真实承接时必须保留这种变体差异。
10. 如果某控件在 HTML 中是固定高度、固定 padding、固定圆角，真实实现时不得随意统一。
11. 如果抽象不可避免，必须保证抽象前后视觉像素结果不变。
12. 如果项目技术栈不能原样表达某种实现，必须说明原因，并使用视觉结果等价的方案，不得自由发挥。
13. 必须防止老项目现有组件默认规格、全局样式和公共图标 / 表格规则干扰 Stitch 还原结果。
```

## Stitch 静态数据与依赖规则

第 4 路线的 UI 壳阶段，直接使用 Stitch MCP 下载下来的 HTML 里的静态数据。

- Stitch HTML 里有什么静态数据，UI 壳阶段就先用什么；
- 不要求 Codex 改写成另一套假数据；
- 不要求 Codex 重新设计 mock；
- 后续开发目标再把这些静态数据替换为真实 API 数据。

依赖规则也和普通外部 AI 路线不同：

- 不提前禁止 Stitch 依赖；
- 不强行要求 Codex 删除 Stitch 的依赖思路；
- 不因为“不能新增依赖”导致 Codex 开始模仿；
- 如果项目真实落地必须引入等价依赖或资源方式，Codex 应先说明，并按当前项目可行方式实现；
- 如果项目技术栈不能 100% 原样搬运某种 Stitch 表达方式，先说明原因、记录受影响元素，再使用视觉结果等价的方案；
- 核心目标始终是一比一还原 Stitch HTML 样式。

例外只能是实现路径例外，不能是视觉结果例外。

## mock/type 规则

Codex 要提前规划 mock 和类型文件。外部 AI 可以使用 mock 撑 UI，但不能把 mock 写成真实接口。

- mock 必须集中放置或在指定 mock 文件里，不允许散落在多个业务文件里。
- 不知道真实字段时，用 `MockXxx`、`UiShellXxx` 这类临时类型名。
- 标注 `待 Codex 接真实类型`。
- 不伪造后端返回结构。
- 不把临时字段写成正式 API 字段。

## 样式作用域规则

样式默认只能在当前 UI 壳范围内生效。禁止污染老页面、重写全局样式、替换 UI 组件库、修改全局主题变量、修改公共组件样式、修改 CSS reset，除非用户明确批准。

优先使用项目已有的局部样式机制：CSS module、scoped style、组件级 class、局部样式文件、页面专属样式文件。Codex 应优先为 UI 壳创建局部样式文件，并在提示词里要求外部 AI 只能写这些局部样式。

## 外部 AI 输入包和提示词

Codex 给外部 AI 的不只是提示词，而是完整输入包，至少包含：当前项目背景、技术栈、现有 UI 库/样式规范/设计系统、已确认文本视觉方案、可选视觉图/原型图路径、接入清单路径、允许编辑文件清单、每个文件用途、查看入口、样式作用域要求、预留接口要求、禁止事项、完成后输出格式。

目标是用户复制过去，外部 AI 就能直接干活，不需要再猜项目结构、文件路径、入口、接口怎么留。

外部 AI 输入包中的可复制提示词是完整执行提示词，不是几句施工摘要。它必须在 `3000–10000` 个字符内完整说明任务性质、当前场景、目标和完成结果、读取要求、修改范围、执行步骤、业务与安全边界、UI 专项要求、验证要求、完成后输出和收口条件；只能在一个 Markdown 代码块中交付，代码块外最多一句用途说明，不得在代码块后再追加施工要求。

外部 AI 提示词必须写清：这是项目真实前端 UI 壳，不是 HTML 原型，不是 demo；必须严格根据确认好的文本视觉方案，或“文本视觉方案 + 视觉图 / 原型图”创建；必须严格根据 UI 壳接入清单预留接口、状态、事件、mock、类型入口；只能编辑 Codex 指定的允许文件；不得自行新增、删除、移动、重命名文件；不得新增依赖；不得重写全局样式；不得替换 UI 库；不得接真实接口；不得补业务逻辑；不得伪造 API、权限、返回结构；样式只能作用于当前 UI 壳；如果文件不够，必须停止并说明需要 Codex 补哪些文件。

完成后必须输出：新增/修改文件清单、确认没有编辑白名单外文件、查看入口、是否新增依赖、是否改全局样式、mock 数据位置、预留接口清单、预留状态清单、预留事件清单、未完成业务逻辑、给 Codex 的接线说明、运行/预览方式。

## UI 壳接收检查

外部 AI 或 Codex 生成 UI 壳后，进入业务接线前，Codex 必须先做 UI 壳接收检查：看 `git diff`，确认是否只改了允许编辑文件，是否新增/删除/移动/重命名文件，是否新增依赖或改 lock 文件，是否改了全局样式、公共组件、主题、权限、后端、高风险文件，样式是否只作用于当前 UI 壳，是否能启动项目或通过最小验证，是否能通过正式入口或临时入口打开 UI 壳，是否严格根据确认好的文本视觉方案或“文本视觉方案 + 视觉图 / 原型图”创建，是否严格根据接入清单预留接口、状态、事件、mock、类型入口，mock 是否集中且清楚，文件是否可维护，是否同步更新 `10-UI壳接入清单.md` 和对应 `ui-shells/...md` 的接收检查结果。

如果是 Stitch 路线，不需要额外怀疑 Stitch 官方产物本身；检查对象仍然是 Codex 落到真实项目里的前端 UI 壳文件。重点检查：

- 是否落到了真实前端文件；
- 是否能在项目入口查看；
- 是否预留了接口；
- 是否没把 UI 壳完成说成业务完成；
- 是否能解锁后续开发目标接线。
- 图标尺寸是否与 Stitch HTML 一致。
- 图标按钮是否被放大或缩小。
- 按钮高度、宽度、padding、gap 是否一致。
- 不同按钮变体是否被错误合并。
- 输入框、textarea、select 的高度、padding、圆角是否一致。
- badge / pill / tag 是否大小失真。
- 表格、表头、单元格 padding、筛选栏、操作列按钮、分页规格是否被统一错误处理。
- header / footer / toolbar / card action / table action 的控件规格是否被统一错误处理。
- 文本是否因为控件尺寸错误被挤压换行、竖排、溢出。
- 排版流是否因为按钮 / 图标 / 输入控件 / 表格控件变大而被带坏。
- 是否存在“通用组件覆盖掉原始 HTML 实例级差异”的情况。
- 是否存在“沿用了老项目默认 Button / Input / Icon / Table 规格而没有覆写到 Stitch 一致”的情况。
- 是否存在“被全局样式或公共组件样式干扰而没有察觉”的情况。

接收检查不通过时，留在当前 UI 目标修壳或回写问题，不解锁开发目标接业务。

## Product Design Design QA 与 Stitch 复修分流

其他 Product Design 路线仍保留 Design QA。普通 Product Design 路线仅执行已触发的 Design QA：用户选择检查页面样式、当前为完整流程，或用户明确要求非 Stitch Product Design 高保真还原时，继续执行 `product-design:design-qa`、同图对比、必要的局部放大、`design-qa.md`、五大保真面、90% 最低相似度线和 actionable P0/P1/P2 收口规则。

第 4 条 Stitch 路线不调用 `product-design:design-qa`，不创建或更新 `design-qa.md`，不执行 90% 门槛，也不执行 P0/P1/P2/P3 Design QA 分级。Stitch 的视觉门禁固定为：

`$Stitch` / Stitch MCP 是官方 MCP；不需要怀疑官方产物本身，但必须检查 Codex 的真实前端承接。其他 Product Design 路线进行 Design QA 时，仍要把源视觉目标和实现结果放在同一张对比图中判断。

```text
初次承接真实前端 UI 壳
→ 初次接收检查
→ 结果只能是“可以进入实例级细节复修”或“初次承接受阻”
→ 自动交付固定实例级细节复修提示词
→ 复修通过后才允许生成业务接线 /goal
```

初次接收检查通过后，Codex 必须自动说明：

```text
为了防止页面的样式、布局、容器比例、字体字号、颜色、资源、层级、状态、响应式以及图标、按钮、输入框、表格等实例级细节与 Stitch 原始产物不一致，需要再执行一次完整视觉维度的实例级规格保真复修。
```

随后必须在一个独立 Markdown 代码块中完整输出 [Stitch-实例级细节复修提示词.md](../templates/Stitch-实例级细节复修提示词.md)。只允许按当前项目微调项目名、模块名、路径、技术栈、入口、验证命令、文件白名单和“不适用”项；不得缩短、概括、重写或并入其他阶段目标。

这一步不是只修图标、按钮、输入框和表格大小。固定提示词必须同等核对页面结构与布局、尺寸与间距、字体与文本排版、颜色和视觉样式、控件规格、图片和视觉资源、层级与组合关系、状态表现、响应式与不同视口；控件规格只是其中一个维度。项目微调只允许填充或替换项目事实、增加项目专属限制/文件/验证；不存在的元素必须保留检查项并标记 `不适用：当前 Stitch 原始产物中不存在该元素。`。不得删除任何固定词语、句子、列表项或章节。实例级复修提示词也必须保持 3000–10000 个字符，但必须通过固定正文和完整性校验。

## 开发目标衔接

后续 development 或 development-and-acceptance 目标以真实前端 UI 壳和接入清单为基线，负责真实 API 调用、状态管理、数据加载、表单提交、权限、路由、错误处理、交互事件、替换 mock 数据和内部测试。Stitch 只有复修通过后才能解锁开发目标。

深度和完整的开发目标必须读取真实存在且受影响的 `liran_docs`、UI 壳接入清单、相关模块文档和代码，不得编造路径。深度最后普通目标继续到已确认验收、回写和复测后等待用户检查；完整 development 只推进到 `内部测试通过`，由 acceptance 目标完成验收交接，正式归档由用户确认后独立执行。

## 4.4 UI 过程资料生命周期

总清单和单壳清单都必须写入当前任务 ID。任务最终验收后，先把仍有效的视觉、交互、状态、接口和接线规则写回当前模块与 `10-UI壳接入清单.md`；再把一次性外部 AI 输入包、Stitch 提示词、接收检查、实例级复修、截图对比和 Design QA 过程归入该任务的单任务归档。尚未完成、待复修或受阻的 UI 壳继续留在活动区，不得提前归档为完成。

## 回退机制

开发目标内发现 UI 壳结构、事件、状态、数据入口或样式作用域需修正时，在当前开发目标内更新文本视觉方案或 UI 壳说明、`10-UI壳接入清单.md` 和对应 `ui-shells/...md`，重跑 UI 壳接收检查后再继续接线和内测。这类范围内修正不回退目标编号、不改 N/M。如果必须重做已确认的视觉方向、深度重构布局/交互或重新走外部 AI/Stitch，则已超出原确认范围：当前目标标记受阻，回到 `$liran-plan` 重新确认和路由，不直接回退到已完成的 UI 目标。

## 禁止幻觉与默认禁止规则

外部 AI 和 Codex 都不得伪造接口路径、后端返回、权限字段，不得把 mock 写成真实数据，不得把没验证的入口说成可用，不得把 UI 壳完成说成业务完成。不知道的 API、字段、权限、路由、接口返回结构、业务规则，一律标 `待确认` 或 mock/schema 占位。

默认禁止新增依赖、替换 UI 组件库、重写全局样式、修改全局主题变量、修改公共组件样式、修改 CSS reset、修改后端代码、修改接口协议、修改数据库/migration、修改认证/权限/支付/数据删除等高风险逻辑、删除文件，除非用户明确批准。

## 纪律

- UI 方案是文档的可视化镜像，不是需求的二次创作。发现文档缺细节，回头补文档（功能二），不要在 UI 壳里临时编。
- UI 阶段默认产物是真实前端 UI 壳，不是独立 HTML 或 demo。
- UI 壳必须严格按确认视觉方案创建，必须严格按接入清单预留接口。
- 外部 AI 不得自行新增文件、依赖、全局样式或业务逻辑，只在 Codex 指定文件里生成 UI 壳。
- Stitch 路线必须严格根据下载下来的 HTML 样式和 HTML 静态数据一比一落真实前端文件，禁止自由发挥、禁止模仿式重画。
- Codex 接收检查通过后，后续开发目标才能接真实业务。
- 若项目已有设计规范/设计系统，遵循它。

## 关联

- **上游**：功能二的微观文档与已确认文本视觉方案（提供行为定义和视觉依据）。
- **中游**：`liran_docs/10-UI壳接入清单.md` 与 `liran_docs/ui-shells/...md`（提供 UI 壳施工合同）。
- **下游**：开发目标按接入清单接真实业务；最后普通目标按已确认验收责任完成真机验证或用户验收交接、问题回写和复测，用户确认“归档”后再执行独立正式归档。
