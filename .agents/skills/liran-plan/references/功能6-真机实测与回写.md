# 功能六 · 真机实测 + 问题回写 SOP

## 目的
把"看起来做完了"变成"真实环境确认可用了"。本功能要求在 UI 壳接线或代码达到可验证节点后，先完成内部验证，再用真实环境跑通关键链路，并把问题明确回写到文档、追踪和实测清单中。

## 适用
- 页面或 UI 壳接线已经能走主流程，但需要真实点击、输入、跳转、刷新验证。
- 代码已经开发完成并通过内部验证，但不能只凭日志、测试或肉眼判断就标完成。
- 插件、扩展、登录态、浏览器环境、系统弹窗等只有真实环境才能暴露问题的场景。

## 一个确认问题决定验收责任

四档的需求确认框只显示一个问题，同时确认需求和测试方式。原生选择框的问题、选项和描述全部使用纯文本，不用 Markdown 包装。涉及页面时可以选择：

选项一：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，也检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 需求没问题，改完后让 Codex 自己真机测试，不检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项三：$liran-plan 需求没问题，改完后我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

“Codex 自己真机测试”表示 Codex 负责打开真实入口、操作真实状态、记录证据、修复和复测。“不检查页面样式是否符合方案”只跳过视觉方案对比，功能、状态、错误和交互仍必须真实验证，且不能声明视觉还原通过。

“我自己测试”表示 Codex 完成内部测试后把状态更新为 `待用户验收`，向用户提供简短的测试入口、步骤和期望结果，然后停止在验收门禁。只有用户明确反馈通过，才能更新为 `用户验收通过`，再完成归档后进入 `已归档 → 已完成`。

深度流程的 documentation 目标准备 `liran_docs/09-真机实测.md` 或用户验收入口；最后 development-and-acceptance 目标完成真实验收、回写和修复复测后进入用户检查交接。完整流程由独立 acceptance 最后目标完成这些工作后同样等待用户检查；正式归档由用户回复“归档”后独立执行。

涉及页面的深度流程使用：

选项一：$liran-plan 需求没问题，直接生成完整提示词，改完后让 Codex 自己真机测试，也检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项二：$liran-plan 需求没问题，直接生成完整提示词，改完后让 Codex 自己真机测试，不检查页面样式是否符合方案（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

选项三：$liran-plan 需求没问题，直接生成完整提示词，完成后我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）

不涉及页面的深度流程可以选择 Codex 真机测试、我自己测试或在自由输入里要求重新判断深度流程。用户完成选择后已经授权对应验收方式，执行 `/goal` 时不得再问是否开始、是否继续或使用哪个工具。

Stitch 路线不调用 Product Design Design QA，但必须完成初次接收检查和强制实例级细节复修；其他明确高保真 Product Design 路线仍不提供跳过已触发 Design QA 的分支。

## 前置条件（强制）
1. 对应模块或流程已达到"UI 壳接线或开发完成"节点。
2. 已完成内部验证，状态至少为 `内部测试通过`。
3. Codex 真机分支已创建或准备创建 `liran_docs/09-真机实测.md`，并明确本轮要验证的范围；用户自己测试分支不强制创建完整真机清单。
4. 如果是 Codex 接力续测，只把本轮新增或受影响项放进 `liran_docs/09-真机实测.md`；上一轮已通过且本轮未受影响的项直接继承，不要重复实测。

## 4.3 编码前与验收前运行时合同

真机清单不是事后补交的报告。深度流程在编码前必须让 `09-真机实测.md` 产生真实 diff，写入真实入口、最短步骤、成功/失败标准、证据位置和受影响任务；所有尚未实际跑通的项目保持空白。标准、深度和完整流程还必须通过产物审计，确认清单、任务和追踪文件存在、内容非占位，并确实出现在本轮 diff 中。否则编码门禁保持锁定。

真机执行状态只能按状态机推进：`准备阶段 → 内部测试通过 → 待实测/待用户验收 → 进行中 → 问题回写 → 修复 → 复测 → 真机测试通过或用户验收通过 → 待用户检查 → 待归档确认 → 归档中 → 已归档 → 已完成`。内部单测、结构脚本或聊天中的“已准备”不能替代真实环境证据。

所有立即生成完整提示词的确认选项必须由同一个 canonical builder 生成，并统一带 `$liran-plan ` 前缀和固定末尾细节后缀；临时写成“Codex 真机测试”或“我自己测试”的裸选项不得交付。

真机准备属于档位执行门禁的一部分；流程合同、真实 diff 和编码解锁未通过前禁止编辑实现源码。

## 最后目标口径

最后目标按已确认的验收责任分支。轻量/标准是 single 1/1，深度是 development-and-acceptance 2/2 或 3/3，完整是 acceptance 3/3 或 4/4。任何档位都不得只验一行清单、只点一个按钮或只看一次日志就说目标完成。

最后目标的可复制普通 Goal 提示词必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同：写清真实入口、验收范围、操作顺序、成功/失败标准、工具路由、证据、问题回写、修复复测、安全边界、暂不归档和用户检查交接条件，并按任务复杂度控制长度。Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整模板和校验规则；适用的专项提示词仍保持 `3000–10000` 字符。

- Codex 真机分支：最后目标一次性跑完真实环境验收、回写、必要修复和复测，然后进入待用户检查；用户回复“归档”后再执行独立正式归档。
- 用户自己测试分支：最后目标准备真实入口、最短步骤、期望结果和失败反馈要求，更新为 `待用户验收`；收到用户反馈后继续同一目标。

可复制启动句（只是完整提示词的开头，不是可单独交付的成品）：

```text
你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。

请直接开始执行下面步骤，先读取 liran_docs/09-真机实测.md、liran_docs/04-开发追踪.md 和对应模块文档，再按真实环境验收、问题回写、修复、复测，不要先解释。
```

如果本轮验收有明确固定顺序、废弃口径或证据边界，就写进 `liran_docs/09-真机实测.md` 和最后目标提示词；没有就不写。

如果只是接力续测，本轮只追变更项和可能回归的点。

Codex 真机分支如果只完成局部实测，保持 `待实测`、`进行中` 或 `受阻`，并继续推进当前最后目标。只有本轮清单全部真实通过、问题回写和文档追踪同步完成后，才允许进入 `真机测试通过`，随后进入待用户检查；用户明确回复“归档”后才进入正式归档和 `已完成`。

## 4.4 验收后的归档确认

### 4.5 真机通过后的普通目标回收

真机清单全部真实通过、问题回写完成、修复复测完成并完成修改后评分后，最后普通目标必须立即结束并回收：goal_status=active → reclaim_pending → reclaimed，项目任务进入待用户检查，资料归档保持待归档确认。回收不创建归档、不更新索引、不清理活动区，也不输出“本次任务已完成并归档”。

用户检查已经脱离普通目标生命周期。用户发现问题时创建新的复修目标，不能重新打开原目标；用户提出新增需求时回到需求整理或需求变更；只有用户回复“归档”才生成独立 archive 目标。归档失败保留原普通目标 reclaimed 和活动资料。

`09-真机实测.md` 只保留当前待实测、失败和待复测任务。任务通过 Codex 真机或用户验收后，最后普通目标先把验收与问题结果写回当前模块并进入待用户检查；只有用户明确回复“归档”后，独立归档目标才更新长期事实、创建并验证单任务归档、更新索引并按任务 ID 从 `04/08/09/10` 移走本任务过程记录。历史成功轮次只在归档保留；需要回归时重新把受影响项列为当前待测。

归档失败时保留所有活动原文并标 `归档受阻`。取消、暂停关闭和被替代任务可以按对应关闭类型归档，但不得写成已完成。只有归档真实成功，最终回复才能写“本次任务已完成并归档”并给出真实路径和活动区清理结果。

## Codex 真机分支的全程托管规则

已明确授权全程自主执行且未指定用户自测时进入**全权托管模式**：默认由 Codex 完成真机和适用的页面样式检查，不再显示验收选择框。用户明确选择“我自己测试”时，以用户自测为准，内测后进入 `待用户验收`。`@Chrome` 无法完成时自动切换 `@电脑`；任何可执行步骤都不得转交用户。客观无法继续时只记录为 `受阻`，不请求用户介入。

真机实测阶段默认交给 Codex 执行。进入本阶段即视为用户已经预授权 Codex 开始真实环境实操；无需再单独询问是否开始、是否继续或使用哪种工具。Codex 自主选择工具、打开入口、点击、输入、刷新、重载、检查反馈、回写问题、修复并复测，直到跑通。

只有四类真实硬性阻塞才允许请求用户介入或改判 `受阻`：

- 缺少必须由用户提供的账号、权限、密钥、私有文件或外部系统访问权限
- 当前环境完全无法运行必要工具，且没有任何替代验证方式
- 任务涉及安全、法律、隐私或平台规则限制，导致无法继续
- 用户要求本身互相冲突，且无法通过合理默认策略自行选择

如果失败，先回写问题，再修复，再复测；如果页面外观看起来像某种状态，但脚本日志、运行状态、结果页没有明确字样，就不能算通过。除上述四类真实硬性阻塞外，不要把“需要用户确认是否继续”或“先让用户选择工具”当作停止理由。

## 工具选择规则
Codex 根据目标环境与链路，自主选择最贴近真实使用方式的能力：

- `@浏览器`：适合 localhost 页面、普通网页流程、纯浏览器交互验证。
- `@Chrome`：适合需要真实 Chrome 会话、登录态、标签页、扩展、用户已有 Cookie/配置的场景。
- `@电脑`：适合桌面级操作、系统窗口、Chrome 扩展管理页、拖拽、多窗口切换或 `@Chrome` 无法覆盖的系统交互。
- 命令行、接口客户端和项目现有集成工具：适合 CLI、服务、接口、数据处理、部署预演和非 UI 集成环境验证。

选择原则：
- 能用 `@浏览器` 跑通的普通页面，不要先上更重的桌面控制。
- 只要验证依赖真实 Chrome 用户态、扩展或现有标签页，就优先使用 `@Chrome`。
- 涉及系统级动作、扩展刷新页、浏览器外的窗口操作，或 `@Chrome` 无法点击、输入、拖拽、切换窗口、处理系统弹窗时，`@Chrome` 无法完成时自动切换 `@电脑`，从当前步骤继续。
- 工具切换由 Codex 自行完成，不得要求用户代为操作；只有本 SOP 列出的真实硬性阻塞才能请求用户介入。
- 非 UI 任务使用最接近真实使用方式的 CLI、服务、接口或集成入口，不为满足“真机”字面含义伪造页面操作。

## 真机实测前要创建什么
在目标项目的 `liran_docs/` 下创建或更新 `09-真机实测.md`：

- 这是项目级的真机实测总清单。
- 大项目可在同一文件下分章节，也可按模块拆分多个文件；若拆分，仍建议保留一个总索引入口。
- 清单必须使用强约束结构：标题、参考真源文件、本轮信息、跑通总规则、实操打勾流程、按步骤分段的跑通表、问题回写记录。
- 每个步骤都必须独立成段；只有当前步骤全部 `✅` 后，才允许进入下一步。
- `跑通` 列默认留空；没有真实成功，不允许预先填写 `✅`。
- 可直接参考 [功能6-真机实测示例-web.md](功能6-真机实测示例-web.md) 作为 Web 项目的成品样板，再替换成你的真实模块与链路。
- 如果是接力续作，清单只列本轮新增或受影响项；已通过且未受影响的项直接继承。

## Codex 真机分支操作步骤
1. **确认范围**：从 `liran_docs/09-真机实测.md`、`liran_docs/04-开发追踪.md` 和模块文档中明确本轮是验证整个项目、某个模块、还是某个关键交互，不为范围确认单独询问用户。
2. **准备清单**：创建或更新 `liran_docs/09-真机实测.md`，把待验证项按真实操作顺序拆成表格行。
3. **切状态**：在 `liran_docs/04-开发追踪.md` 把对应模块从 `内部测试通过` 更新为 `待实测`。
4. **选择工具**：按本 SOP 的工具规则自主决定用 `@浏览器`、`@Chrome`、`@电脑` 中的哪一个，必要时组合使用，把选择写入清单或执行记录，不询问用户。
5. **按清单实操**：严格按照"触发方式 / 前置条件 / 核心链路 / 成功标准 / 失败标准 / 复测方式"逐项验证。
6. **打勾或记失败**：只有真实操作成功的项才能在 `跑通` 列填写 `✅`；失败项要写清问题现象。
7. **问题回写**：把失败项同步写回：
   - `liran_docs/09-真机实测.md` 的问题回写记录
   - `liran_docs/04-开发追踪.md` 的状态与备注
   - 对应模块文档或叶子交互文档
   - 必要时 `liran_docs/08-测试用例.md`、UI 壳接入清单、页面入口或架构文档
8. **修复并复测**：修复后重新走真实操作；若修复期间继续推进，则状态回到 `进行中`，卡住则改 `受阻`。除客观外部阻塞外，持续修复和复测直到跑通。
9. **收口**：当对应清单全部通过、回写完成且无未处理回归时，把状态更新为 `真机测试通过`，随后按 `goal_status=active → reclaim_pending → reclaimed` 回收最后普通目标，并把项目状态写为 `待用户检查`、资料归档状态保持为 `待归档确认`。只有用户明确回复“归档”后，才启动独立 archive 目标；归档真实成功并确认追踪、索引和活动文档一致后，才允许标 `已归档 → 已完成`。

## 结构性校验兜底（机制辅助，不替代人工判断）

在把状态更新为 `真机测试通过` 之前，先跑一次仓库自带的结构校验脚本：

```bash
python3 scripts/check_real_test_checklist.py liran_docs/09-真机实测.md --require-complete
```

这个脚本只做结构门禁，不替代真实操作。至少检查：
- 找出打了 `✅` 但那一行仍留着模板占位符（形如 `<...>`）没填的行——这种大概率是复制模板后忘记替换成真实内容就打勾。
- 找出前一步骤没有全部 `✅`、但后一步骤已经出现 `✅` 的情况——这违反了“当前步骤没打满不能进入下一步”的门禁规则。
- 检查是否存在连续编号的步骤、每个步骤是否有合法表格、必填列是否存在、已勾行的必填证据列是否非空、`跑通` 是否严格等于 `✅`，以及准备标记完成时是否所有行都已通过。

**脚本只能抓机械性的结构漏洞，不能、也不会判断“这些 ✅ 对应的真实操作是否真的发生过”。** `--require-complete` 返回 0 只代表步骤、表格、必填列、编号、状态和完成门禁在结构上成立，**不代表真机验证真实可信**。是否真的做了真实操作、问题回写是否属实，仍然由本 SOP 的证据纪律和 Codex 的如实执行负责。

## 问题回写规则
- **回写到文档，不只回写到脑子里**：任何真实问题都必须落字，不允许口头记住就算。
- **先修文档预期，再修实现**：如果问题暴露的是需求或交互定义缺失，先补文档，再改 UI 壳接线或代码。
- **通过就先打勾**：本轮一项真实通过就立刻回写 `✅`，不要等整轮结束后再统一补。
- **失败会撤销已通过项**：如果后续改动把之前打 `✅` 的项改坏，必须撤销该项并重新实测。

## 验收纪律
