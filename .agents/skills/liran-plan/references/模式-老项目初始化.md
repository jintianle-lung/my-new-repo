# 模式 · 老项目初始化式 SOP

本模式中供用户直接复制执行的普通 Goal 提示词，必须遵守 [通用完整执行提示词规范](../templates/通用完整执行提示词规范.md) 的文件指针型短合同；专项提示词继续使用各自完整模板和校验规则。扫描启动句、澄清问题、选择框、进度和阻塞说明不属于完整提示词。

## 适用
目标项目**已有代码/结构**，但缺少（或不完整）本技能的文档体系。目的：让 AI 先**了解现有项目**，**逆向构建**出文档树，帮用户更了解自己的项目，再去完善与继续开发。

## 先评分，不自动完整化

“老项目”只是项目背景，不等于必须重建整套文档。Codex 先只读调查当前代码、文档、测试、调用方和 Git 状态，按五项 `0–20` 分模型完成修改前评分：

- 单点 Bug 或局部小改动可以进入轻量流程。
- 同一模块或有限业务链进入标准流程。
- 跨模块、共享逻辑、高风险或复杂验证进入深度流程。
- 只有同时新增三个或以上独立功能模块、整体架构重构、大规模数据或技术栈迁移、多个大型模块同时改造、项目事实严重混乱或用户明确要求完整流程时才进入完整流程。

如果只是修复或新增少量功能，不因为缺少完整 `liran_docs` 就机械创建整套体系。信息未知时至少打 `1`，关键影响未知打 `2`，先查证后再决定档位。

## 判断是不是老项目
- 已有实质代码、目录结构、依赖配置。
- 用户描述为"我这个项目……""帮我梳理现有的……"。

## 逆向构建流程
以下步骤只在评分和项目级条件已经判定为完整流程时执行。轻量、标准和深度流程只读取完成当前任务所需的最小范围，并按对应档位定向更新。

4.6 当前节奏：完整非 UI 使用 documentation 1/3 → development 2/3 → acceptance 3/3；完整 UI 在文档后插入 ui 2/4，共 4 次。本节后文中若出现旧的“第一/第二”口径，必须按文档/UI/开发/验收的新阶段映射执行；UI 目标不接真实业务，最后 acceptance 目标完成验收后先等待用户检查，用户回复“归档”后才执行独立归档。

无论最终档位如何，只要当前是具体项目修改任务，就在需求整理首轮创建或复用一份聊天式需求整理文档；用户确认整理完成后再生成独立正式 PRD。路径依次取用户指定、项目 `AGENTS.md`、`03-索引.md`、既有同类目录或同任务文件；仍不明确就询问。轻量只建需求整理文档，不因此逆向生成完整文档体系。

1. **扫描与理解**（只读，先不改代码）：
   - 读 README、package/依赖清单、目录结构、入口文件、配置。
   - 识别技术栈、主要模块边界、对外接口、数据模型。
   - 必要时让用户补充：项目背景、目标用户、哪些是核心功能。
2. **读取旧文档兼容**：如果已有旧 `docs/`，先当作历史资料来源读取；后续新增和维护优先落到 `liran_docs/`。
3. **完整流程多轮需求整理**：只有评分和项目级条件判定为完整流程时，才整理用户要新增、续作、修复、删除，还是属于“其他”非标准需求；用户未说“需求整理好了/总结好了”前，不写代码、不拆任务、不开 `/goal`。
   - 每轮先更新需求整理文档，再只回复新增、变更、待确认点和真实路径，末尾问“整理好了吗，还需要补充吗？”；用户要求全文或进入集中确认时才输出完整总结。
   - 用户说“需求整理好了/总结好了”后，读取需求整理文档重新归纳生成独立正式 PRD、建立 PRD 索引并在对话输出，等待用户回复“PRD 没问题”；确认后在同一个纯文本确认问题里让用户选择 `$liran-plan Codex 真机测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）` 或 `$liran-plan 我自己测试（额外要求：生成提示词里面的目标需求需要详细，不漏一点细节。）`，然后才进入 `liran_docs` 一次性补齐流程。
   - 保留这句口令：`[$liran-plan](../SKILL.md) 整理好了或者需求整理好了或者总结好了`。用户说出这句或等价表达时，都视为进入总结确认阶段。
4. **建文档骨架**：创建 `liran_docs/`，放入 `用户原话.md`（记录用户对项目的口述背景）。
5. **逆向回填顶层文档**：
   - `00-项目说明书.md`：根据代码 + 用户口述，归纳项目是什么、为谁做。**推断的内容要标注"待用户确认"。**
   - `02-架构文档.md`：依据真实代码结构画出现有架构、技术栈、模块划分。
   - `01-需求文档.md`：从已实现功能反推现有需求清单（标注哪些是推断）。
6. **建索引与模块树**：`liran_docs/03-索引.md` 按代码现状画模块树 + 横向依赖；`liran_docs/modules/` 下为每个真实模块建 `_X.md`，逐步细化到关键交互；同步建 `04-开发追踪.md` 标记各模块真实状态。
7. **校对结果写回**：前面的详细总结确认已经是本轮唯一事实确认。仍无法确认的推断在文档中标记 `待确认`，不得在文档和任务之间新增第二次逐项确认门禁。
8. **功能二 + 功能五（合并为一步）：文档补齐后一次性拆完全部已确认需求**：在同一条提示词、同一步里，把本轮全部已确认需求（新增/续作/修复/删除）一次性拆成可执行的微观任务，不分批、不留尾巴。补齐后再判断是否需要真实前端 UI 壳五路线（功能三）。
9. **完整流程中的真实前端 UI 壳与已有前端兼容**：判定为完整流程且本轮涉及 UI 时，进入真实前端 UI 壳五路线，不生成独立 HTML 或 demo。已有前端或前端 + 业务代码场景下，先确认目标页面/组件/模块、优化范围、是否允许改布局、是否允许改交互、哪些业务逻辑不能破坏、验收标准。五条路线为：`Codex 直接生成前端 UI 壳`、`@product-design`、`@product-design + 外部 AI 生成前端 UI`、`@product-design + $Stitch / Stitch MCP`、`@product-design + Codex 内嵌 Gemini 或其他生成的好看的模型生成前端 UI`。第五路线由 `@product-design` 先确认文本视觉方案，再由 Codex 通过 OpenCodex 本地路由在当前会话内选择 Gemini 或其他实际可用模型生成 UI 壳；不复制提示词到外部软件、不维护固定模型白名单、不新增强制模型选择框，并继续执行 UI 壳接入清单、文件白名单、样式隔离、接收检查和非 Stitch Design QA。造壳前 Codex 必须先生成 `liran_docs/10-UI壳接入清单.md` 和对应 `liran_docs/ui-shells/...md`，规划文件、创建合法占位文件、安排入口、准备 mock/type/局部样式/注释锚点，并写清允许编辑文件清单。外部 AI 只能在 Codex 指定文件里生成 UI 壳，不得自行新增、删除、移动、重命名文件，不得新增依赖、重写全局样式、替换 UI 库、接真实接口或补业务逻辑。若选择 Stitch 路线，必须先确认文本视觉方案和可选视觉图，再由 Codex 追问 `视觉方案确认好了吗？`，确认后生成 Stitch 提示词，等用户提供 `$Stitch` / Stitch MCP 信息后，先更新 UI 壳接入清单和合法占位文件，再下载 Stitch 文件并严格根据 HTML 样式和 HTML 静态数据一比一还原到真实前端文件；Stitch 不负责预留接口，预留点由 Codex 根据接入清单补上。开始真实前端承接前，必须先做 `控件规格盘点`，并按事实来源优先级读取：第一事实来源是 Stitch 下载下来的 HTML，第二事实来源是 Stitch 下载下来的代码 / 样式 / MD 规范，第三事实来源才是截图。真实落地时必须执行 `实例级尺寸保真规则`：禁止把不同按钮、图标、输入控件、表格规格统一掉，禁止先组件化再凭感觉回调视觉，禁止被老项目默认 Button / Input / Icon / Table 规格、全局样式和公共组件样式带偏。UI 壳必须严格根据确认好的文本视觉方案，或“文本视觉方案 + 视觉图 / 原型图”创建；预留接口、状态、事件、mock 和类型入口必须严格根据接入清单创建；样式默认只能在当前 UI 壳范围内生效，不能污染老页面或全局样式。如果是非 Stitch Product Design 路线且有真实图片或视觉方向图，最终真实前端 UI 壳截图必须达到 90% 以上高还原；布局主要结构、样式、配色、字体字号、间距、层级和状态要贴近原图；按钮、输入框、输出框/结果区、表单、表格、列表、卡片、导航、菜单、弹窗、图标、图片、提示、加载/空/错误状态和交互状态等所有可见前端元素都要纳入 QA。QA 不能挤牙膏：每轮先批量差异盘点，按 P0/P1/P2/P3 分级，优先批量修 P0 + P1 并尽量合并处理 P2；Product Design 路线必须更新 design-qa.md，只有没有 actionable P0/P1/P2 才能 passed。Stitch 路线不执行 Product Design Design QA；初次接收后必须自动交付固定实例级细节复修提示词，复修通过后才允许进入业务接线。UI 壳完成后 Codex 必须先做 UI 壳接收检查；接收检查不通过时，先修 UI 壳或回写问题，不进入后续 development 目标接业务。
   - Stitch 初次接收后的固定复修要同等检查结构布局、尺寸间距、字体排版、颜色样式、控件规格、图片资源、层级组合、状态和响应式。项目微调只能补充或替换事实，不得删除固定正文；不适用元素仍保留规则并标记。实例级复修提示词也必须保持 3000–10000 个字符，也不走普通流程合同。
10. **进入开发与收口**：documentation 通过后，如适用先执行唯一 ui 目标，再执行 development 内部闭环；所有中间目标禁止归档。acceptance 最后目标按已确认责任完成真实验收、回写和修复复测后进入待用户检查；用户明确回复“归档”后才执行安全归档，只有 `已归档` 后才能标记 `已完成`。

## 纪律
- **先理解，后下笔**：逆向文档必须基于真实代码，不臆造。
- **明确区分"现状"与"推断"**：凡是 AI 推断而非代码明证的，标注待确认。
- **不擅自改代码**：本模式只建文档；改代码走功能五的任务流程，且需用户确认。
- **允许回退**：如果后面发现方向不对，可以回到前面的任一步重新整理需求、补文档、重做 UI 壳或重拆任务。
