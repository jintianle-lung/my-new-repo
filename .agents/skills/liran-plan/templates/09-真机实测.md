## 跑通总规则

> 以下打勾规则只用于 Codex 真机测试分支。用户自己测试分支使用上面的用户验收状态，不伪造 Codex 真机 `✅`。

1. 任何按钮点击后必须有真实动作或明确中文提示，不能静默无反应。
2. 任何输入框、下拉框、开关都必须能真实影响后续流程，不能只是 UI 样式。
3. 任何状态展示都必须来自真实数据或真实状态机，不能长期显示静态示例。
4. 任何弹窗必须能验证打开、确认、取消、关闭四种行为。
5. 任何后台能力必须能从 UI 触发到真实 controller、background、native host、服务端或真实存储。
6. 任何正式结果必须校验项目定义的关键输出；缺少关键字段、关键状态或关键文件，就不算跑通。
7. 任何后续修改导致已打 `✅` 的项失败，都必须撤销该项 `✅` 并重新修复。
8. 每一项打 `✅` 前，必须先完成 UI 壳接线或代码的内部验证，再使用 `@浏览器`、`@Chrome` 或 `@电脑` 进行真实实操验证。
9. 真实实操验证必须包含必要的刷新、重载、重新进入步骤，确保不是旧状态侥幸通过。
10. 只有实操成功的行才能打 `✅`；没有成功、只看代码、只看日志、只理论判断，都不能打 `✅`。
11. 当前步骤下的全部行都打 `✅` 后，才允许进入下一步；如果任一行失败，必须停在当前步骤修复并复测。
12. 后续步骤开发过程中如果改坏前面已打 `✅` 的行，必须撤销该行 `✅`，回到对应步骤重新修复和实操验证。
13. 选择 Codex 真机测试后，自主选择工具并持续实操、回写、修复、复测，直到跑通。
14. 只有四类真实硬性阻塞才允许标 `受阻` 并请求用户提供最小必要信息，细则见 `README.md` / `功能6-真机实测与回写.md`。
15. 如果本轮验收确实有明确固定顺序、废弃口径或证据边界，就写在“本轮信息”或步骤备注里；没有就留空或不写。
16. 页面外观看起来像某种状态不代表真的通过，必须以脚本日志、运行状态、结果页里的明确字样为准。

## 实操打勾流程

每一项从空白变成 `✅`，必须按下面顺序执行：

1. 内部验证：检查代码链路、状态来源、存储读写、错误处理和相关测试。
2. 环境准备：根据实际场景使用 `@浏览器`、`@Chrome` 或 `@电脑` 打开真实入口，并完成必要刷新、重载、扩展重载或系统级准备。
3. 页面或应用重载：确认最新代码、最新 UI 壳接线、最新配置已生效。
4. 单项实操：按照该行“触发方式”和“复测方式”真实点击、输入、切换或等待自动流程。
5. 成功确认：同时满足该行“卡点验证”和“成功标准”，且没有触发“失败标准”。
6. 打勾记录：只给当前已经实操成功的本轮行填写 `✅`；同一未归档任务的继承项可保留原勾。
7. 阶段门禁：当前步骤本轮必测项都 `✅` 后，才能继续下一步；同任务继承项不占门禁。
