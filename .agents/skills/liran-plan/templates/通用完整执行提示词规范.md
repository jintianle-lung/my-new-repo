# 通用完整执行提示词规范

本文件是 `liran-plan` 生成可直接复制执行提示词时的通用质量合同。普通目标提示词采用短版文件指针格式；Stitch、外部 AI、Product Design、生图等专项提示词继续使用各自完整模板。

## 适用范围

下列普通目标提示词必须遵守本规范的短版合同：轻量/标准 single `/goal`；深度和完整流程的 documentation、ui、development、development-and-acceptance、acceptance 阶段 `/goal`。正式归档使用独立 archive 模板，不计入普通目标数量；外部 AI、Stitch、Product Design、生图等专项提示词使用各自模板和校验器。

普通澄清问题、Codex 原生选择框、进度更新、状态说明、阻塞说明、一句话原因、文件路径、单条命令、启动句和用户明确要求的简短自然语言回复不属于完整执行提示词，不强制扩写到 3000 字符。

## 字符与细节门禁

- 每条完整执行提示词的第一行必须原样使用：`你自行判断本任务是否需要多智能体协作；如需开启，只允许一个主智能体统筹，任一时刻最多同时运行五个子代理，子代理完成后必须及时回收，回收后可按需启用新的子代理，禁止子代理继续派生代理。`
- 是否启用多智能体由执行者根据任务范围、可并行性和收益自行判断，不得为了形式强制开启。启用时只有一个主智能体，任一时刻的子代理并发上限为五个；子代理完成、失败或确认无需继续时必须及时回收，释放并发名额后可按需再启用新的子代理，因此不限制整个任务历史上的子代理累计数。子代理不得再派生新代理；各子代理必须有独立、不冲突、能产生实际价值的责任范围。
- 普通目标提示词不设 3000 字最低门槛，长度按当前任务复杂度决定；专项提示词是否有长度门槛，以专项模板和校验器为准。
- 禁止重复句子、同义改写、空话、无意义背景或大量“不适用”机械凑字。
- 接近 10000 字符时先合并重复说明，不得删除目标、范围、安全边界、验证、输出或收口条件。
- 允许使用“以正式 PRD 当前内容为准”等文件指针，但必须列出真实路径、执行范围、验证和完成条件。
- 普通目标提示词不得大段复制 PRD、模块、测试或真机正文；专项提示词继续执行自身的长度、固定正文和完整性规则。

## 普通目标短版合同

专项完整模板仍可使用以下标准结构名称作为校验字段：任务性质、当前场景、目标和完成结果、读取要求、修改范围、执行步骤、业务与安全边界、UI 专项要求、验证要求、完成后输出、收口条件、任务文档与归档合同。

每条普通目标提示词必须明确以下字段：

1. **任务 ID、流程档位、修改前评分、阶段和目标 N/M**。正式 PRD 转换完成后必须先完成五维评分和流程分级；目标提示词必须携带当前流程等级和修改前评分，不能只写目标编号。
2. **必须读取的真实文件**，至少包含正式 PRD 和本阶段相关文档。
3. **允许修改范围与禁止范围**。
4. **验证要求与状态回写位置**。
5. **完成条件与下一阶段解锁条件**。
6. **必要的安全、UI、外部等待或归档边界**；不适用时用一句具体原因说明。

普通目标不需要复制 PRD、模块、测试、真机或 Goal 正文；以正式 PRD 和对应执行文档当前内容为准即可。专项提示词不得套用本短版合同，继续执行专项固定结构。

## 交付格式

- 代码块外只保留一句必要的用途或原因说明。
- 代码块内第一行必须是固定多智能体判断句，第二段再开始写“请直接开始执行”和当前任务正文。
- 完整提示词只放在一个独立 Markdown 代码块中，不得拆成多个代码块，不得在内部嵌套三反引号。
- 代码块后不得再追加执行要求，也不得继续补充遗漏的执行要求。
- 提示词必须根据当前项目填入真实的项目名、模块、文件、入口、技术栈、验收责任和验证命令。只有用户明确要求通用版时才保留清晰占位符。
- 用户在 Codex 原生选择框中完成选择后，必须在同一轮自动交付完整提示词，不得再要求用户说“生成提示词”或“继续”。

## 普通目标与正式归档边界

中间目标使用 non-final；最后一次普通目标使用 handoff。最后一次普通目标只完成开发、测试、验收、问题回写、必要修复和复测，然后进入“待用户检查 → 待归档确认”；不得创建归档、更新索引、清理活动文档、标记已归档或标记最终已完成。固定通知用户检查软件并在没有问题时回复“归档”。只有收到用户明确回复“归档”后，才读取并执行 templates/任务正式归档目标提示词.md，正式归档成功后才允许输出“本次任务已完成并归档”。旧 final 仅按 handoff 兼容，full-first 仅按 non-final 兼容。

## 收口标准

只有当最终可复制正文符合长度范围、标准结构齐全、项目事实已填充、不存在摘要替代和重复凑字、交付仅有一个代码块，且不会误报未验证状态时，才算通过通用提示词质量门禁。中间目标使用 `--archive-stage non-final`，最后目标使用 `--archive-stage handoff`；正式归档使用 `--prompt-kind archive`。校验失败时不得交付。

## 编码解锁硬规则

## 最后普通目标回收合同

最后一次普通目标完成真实验收、问题回写、修复复测和修改后评分后，先把当前目标写入 goal_status=reclaim_pending，保存 goal_completion_evidence，完成真实回收后再写入 goal_status=reclaimed。普通目标回收只关闭当前 N/M 目标，不改变项目最终完成状态。

回收完成后必须同时保存 task_state_after_goal=待用户检查、archive_state_after_goal=待归档确认、用户检查通知及其证据。普通目标回收不等待用户回复“归档”，不创建归档包，不更新归档索引，不清理活动区，也不能输出“本次任务已完成并归档”。

reclaim_pending 表示回收申请已经发起但尚未确认成功；回收 API 失败时必须保留该状态并记录原因。平台没有目标回收 API 时，使用流程合同中的 reclaimed 表达运行时目标已停止，并停止继续生成同一目标命令。重复回收必须幂等，不能重复计数、重复通知或启动 archive。

用户检查属于项目任务状态，不属于普通目标执行状态。用户发现原需求问题时创建新的复修目标，不能把原目标重新设为 active；用户提出新增需求或优化时回到需求整理或需求变更。只有用户明确回复“归档”后，才创建独立 archive 目标；archive 目标不计入普通 N/M，且归档成功后自身也必须完成并回收。

“已更新文档”“已拆完任务”“已准备真机”只有在真实文件存在、内容非占位、任务编号与影响文件齐全、对应文件产生真实 diff，并有命令输出作为证据时才算成立。深度和完整的 documentation 目标未通过产物审计时，禁止解锁 ui 或开发目标。
正式 PRD 转换完成后必须评分并确定流程等级，目标提示词必须携带五维评分、总分、评分证据和当前流程档位；评分、正式 PRD、任务拆分、微观任务、索引和用户原话检查未通过前，不得生成或执行目标提示词。
