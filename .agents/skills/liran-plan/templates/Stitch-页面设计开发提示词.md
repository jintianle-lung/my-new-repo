# {系统题目} — Stitch 多页面设计提示词

额外设计约束：
（0）视觉风格整体要清爽明亮，禁止使用深沉压抑的配色（禁止米黄、奶油、深棕、暗金等暖旧色系，禁止纯黑或接近纯黑的深色背景），具体配色、排版、组件样式自由发挥，以轻盈、有光感、透气为方向。
（1）信息密度：每屏只有一个主角元素，其余全部降权；每个页面功能模块最多保留3个，超出的合并或隐藏到次级页面；列表每行只显示标题+1个状态+1个操作，禁止堆叠副信息。
（2）文字克制：每个组件内文字不超过2行；禁止在任何UI组件内出现段落描述、产品介绍、技术说明；禁止展示开发注释（路由路径、API标签、英文技术副标题、状态机标识）；导航菜单只显示标签名，禁止在菜单项下方添加任何说明文字。
（3）色彩纪律：全局强调色只用1个，状态色共用1套，总计不超过4色；优先级和分类差异用形状或位置区分，不新增颜色；禁止同一屏内同时出现超过2种状态色。
（4）层级与留白：用尺寸和留白区分主次，禁止所有模块等宽等高平铺；区域分隔靠留白完成，禁止用分割线或描边堆砌结构；主操作区、数据区、列表区之间留白不少于内容区高度的20%。
（5）一致性：全站所有页面共用同一套背景色、组件色、字体，禁止跨页面出现两种风格；每个视图只保留1个主操作按钮，其余收进溢出菜单；标签最多显示2个，其余折叠为+N。
（6）必须删除：一切以填充空间为目的存在的文字或图标；没有点击行为的装饰性元素；与页面标题或导航重复的区块标题；用户不会主动需要的系统运行信息。
（7）组件克制：禁止在同一屏内堆叠超过3种不同的组件形态；弹窗和抽屉只在用户主动触发后出现，禁止自动展开的浮层干扰主界面。
（8）空白保护：任何内容区域的填充率不超过70%，剩余30%必须保持空白；禁止为了看起来饱满而填充占位内容、示例数据或说明性文字。

> 本段为用户明确指定的强制设计约束，优先级高于本文其他视觉自主规则；Stitch 只在不违反本段的范围内自由发挥。

> 本段也优先于已确认文本视觉方案中的风格描述。视觉风格可以写入后文，但不得突破本段。

> 用途：把本提示词整体交给 Google Stitch，完成本项目的全部页面视觉设计。占位内容必须已从 `liran_docs` 正式 PRD、功能树、模块文档、完整页面清单和已确认文本视觉方案填实。设计完成后请回传 Stitch Project Title、Stitch Project ID、Stitch Screen Name、Stitch Screen ID；Codex 再用 `$Stitch` / Stitch MCP 读取 HTML、样式、静态数据、图片、代码和 MD 规范，一比一落到真实前端 UI 壳，随后进入实例级细节复修。Stitch 不负责预留接口，不接真实业务逻辑。

## Stitch 任务边界

本提示词只交给 Google Stitch 做视觉设计，不是 Codex `/goal`。目标是完成已确认完整页面清单中的**全部屏幕及其关键状态**；生成一个示例屏幕、草稿屏幕或只完成主流程都不算完成。

- 所有描述使用具体词，不使用抽象词；尺寸必须写死为具体数值；页面区块必须分层书写。
- Stitch 根据项目业务、端形态、内容密度和可用空间自行决定设计系统、页面壳层、导航位置（顶部/侧边/底部/标签/上下文/浮动/无全局导航）、布局和视觉风格；本提示词中任何颜色、字体、像素、栅格或导航示例均仅为语义参考，不是固定模板。上述自主权不得突破文首“额外设计约束”。
- 普通设计决策、屏幕命名、变体补齐、预览和交付整理直接自主完成，不逐项询问用户。
- 页面数量不设置固定上限或下限。页面清单有几个页面，Stitch 就生成几个页面，不得遗漏，也不得自行增加。
- 独立路由或独立业务界面默认计为页面；弹窗、抽屉、面板、组件和 loading / empty / error / success 等状态默认归属对应页面，不额外计数，除非已确认清单明确把它们定义为独立 Screen。
- 如果 Stitch 单次无法生成全部页面，可以分批生成；所有批次最终必须覆盖完整页面清单，页面总数、名称、职责和关系不得漂移。
- 若某模块与当前产品形态无关，直接标注“不适用”并说明原因。
- Stitch 不负责预留接口。完成后按第七节回传屏幕标识，由 Codex 落到真实前端 UI 壳。

## 四、每个屏幕的详细设计要求

按 PC 端 `PC-P01` 至 `PC-P{N_PC}`、移动端 `M-P01` 至 `M-P{N_M}` **逐端逐页输出以下完整结构**，不允许只写标题。单端项目可沿用 `Pxx`，但必须明确另一端为 0 页：

### P{编号} — {页面名称}

1. **屏幕元数据**：端、Stitch 屏幕名称、建议尺寸/方向、路由、可访问角色、进入条件、返回路径。
2. **布局骨架**：先判断是否需要页面壳层和导航，再写出实际采用的顶部/侧边/底部/页内/混合布局或“无全局导航”，以及内容容器、列数、固定/滚动区域、响应式断点和关键尺寸。不得默认包含顶部导航或左侧栏。
3. **视觉层级**：页面标题、摘要指标、主操作、次操作、危险操作、状态标签、空状态和帮助信息的优先级。
4. **组件清单**：逐个列出 Button、Input、Select、DatePicker、Table、Card、Tabs、Pagination、Modal、Drawer、Toast、Skeleton、Empty、Error 等实际使用组件及状态。
5. **字段/列定义**：字段名、展示标签、类型、是否必填、示例值、格式化、校验错误文案、可编辑性、脱敏规则。
6. **真实语义数据**：至少列出 5 条列表记录或 3 组详情数据，覆盖所有业务状态、角色、分类和近期时间；禁止“测试用户”“标题1”等无意义文本。这些数据用于说明业务语义，不得变成撑满空白的装饰文案。
7. **交互流程**：点击、输入、筛选、分页、排序、拖拽、上传、确认、取消、成功、失败、重试、返回和跳转的可见反馈；说明触发后哪个区域变化。
8. **状态变体**：初始加载、加载失败、空数据、无权限、未登录、表单校验失败、保存中、保存成功、保存失败、删除确认和网络超时；需要独立屏幕时在所属端编号后追加状态名，如 `PC-Pxx-loading` 或 `M-Pxx-error`。状态变体不计入基础页面数。
9. **端内适配规则**：PC 页面只处理 PC 目标尺寸内的变化；移动页面处理移动尺寸、安全区、软键盘、手势、触摸和弱网。不得把“PC 到移动响应式变化”当作替代另一端独立设计的方式。
10. **可访问性**：语义结构、键盘顺序、焦点、label、错误关联、alt、对比度、非颜色状态提示和触摸目标尺寸。

## 五、端与页面类型补充要求

### 门户/用户中心

- 如果页面采用全局导航，导航应覆盖与当前任务相关的首页、搜索、分类/详情、收藏/业务入口、登录状态和个人菜单；如果设计器判断不需要全局导航，则在页面交付说明中写明入口、返回路径和替代方式。
- 详情页必须写主 CTA、状态、相关推荐、错误/空状态和返回路径。
- 用户业务流必须从入口到提交成功完整覆盖，不只画静态列表。

### 业务管理后台/超级管理员后台

- 根据内容密度和权限复杂度选择侧栏、顶部导航、标签导航、面包屑或其他合适的导航结构；若采用侧栏，明确其层级、当前菜单、折叠规则，否则说明替代结构。无论采用何种结构，都要明确筛选区、表格列、批量操作、权限隐藏和审计入口。
- 列表必须包含分页、搜索、筛选、排序、列空状态、操作确认、成功刷新和失败保留输入。
- 超级管理员页面额外区分用户、角色、权限、系统配置和危险操作确认。

### 移动端（统一包含 H5/微信小程序）

- 写明屏幕宽度、顶部安全区、底部安全区、手势/返回、吸底按钮、键盘遮挡和弱网反馈。
- 小程序页面不得依赖桌面 hover；所有操作提供触摸态和可见成功/失败反馈。

## 六、Stitch 执行顺序

1. 在同一个 Stitch 项目中先建立统一设计系统和组件基线。
2. 先完成 PC 端 `PC-P01 → PC-P{N_PC}`，再完成移动端 `M-P01 → M-P{N_M}`；也可按业务链路交替，但每个页面完成后都要检查端、布局、字段、状态、适配和可访问性。
3. PC+移动多端项目必须使用 `PC-Pxx-*` 与 `M-Pxx-*`；H5 和微信小程序共用移动端编号，通过“适用平台”区分，不生成 `H5-Pxx-*` 与 `MP-Pxx-*` 两套重复页面。
4. 需要状态变体时保留独立屏幕或明确可切换的 variant，并在名称中写出状态。
5. 完成后分别核对 PC 页面数、移动页面数、两端总数、命名、状态和资源；不要删除设计记录、跨端合并屏幕或用响应式变体减少数量。
